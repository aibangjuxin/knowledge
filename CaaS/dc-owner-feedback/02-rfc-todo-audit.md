## 二、逐条展开

### T5 · §8 能力目录 —— **你的主战场**

RFC 原文:

> 能力项包括 —— 地理支持、IAM、服务网格等。**[待补充]** —— 完整的能力目录在原文档中并未列举,
> 需定义为一个版本化的 schema,由 app.caep Compute 拥有,CTOi 云工程师参与贡献。

**为什么是 P0**:§7 说"每个工作负载通过集群申请单与工作负载准入画像声明自身需求。CaaS 依据这些需求
来选定兼容的云厂商、集群与管控画像"。**能力目录不存在,放置校验就无从写起。**

**你能给的**:GCP 侧全部 20 个维度的四态取值 + 证据。草案见
[`03-gcp-capability-profile.md`](./03-gcp-capability-profile.md)。

**我加的一条**(`07-decisions-and-open-questions.md` D2):四态要加一个**正交的证据新鲜度**标记。
理由:§8 自己写了"'尚未评估'不得被解读为'已支持'",但没有机制强制"已支持"这三条保持诚实。
一个 18 个月前评估过的 ✅,和一个上周评估的 ✅,不是一回事。

### T8 · §9.4 IAM 模型与 R&R —— **第二重要**

RFC 原文:

> **[待补充]** —— 同一账号下集群与其他资源之间的边界需要评估。IAM 模型与 R&R(角色与职责)需要达成一致。

**两句话,两个问题:**

1. **"同一账号下集群与其他资源之间的边界"** —— 这是在问:一个 GCP project 里,GKE 集群和别的资源
   (BigQuery / Cloud Storage / 其它服务)怎么隔离?谁的项目?谁的成本归属?
   **这个问题只有你能答**,而且它会决定 CaaS 的 `costAllocation` 字段怎么设计
   (见你的 `caas-finops.md` §成本归集)。
2. **"IAM 模型与 R&R"** —— 见 [`01-workplan.md`](./01-workplan.md) WP-4。

**你在这里的独特价值**:CaaS 的团队知道他们需要什么权限来**操作**集群;
只有你知道什么权限在这个组织里**可被授予**。这两个集合不一定相等。

**我建议的拆分**:IAM 模型 = 你出;R&R(运营职责的归属与交接)= app.caep SRE 出,你对技术部分复核。

### T10 · §12 运维与服务管理 —— **内容全无,但你要交一半**

RFC 原文:

> **[待补充]** —— 该服务设计必须在生产上线前定义以下内容,**其明细未能在原文档中保留下来**。
> 整体应与 app.caep SRE 战略保持一致。

**这里有个陷阱**:编辑把要列的明细整个丢了,所以我们**看不到 RFC 本来打算要求什么**。
但从 §6.3 契约项 5 和 §10 反推,至少要覆盖:备份、恢复演练周期、DR 态势、升级执行、变更窗口、
oncall、支持请求路由。**其中升级执行、备份保留、变更窗口是云侧输入。**

**你要交的**(`01-workplan.md` WP-3):

- 版本支持窗口与升级节奏
- 备份保留期要求(数据分级 → 保留期)
- **break-glass 流程的技术实现**(`caas-day2-ops.md` 已经写了你的版本,可以直接引用)

**别越界**:oncall 轮转、响应时间、SLO 数值是 SRE 的活,不是你的。
RFC §3 非目标已明确:"在各责任方验证之前,就先行确定……服务等级或数值化的 SLO"。

### T9 · §11.1 控制项映射 —— 你的角色是"可行性顾问",不是作者

RFC 原文:

> 起草本稿期间该标准内容无法获取,因为其页面需要通过 Confluence 进行认证访问。
> 因此,下文所描述的是一个自动化与证据**框架**,而非对该标准控制项的经核验转录。

**这一条跟你的关系是间接的,但不能不管**:安全架构师要写"每一条适用控制项 → 一条版本化编码策略"的
映射表,而**哪些控制项在 GCP 上真的可自动化**,只有你能说。

**你要提供的输入**(半页就够,不用你写映射表):

| 控制项类别               | 你的输入                                                     |
| ------------------------ | ------------------------------------------------------------ |
| 加密(静态/传输/使用中)   | CMEK 是否可用、哪些服务不支持 CMEK、Confidential Nodes 的限制 |
| 身份                     | Workload Identity 覆盖度、哪些工作负载类型做不到              |
| 网络隔离                 | VPC-native / Private cluster / Policy / PSC 能力             |
| 审计                     | Cloud Audit Logs 覆盖哪些操作、留存限制                       |
| 镜像                     | Binary Authorization 覆盖哪些 registry                        |
| 特权访问                 | Autopilot privileged 策略的 org policy 怎么管                |

**我建议**:主动约安全架构师一次会。你带能力输入,她/他带标准条款,当场对齐映射可行性。
**这是你这次最容易产生高杠杆的一小时。**

### T6 · §9.1 准入条件 —— 并行非生产/生产集群

RFC 原文:

> 应用必须提供**相互独立**的非生产与生产集群实例。每个实例都独立登记、独立纳管,
> 并且必须先满足相应的 CaaS 要求,之后才能被纳管或用于该环境下的工作负载。

**这条对你有直接影响**:DC 若有存量集群,可能存在"一套集群既跑 dev 又跑 prod"的现实。
**CaaS 会拒绝这种集群。** 你需要提前判断:DC 现有的混用集群怎么办?

| 选项                       | 成本           | 适用                                    |
| -------------------------- | -------------- | --------------------------------------- |
| 拆分集群                   | 高(重做数据层) | 数据可以分离                            |
| 同一集群、不同 namespace   | 无            | **RFC 不接受** —— 不要试图论证         |
| 走 `尚未评估` + 例外流程   | 中            | 若安全架构师批准                        |

**建议**:在 §9.1 就把"DC 现存混用集群 X 个"的实际情况摆出来,让 RFC 面对现实,
而不是等 BYOC 阶段 3 评估时才发现。
