## 0.5 · DC 实际立场(2026-09-29 确认)

| 项                  | 确认值                    | 对本文档的影响                                              |
| ------------------- | ------------------------- | ----------------------------------------------------------- |
| **集群模式**         | **全部 `Standard`**       | ⬇️ Autopilot caveat 降级;⬆️ **CaaS 节点编排责任变大**       |
| **Release channel** | **全部 `Stable`**         | 版本节奏最保守;**可放心排除 Rapid 的 SLA 风险**             |

### 这两个选择组合起来意味着什么

`Standard` + `Stable` 是 **DC 风险偏好最低**的组合。它的四个直接后果:

| #  | 后果                                                       | 影响的文档/工作                        |
| - | ---------------------------------------------------------- | -------------------------------------- |
| 1  | **节点层完全由 DC/CaaS 负责**                              | CaaS Day-2 编排责任**上升**(见下 §3.1) |
| 2  | **新特性延后 2–3 个月**才可用                               | AI/GPU 类新能力的引入节奏要相应放慢    |
| 3  | **✅ 稳定在 GKE SLA 内**(不像 Rapid 那样被排除)            | 已有安全保证,无需额外声明              |
| 4  | **可获得完整 maintenance exclusion 权限**                  | 维护窗口可控,利于 `04` 模板的窗口声明 |

### ⚠️ Stable channel 在 BYOC 上的一个具体坑

Stable channel 的**可用 minor 版本区间比 Rapid 窄**(新版本进 Stable 最晚)。
结果可能是:

> **一个跑在较新 minor 版本上的存量集群,可能无法加入 Stable channel。**

**这直接影响你几十个存量集群的纳管**(见 [`12-byoc-scaleup-playbook.md`](./12-byoc-scaleup-playbook.md)):
如果某集群的版本高于当前 Stable 支持的最高版本,它要么降级,要么留在 `No channel`。

**行动**(纳入 `12` §1.2 分类自查):
```bash
# 对每个存量集群:当前版本 vs Stable 通道的可用区间
gcloud container clusters describe <name> \
  --format="value(currentMasterVersion,releaseChannel.channel)"

# 对照 Stable 当前支持的 minor 版本区间
# https://docs.cloud.google.com/kubernetes-engine/docs/release-schedule
```

> **这一条会影响 A/B/C 分类结果的分布** —— 建议在跑分类自查时一并采集。

### 概念对照(避免后续混淆)

| 概念               | 合法取值                                     | DC 实际 |
| ------------------ | -------------------------------------------- | ------- |
| **集群模式**       | `Standard` / `Autopilot`                     | ✅ `Standard` |
| **Release channel** | `Rapid` / `Regular` / `Stable` / `Extended` | ✅ `Stable` |
| ~~(已废弃)~~      | `No channel`                                 | ❌ 未使用 |

> **两个"标准"是不同概念** —— `Standard` 是模式,`Stable` 是通道。
> 后续文档一律用完整术语,避免再出现"都用 Standard 版"这种双关表述。

### 确认 Standard 模式后的连锁影响

| #  | 影响                                                    | 说明                                                |
| - | ------------------------------------------------------- | --------------------------------------------------- |
| 1  | **Autopilot 类 caveat 降级,但不删**                     | DC 不用,但 RFC 是组织级的,其它团队可能在用         |
| 2  | **`gke-caas.md` 的 `default: autopilot` 明确错了**      | 见 `14-doc-conflict-review.md` C3                   |
| 3  | **🆕 Standard 模式 → 节点层配置由 DC 定,升级执行由 GKE 做** | **默认能力足够,但缺默认安全基线** —— 见 §3.1       |

### 第 3 点值得单独说:Standard 模式让 CaaS 的活变多了(2026-09-29 已修正)

> #### ✅ 更正:我原来把"必须由 CaaS 编排"说过头了
>
> **你的理解是对的,我写错了。**
>
> 你说:Standard 模式下开了 auto upgrade、配了 maintenance window、且有"必须自动升级"的严格要求
> —— **这正是 GKE Standard 的标准用法,能力完全够用,CaaS 不需要重做一遍升级编排。**
>
> **我原文的错误在于把两件事混为一谈:**
>
> | 我混淆的                    | 实际是什么                                                          |
> | -------------------------- | ------------------------------------------------------------------- |
> | **谁来配置**节点升级参数     | **DC 的策略决定**。这是 DC 的治理权,**不是 CaaS 的工作量**           |
> | **谁来执行**升级             | **GKE 做的**。auto-upgrade + maintenance window 生效后,GKE 自动完成  |
>
> **"DC 要自己选策略" ≠ "CaaS 要编排升级"。** 前者是决策,后者是工作。
> 我把决策权错记成了工作量。**这是我的错,不是你的场景特殊。**

> #### ✅ 正确的表述:CaaS 不编排执行,CaaS 提供**默认安全基线**
>
> **GKE 侧的默认行为已经覆盖了你的场景**(核实自官方文档):
>
> | 机制                    | GKE 默认值                                | 是否需 DC 配                    |
> | ----------------------- | ----------------------------------------- | ------------------------------- |
> | Standard 节点池 auto-upgrade | **默认开启**(`upgrading nodes` 文档明确) | ❌ 默认就是开的                  |
> | 维护窗口                 | 无(默认任意时间可升级)                    | ✅ 你已配                        |
> | 升级策略                 | **surge**(默认)                          | 🔶 不配也能跑,配了更稳            |
> | 节点版本与控制面同步      | GKE 自动处理,遵循 version skew policy   | ❌                              |
> | 到期强制升级            | 版本支持窗口结束时自动触发                 | ❌ **且不可关闭**                |

> **所以:CaaS 要做的不是"编排升级",是"确保默认值是安全的"。**

| 能力                     | Standard 下的现实                                          | CaaS 真正该做的                    |
| ------------------------ | --------------------------------------------------------- | ---------------------------------- |
| **节点升级策略**          | **surge 是默认,已能自动跑。**DC 可选 blue-green            | **不编排执行**;把推荐策略写进画像作为**默认值** |
| **节点池自动伸缩**        | Cluster Autoscaler 需配 min/max                            | **Day-0 注入安全边界**(防成本失控)  |
| **节点自动预配(NAP)**     | 默认关闭,需显式配置                                        | **默认不启用**,作为画像可选项        |
| **节点池数量治理**        | 节点池会随需求膨胀                                          | **成本归集 + 异常告警**,不主动删除  |
| **系统组件升级**          | GKE 托管大部分                                              | ❌ 不需要                          |
| **Pod 密度规划**          | 标准 256 Pods/节点                                         | 容量模型参考,非 CaaS 责任           |

> **换句话说:选 Standard 不意味着"少一个云厂商能力"。**
> **它意味着"CaaS 的职责从'做升级'变成'把安全的默认值铺好,让 GKE 自己跑'。"**

> #### ⚠️ 升级容量余量 —— DC 已有实践覆盖,画像层只需确认不推翻
>
> **⚠️ 2026-09-29 再修正:我原先写"至少 1 个节点"是偏保守的技术错误。**
>
> **核实官方文档后:**
> - GKE 集群规模上限是 **15,000 节点**(不是"上千");`maxSurge` 同时升级上限 Standard 模式 100。
> - surge 需要的是**项目级 CPU/内存/GCE 资源余量**,**不是节点总数**。
> - 真正会卡住 surge 的不是集群规模,是 **`--total-max-nodes` / autoscaler 上限** 和 **项目配额**。
>
> **DC 实际做法已覆盖这个风险(2026-09-29 确认):**
> - 默认让集群运行在 **~80% 负载** —— 天然留出 20% 余量
> - 集群不够用时**自动扩容**
> - **有监控**
>
> **所以这不是 DC 的风险敞口,是"画像层别把已有实践推翻"。**
>
> | 画像层该做的                        | 不该做的                          |
> | ---------------------------------- | --------------------------------- |
> | **确认** autoscaler 上限 ≥ 业务峰值 + 升级并行度 | ❌ 定死"必须留 N 个节点"        |
> | 确认 maintenance window **不与扩容告警窗口重叠** | ❌ 重新设计 DC 的容量策略          |
> | 确认 80% 目标在 CaaS 画像里被记录   | ❌ 假设 CaaS 比 DC 更懂容量         |
>
> **画像里建议写的是(而不是节点数):**
>
> ```yaml
> capacity_policy:
>   utilization_target: 0.80      # DC 既有实践,画像记录即可
>   autoscaler:
>     #   ⛔ 关键:上限必须 > 业务峰值,否则 surge 建不出新节点
>     #   maxSurge + maxUnavailable 决定同时升级几个节点
>     total_max_nodes: ">= peak_load + upgrade_parallelism"
> ```
>
> #### 📌 升级时序 —— 不是 CaaS 的考虑范围(2026-09-29 第三次修正)
>
> **我原先写"几十个集群同时进维护窗口可能集体卡住",这个风险不存在。**
>
> **DC 的实际情况:**
> - **maintenance window 是每个集群单独配的**,GKE 不会替你统一排时
> - DC **已在按时段/区域错开** —— 规定时间内只升级某些区域的集群
> - 升级节点时间**独立设置**
>
> **所以"同时大规模升级"这个前提本身就不成立。是我假设了一个 DC 已经防住的场景。**
>
> **职责划分(正确的):**
>
> | 谁                              | 负责什么                                |
> | ------------------------------- | --------------------------------------- |
> | **DC**                          | 窗口怎么排、错峰策略、区域节奏           |
> | **GKE(云厂商)**                 | 窗口内执行升级、版本可用性、EOL 强制时点  |
> | **CaaS**                        | **只需知道这个概念存在**                 |
>
> **CaaS 唯一该做的是:在输入模板里留一个 `maintenance_window` 字段,让业务方声明。**
> **不排期、不检查冲突、不做容量余量计算。** 那是 DC 的既有职责,不该被 CaaS 接管。
>
> **这条留在这里,是因为它是我连续三次犯的同一类错误的样本:**
> 拿通用最佳实践当结论 → 没先问 DC 实际怎么做 → 造出一个 DC 已经防住的风险。

## 1. Schema 草案(与 app.caep Compute 共同定)

### 1.1 RFC 已规定的部分 —— 不要改

RFC §8 原文:

> 画像必须以**已支持**、**有限支持**、**不支持**或**尚未评估**这四种状态来声明能力。
> **"尚未评估"不得被解读为"已支持"。**

这四态是**强制的**,不是我加的。以下 schema 设计要在这四态之上做扩展。

### 1.2 我建议的能力条目结构

```yaml
- id: network.pod-cidr            # 稳定的点分 ID,CaaS 放置校验按它匹配
  dimension: networking            # 归到 20 个维度之一
  scope:                          # 作用域 —— 关键:让 Autopilot/Standard 不必压成一行
    mode: [autopilot, standard]   # 这个取值在哪些 cluster mode 下成立
    region_scope: all              # all | [asia-northeast1, ...] | per-region
  status: limited                  # RFC 四态之一,不可自定义
  caveat: "hostPath 写模式被禁;仅 /var/log 前缀只读"
  blocking: false                  # true = 不满足则拒绝放置
  evidence:                        # ← 我建议新增,见 §5
    source: "https://docs.cloud.google.com/..."
    assessed_at: "2026-09-29"
    freshness: fresh               # fresh(<6mo) | aging(6-12mo) | stale(>12mo)
  owner: ctoi                      # 谁对这条结论负责
```

### 1.3 三个关键 schema 决策(我的意见)

#### 决策 A · 必须有 `scope`,不能让 Autopilot 和 Standard 压成一行

GKE 的 Autopilot 与 Standard 在**至少 6 个维度**上能力不同。压成一行会产生最坏结果:
CaaS 看到 ✅,业务方在 Autopilot 上跑 DaemonSet 采集 agent,被拒。

| 维度       | Standard                      | Autopilot                        |
| ---------- | ----------------------------- | -------------------------------- |
| 节点       | 自管                          | **GKE 全管,无节点概念**        |
| 拓扑       | zonal 或 regional             | **只有 regional**               |
| 特权容器   | 允许                          | **默认拒绝**,需 allowlist       |
| hostPath   | 允许                          | **仅 /var/log 只读**            |
| hostNetwork| 允许                          | **禁止**                        |
| 资源配额   | 按节点数算                    | **按 Pod 资源请求算**           |

> **这条主张我会在评审会上坚持。** 成本:schema 复杂度上升。收益:CaaS 不会做出错误的放置决策。

#### 决策 B · 状态枚举里必须有 `caveat` + `blocking` 两个字段

四态是 RFC 强制的,但四态表达不了"支持,但有约束"。加 `caveat` 后,
`limited` 才有信息量 —— 否则 `limited` 是个没有定义的黑洞词。

`blocking` 决定 CaaS 放置校验行为:非阻断的 caveat 可以走例外流程,阻断的必须拒绝。

#### 决策 C · 加 `evidence.freshness`(我给 RFC 的一条实质建议)

RFC 已经意识到证据时效问题 —— 它写"'尚未评估'不得被解读为'已支持'"。
**但它没有解决反向问题:一个 18 个月前评估过的 ✅,和上周的 ✅,在文档里长得一模一样。**

对 GCP 尤其严重,因为 GKE 迭代很快:Autopilot 权限从 1.34 引入、Confidential Nodes 2023 年 GA、
Windows Server 2019 节点镜像 2025-12 后已冻结。

**成本**:每次能力评估多记两个字段。**收益**:CaaS 可以自动把 `stale` 的 ✅ 降级为 `尚未评估`。
**这一条我认为值一个决策记录**(见 `07-decisions-and-open-questions.md` D2)。

## 2. 四态的使用纪律

| 状态         | 含义                          | 你交的时候必须附带的证据                          |
| ------------ | ----------------------------- | ------------------------------------------------- |
| **已支持**   | 该云原生提供,无重大限制      | 文档链接 + 查阅日期                                |
| **有限支持** | 可用但有实质约束              | **caveat 写清楚具体约束** + 文档链接               |
| **不支持**   | 技术上做不到,或代价不可接受  | 文档链接或技术论证 —— **这条最值钱**              |
| **尚未评估** | 还没查                        | **不能**当作已支持(RFC 明确)                      |

> **你的立场:一份全是 ✅ 的能力目录是负资产。**
> 它让 CaaS 误判工作量,让它在排期时相信一切顺畅,然后在生产上发现"这个做不了"。
> 你写的每一个 `不支持`,都会成为 CaaS 排期时的一个既定事实。
> **主动交坏消息,是你在这个项目里最划算的投入。**

### 2.1 ⚠️ 每条 `不支持` 必须配一个替代方案(评审会上一定被追问)

只给 `❌` 而不给替代路径,评审会上会被问"那怎么办",答不上来会显得没准备。

**建议在能力目录 schema 里加一列 `alternative`**:

| 不可支持的诉求          | 替代路径                                                          | 代价                 |
| ---------------------- | ----------------------------------------------------------------- | -------------------- |
| GPU 独占拓扑            | 配额隔离 + 专用节点池(taint/affinity)+ 资源上限                  | 弱隔离,须讲清差别   |
| 物理隔离                | sole-tenant nodes(⚠️ **不支持 Autopilot**,节点巨大需提额)        | 成本高、容量受限     |
| 使用中加密 **+** 独占   | **⚠️ 两者互斥,无替代** —— 只能取舍                              | 无                  |
| Autopilot 特权工作负载  | 切 Standard,或申请 `WorkloadAllowlist`(GKE 1.35+)               | 需走审批            |
| Autopilot 采集类 DaemonSet | 使用官方 allowlist 的 agent,或改用 GKE 原生观测方案            | 采集能力可能打折    |

> **显式承认"有些东西给不了",比被发现给不了好得多。**
> 而"两个诉求互斥"这种信息尤其重要 —— 它只有你知道,
> 因为只有你同时了解这两项能力的限制。

## 3. GCP 能力矩阵(草案 · 20 维度)

图例:`✅` 已支持 · `🔶` 有限支持 · `❌` 不支持 · `⬜` 尚未评估

### 3.1 集群生命周期与版本

> **前提**:DC 全部使用 **Standard** 模式(2026-09-29 确认)。
> 因此"节点层"相关能力**全部由 DC/CaaS 负责**,不是 GKE 托管。

| 能力                                     | 状态   | caveat / 依据                                                                 | DC 需确认                |
| ---------------------------------------- | ------ | ----------------------------------------------------------------------------- | ------------------------- |
| 自动创建集群                             | ✅     | GKE API `CreateCluster`,异步 LRO                                            | 项目/区域配额 `🔶`        |
| 托管控制面                               | ✅     | GKE 管理,客户无 etcd 负担                                                    | —                         |
| ~~Autopilot(无节点)~~                   | —      | **DC 不使用**。但 RFC 是组织级,保留此行供其它团队参考                       | 见下方"Autopilot caveat" |
| **节点池生命周期**                       | ✅     | **Standard 下配置由 DC 定、升级由 GKE 执行**(auto-upgrade 默认开启);窗口与错峰由 DC 排 | 成本归集规则 `🔶` |
| 多可用区 / regional 集群                 | ✅     | regional 需 `roles/container.clusterAdmin` 跨区                              | 允许的 region 列表 `🔶`   |
| K8s 版本支持窗口                         | ✅     | **标准 14 月 + Extended 10 月(需 Extended channel,额外按集群收费)= 最长 24 月** | ✅ **Stable**(已确认) |
| 自动 patch 升级                          | ✅     | 可每周发生;maintenance window / exclusion 可控                              | 窗口策略 `🔶`             |
| minor 版本升级(1.33+)                   | ✅     | **两步升级**,可 soak、可回滚                                                | 升级节奏 `🔶`             |
| **90 天控制面升级底线**                  | ✅     | **GKE 强制**:控制面至少每 90 天升一次 patch,超时 GKE 自行升级               | —                         |
| **EOL 强制升级**                         | 🔶     | **EOL 后 GKE 强制升级,maintenance exclusion 无法阻止**(紧急情况除外)        | 通知义务 `🔶`             |
| Extended channel(超 14 月长支持)         | ✅     | 额外按集群收费;**DC 当前不用**                                              | 成本模型 `🔶`             |
| **Stable channel(DC 采用)**              | ✅     | **新特性延后 2–3 个月**;✅ **在 GKE SLA 内**;可获得完整 maintenance exclusion | **已确认** |

> ##### 📌 对账注意:WI 可变,但有 3 个非 API 步骤
>
> ~~初稿曾写"Workload Identity 绑定集群创建后不可变更"。经 2026-09-29 复核,
> **该说法错误,已更正。** 实际是:集群与节点池启用 WI 后,
> KSA 注解、GSA 上的 `roles/iam.workloadIdentityUser` binding 均可增删改。
>
> **但 CaaS 的对账逻辑仍需注意三件事 —— 它们都不是纯 API 调用:**
>
> | 事项                   | 性质                                                       | 对 CaaS 的含义                                              |
> | ---------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
> | 节点池 `GKE_METADATA`  | 需 `gcloud container node-pools update`,**触发滚动节点升级** | **有工作负载影响** → 必须走灰度/维护窗口,不能自动修        |
> | IAM 传播               | 授权后**最长约 60 秒**才生效                                | 立即验证会误报为失败 → 对账需带传播延迟与重试               |

> CaaS 的"发现 → 常规对账 → 特权整改"三身份划分(§10)正好对应这个边界 ——
> 建议在能力目录里把这一条作为该划分的**实例证据**写进去,它比抽象论述更有说服力。

### 3.4b 🆕 有状态服务(2026-09-29 依 DC 实战回填)

> **这一节是本次回填新增的。** 原来的能力目录只覆盖了"集群"和"集群周边",
> 漏了 **K8s 生态里那些被多个集群共享的有状态服务** ——
> 而它们是几十集群时代**比 GKE 配额更早爆的瓶颈**。

> #### 🆕 前置:⚠️ GCP 服务分两类,私有访问路径完全不同
>
> DC 实证(`cross-project/cross-project-bigquery.md` 记录 GCP 官方分类):
>
> | 服务类型                    | 例子                                            | 私有访问方式                          |
> | --------------------------- | ----------------------------------------------- | ------------------------------------- |
> | **Google 生产基础设施 API** | BigQuery、Cloud Storage、Compute API、KMS、IAM  | **PGA** + `*.googleapis.com` private VIP |
> | **VPC-hosted 服务**         | **Cloud SQL**、Filestore、**Memorystore/Redis** | **PSC**(或 PSA / peering)              |
>
> **BigQuery 走 PGA 不走 PSC** —— 它是 PaaS,不暴露 producer VPC,**没有 Service Attachment 可申请**。
> **能力目录不能笼统写"支持 PSC"** —— 必须标注每个服务走哪条路。

| 服务                    | 状态   | 关键约束                                                       | 私有访问 | DC 需确认        |
| ----------------------- | ------ | -------------------------------------------------------------- | -------- | ---------------- |
| **Cloud SQL(PostgreSQL)** | ✅   | **瓶颈是连接数,不是 CPU**。`max_connections` 由实例规格决定;**多个集群的连接池总和共享同一个上限** | **PSC** | 实例规格 `🔶` |
| **Cloud SQL → GKE 路径**| ✅     | 走 **PSC**;`psa-psc/Kiro-psc-CloudSQL.md` 有实证                 | PSC     | 标准路径 `🔶`    |
| **Memorystore / Redis**  | ✅     | **走 PSC,且 Redis 会"自动创建服务附件"** —— 不像 Cloud SQL 需手工建 ILB+SA | PSC | 实例规格 `🔶` |
| **BigQuery**             | ✅     | ⚠️ **走 PGA 不走 PSC**;跨项目需 **auth(WI)+ network(PGA)双腿**,缺一无效 | **PGA** | `🔶` |
| **PostgreSQL 连接池治理**| 🔶     | 需限定单用户连接数、`statement_timeout`、`idle_in_transaction_session_timeout` | — | 策略 `🔶` |

> #### 🔴 有状态服务的编排流程按服务不同
>
> **Cloud SQL**:producer 侧需手工建 ILB + Service Attachment
> **Redis**:**自动创建 Service Attachment**
>
> **如果 CaaS 把两者当同一种"有状态服务"处理,会在 Redis 上多出不必要的人工步骤。**
> 能力目录里有状态服务维度要**按服务逐个列**。

> #### 🔴 为什么连接数是"跨集群共享池"
>
> ```
> Cloud SQL 实例(max_connections = 1500,按规格而定)
>    ├── 集群 A 的 200 个 Pod × 连接池 10 = 2000  ← 打满
>    ├── 集群 B 的 100 个 Pod × 连接池 5  = 500   ← 抢不到
>    └── ...
> ```
>
> **这与 `13` 号文件 R2 说的 GKE 集群配额是同一类问题,但对象是有状态服务。**
> 区别在于:GKE 配额不足时报错清晰,而**数据库连接数不足时报的是"性能下降"** ——
> **更难归因,恢复更慢。**
>
> **建议新增一条 RFC 开放问题**(已写入 `11` 的 N4):
> `CaaS 的容量模型是否覆盖对 Cloud SQL / Memorystore 的连接数预算?`

| GPU 节点自动伸缩         | ⬜     | Autopilot 支持;Standard 需节点自动配置                      | —                   |
| 设备插件 socket 名长度  | 🔶     | 网络名 **超 41 字符** 导致 device plugin 启动失败           | **命名规范必读**    |

> #### 🔴 必须主动声明,不能留白
>
> **如果这几行是空的,会发生什么:**
> CaaS 的放置校验(§7)看到"加速器需求 = true",查能力目录**找不到明确结论 → 放行 →
> 置备阶段才失败**。业务方在申请时被告知"可以",几周后收到失败。
>
> RFC §8 写"'尚未评估'不得被解读为'已支持'" —— 这保护了 CaaS,
> **但没保护业务方**。**一条明确的 `不支持`,比一片空白对业务方友好得多。**
>
> **建议写法**:状态标 `尚未评估`,caveat 写 **"DC 主动不支持,非技术限制"**。
> 留空 = 别人以为你忘了填;写清楚 = 别人知道这是有意的决策。

> #### 🆕 真正该向 RFC 提的问题不是"要不要做 GPU"
>
> DC 已有 **Vertex AI 生产实践**(`vertex-ai/` 4 篇:BYOC 训练/预测 + IAM/CI-CD),
> 身份体系(trainer/predictor/pipeline 三 SA 分离)已建。
>
> **但 GKE 侧无 GPU 规划 —— 说明 AI 不跑在 CaaS 纳管集群上。**
>
> 而 RFC §7 把「AI 与 Agent 工作负载」列为四类场景之一,隐含"跑在 CaaS 集群上"的前提。
>
> **→ 已提为开放问题 N10:`§7 的 AI 工作负载是否指"跑在 CaaS 纳管集群上的 AI"?`**
> **这一条是在帮 CaaS 避免为一个 DC 不用场景设计准入画像。**


> #### 📌 关于下面那条 `❌`(技术结论,不是当前痛点)
>
> **GPU 独占拓扑给不了 —— 这条仍然是有效结论,原因记录如下。**
>
> **但请注意它在 RFC 里的定位**:
> - 之前我把它当成"最该主动交的坏消息"。**现在不应该了。**
> - 因为 DC 本身不提供 GPU 场景,**这条对业务方没有现实影响**。
> - 它现在的价值是:**当将来评估 GPU 时,不要重新踩这个坑**。
>
> **换句话说:从"立即交的反面消息"降级为"扩展位的技术约束"。**
> 它应该待在 `18-gpu-ai-assessment.md` 的扩展位模板里,而不是能力目录的显眼位置。
>
> 如果评审会要"你有什么做不到的",这**不是**那个答案 ——
> 真正的答案是 **"§7 的 AI 工作负载在 DC 侧由 Vertex AI 承载,不在 CaaS 集群上"**(见 N10)。

### 3.6 配额与容量

| 限制项                      | 值                     | 可否调整          | 对 CaaS 的含义                        |
| --------------------------- | ---------------------- | ----------------- | ------------------------------------- |
| 每 zone 集群数              | 50                     | ✅ 可申请         | 放置校验前置检查项                    |
| 每 region regional 集群数   | 50                     | ✅ 可申请         | 同上                                  |
| Standard 节点数/集群         | 最高 65,000(分档要求) | 需联系支持        | 大集群需提前报备                      |
| Autopilot 节点数/集群        | 5,000                  | 需联系支持        | 同上                                  |
| 节点数/节点池/zone           | 1,000                  | ❌ **硬限制**     | 节点池不能无限扩                      |
| Pods per node(Standard)     | 256                    | ❌ 硬限制         | 影响密度规划                          |
| Pods per node(Autopilot)    | 动态 8–256             | —                 | GKE 自行决定                          |
| Accelerator/Perf 类 Pod     | **每节点 1 个**        | ❌ 硬限制         | GPU Pod 无法密集部署                  |
| **`gke-resource-quotas`**    | **<100 节点集群自动对每个 namespace 施加,不可删除** | ❌ | 🔴 **见下**   |

> #### 🔴 最容易被漏掉的一个坑:`gke-resource-quotas`
>
> GKE 对**节点数少于 100** 的集群,会自动对每个 namespace 施加一个**不可删除**的资源配额
> (`gke-resource-quotas`),用来保护控制面免受业务 bug 冲击。这个配额**随节点数自动缩放**。
>
> **后果**:业务方申请集群时一切正常,规模涨上去之后开始莫名其妙申请不到资源,
> 而**查 CaaS 的配额发现 CaaS 什么都没设** —— 因为限制来自 GKE 自己。
>
> **CaaS 必须在申请校验与容量告警里显式读取这个对象**(`kubectl get resourcequota gke-resource-quotas`)。
> 我建议把这条直接写成 CaaS 的一个**强制需求**,而不是让你以后反复解释。

### 3.7 治理与策略(这一维是 GCP 相对其它云的**强项**)

| 能力                        | 状态 | caveat / 依据                                                       | DC 需确认      |
| --------------------------- | ---- | -------------------------------------------------------------------- | -------------- |
| **Policy Controller**        | ✅   | 基于 Gatekeeper;`enforcementAction` 可取 `deny` / `warn` / `dryrun`  | 强制哪些 `🔶`  |
| 审计既有资源(非仅准入)      | ✅   | Policy Controller 可**回溯审计已存在资源**,不只拦截新变更           | 审计周期 `🔶`  |
| **Config Sync**            | ✅   | GitOps,**持续检测配置漂移**并修复                                    | 仓库结构 `🔶`    |
| **Config Controller**        | ✅   | 托管版 Config Connector —— 用 K8s 声明式管理 GCP 资源                 | 是否启用 `🔶`  |
| **审计可回溯,但结果有上限**  | 🔶   | 可审计既有资源;但 `totalViolations` 计数可能**大于**实际列出的条目 —— 超上限部分只计数不列明细 | 证据包怎么表述 `🔶` |
| **Binary Authorization**         | 🔶     | 需**分别配置 GCR 与 GAR**(DC 实证两个都在用);GAR 端点带 region 前缀(`*.pkg.dev`),跨 region 拉取有延迟与出网成本 | registry 清单 `🔶` |
| **🆕 镜像 tag 实践**            | 🔶     | **DC 实证大量使用 `:latest`** —— 与"生产用不可变 tag/digest"冲突。**建议:BYOC 不作硬门槛,新集群默认强制 digest** | BYOC 门槛 `🔶` |
| Binary Authorization 豁免   | 🔶     | 需要豁免流程(镜像回溯)                                               | 流程 `🔶`      |
| Policy Bundle                | ✅   | 官方维护的策略包,可作策略基线起点                                    | 选哪套 `🔶`    |
| **升级编排(rollout sequencing)** | ✅ | **需集群归入 fleet**,每序列最多 5 组,soak 上限 30 天;需 `roles/gkehub.editor` | 是否启用 `🔶` |

> 💡 **这是你在能力目录里最该显摆的一栏。** 其它三朵云在"策略 + 漂移检测"这一格上,
> 大多只能给 `🔶 需要适配`。GCP 这里给的是完整的
> **Policy Controller(执行) + Config Sync(漂移) + Config Controller(声明式管理)** 三件套,
> 而且 Config Controller 托管运行,省掉安装维护。
>
> **CaaS 的"对账即运维模型"(RFC §5)在 GCP 上落得最顺。** 这句话你写进 §8,
> 是对 CaaS 排期最有说服力的支持性论据 —— 但同时意味着 CaaS 应当在 GCP 上
> **优先复用这三件套,而不是自己再造一个漂移检测引擎**。

> 📌 **rollout sequencing 的隐藏依赖**:它要求集群**归入 fleet(Anthos)**。
> 换句话说,想用 GKE 官方的灰度升级编排,**前提是这个集群已经在一个 fleet 里**。
> CaaS 如果要提供"按环境分批升级"的自动化,要么自己管 fleet 成员关系,
> 要么接受 GKE 的 fleet 作为前提。这是一个需要在 §8 里讲清楚的**架构前提**。

## 4. 能力目录里最容易踩的四个口径问题

给评审会用的,免得被问倒:

### 4.1 "已支持"不等于"CaaS 不用做任何事"

GKE 原生支持 ≠ CaaS 零工作量。比如 Workload Identity:GKE 提供机制,
但**"哪个工作负载用哪个 GSA"是 CaaS 的准入画像要管的事**。
建议能力目录的 `caveat` 字段明确区分:

- `native` — 平台原生,零适配
- `platform-supported` — 平台支持,但 CaaS 需编排
- `adapter-required` — 需 CaaS 写适配

### 4.2 "尚未评估"要真的留白,不要偷偷变成 ✅

RFC 明确禁止。**留白不丢人,假装评估过才丢人。**
GCP 侧我现在敢标 `⬜` 的:etcd 备份等价性、Filestore regional 细节、备份标准方案、
Windows 节点全貌。**这些留在白区,比编一个答案有价值。**

### 4.3 区域差异要单列,不要藏在 caveat 里

同一个能力在 `asia-northeast1` 和另一个区域可能不同。
建议 schema 有 `region_scope` 字段,并让 CaaS 在放置校验时**按 region 查表**。
**这是 DC 最应该硬性坚持的一个 schema 字段** —— 因为你的区域清单是动态变化的。

### 4.4 加速器能力不要和普通资源用同一套字段

GPU / TPU / 高内存在**配额、机型、隔离、计费**上完全不是一回事。
你的 `caas-providers.md` 已经指出 AI 工作负载要单独建模,这里要在 schema 层落地,
而不是等到实现时再发现。

## 5. 证据规则(我建议写进 RFC)

每条非 `尚未评估` 的结论必须带:

1. **文档 URL**(官方文档优先)
2. **查阅日期**
3. **freshness 判定**:`fresh`(<6 月)/ `aging`(6–12 月)/ `stale`(>12 月)
4. **CaaS 侧每 6 个月自动把 `stale` 的 ✅ 降级为 `尚未评估`**

第 4 条是关键。**它让"能力过期"变成一个自动发生的、可观测的状态,
而不是依赖某个人在某天想起来复查。**
