# 05 · BYOC 存量集群纳管交付物包

> **对应 RFC**:§9.1 准入条件、§9.2 八阶段、§9.3 移交契约、§9.4 纳管结果
>
> **适用前提**:DC 有存量 GKE 集群希望交给 CaaS。**如果没有,本文件降级为参考,
> 只读 §2(准入条件对照)和 §4(混用集群问题)即可。**

---

## 1. 为什么 BYOC 这条路值得你花时间

RFC §1 说得直接:

> 若要求每个团队都替换掉正在正常运行的基础设施,将拖慢采纳速度并引入本可避免的迁移风险。
> 反之,若在缺乏严格基线的前提下就接收既有集群,则平台级的安全与支持承诺将无法被强制执行。

**你的处境正好在中间**:DC 是 GCP 的 owner,很可能已经有若干 GKE 集群在跑。
**这批集群是 CaaS 的第一批真实供给,也是最容易成为负担的一批。**

**但请先想清楚一件事:纳管意味着交出运维权。**
你的团队会失去对自己集群的直接控制。这是**组织决策,不是技术决策**。
本文件的技术部分只占一半,另一半(`06-boundary-and-raci.md`)是签字权与 break-glass。

## 2. §9.1 准入条件对照表(交之前逐条打勾)

| #  | RFC §9.1 要求                                     | 自查                                                                 |
| -- | ------------------------------------------------- | -------------------------------------------------------------------- |
| 1  | 提供云厂商                                        | GCP ✅                                                               |
| 2  | 提供位置                                          | region/zone 须在 DC 允许清单内 `🔶`                                   |
| 3  | 提供租户 / 应用清单                               | 命名空间 + 归属方 + 环境,需完整到"能识别出未知/孤立工作负载"         |
| 4  | 提供 K8s 版本                                     | 需在 GKE 支持窗口内 —— **不在窗口内是硬阻塞**(见 §3)                  |
| 5  | 提供数据分级                                      | 公开/内部/机密/受监管                                               |
| 6  | 提供工作负载与依赖关系                             | 含跨项目依赖                                                        |
| 7  | 提供维护窗口约束                                  | 含"不可中断"日期                                                    |
| 8  | 提供当前运维模式                                  | 谁在做、什么频率、什么工具                                           |
| 9  | **先**授权只读发现                                | ⛔ 顺序强制:**没有只读发现授权,后面全部走不了**                      |
| 10 | 云厂商与位置有已评估的画像                          | 依赖 `03-gcp-capability-profile.md` 交付                             |
| 11 | 该画像支持集群各项要求                              | 依赖能力目录                                                         |
| 12 | **非生产与生产是相互独立的集群实例**                 | ⛔ 硬要求,见 §4                                                      |

> **第 9 条是顺序上的强约束,容易被忽略。**
> 业务方常常想"先给 CaaS 权限看看会怎样",但 RFC 的顺序是反的:
> **先授权只读发现 → CaaS 出评估报告 → 双方确认差距 → 才谈后续权限。**
> 如果你在 DC 内部先开了全量管理权限给 CaaS,等于跳过了 Discover 阶段,
> 后面 §9.2 的 6 个阶段就没有可信的评估基础了。

## 3. 存量集群的已知差距(提前自查,省掉阶段 3 的来回)

下面这些是 GKE 存量集群最常见的硬伤。**自己先查一遍,比让 CaaS 查出来再改体面得多。**

| 差距                                 | 为什么是问题                                | 整改动作                                    |
| ------------------------------------ | ------------------------------------------- | ------------------------------------------- |
| **K8s 版本已过 EOL 或接近 EOL**      | ⛔ **硬阻塞**。GKE 会强制升级且无法用 exclusion 阻止 | 立即排升级。这是纳管前的第一件事          |
| 未加入 release channel               | 升级节奏不受控,无法排期                    | 加入 Regular 或 Stable channel              |
| 用了 1.33 之前的老版本                 | **无两步升级**,即无 soak、无回滚           | 先升到 1.33+ 再谈纳管                      |
| Autopilot 集群                        | 能力矩阵与 Standard 不同,画像需分别评估     | 标注 mode,CaaS 按 mode 出结论              |
| 用了 Cloud SQL / GCS 等跨服务依赖      | 边界不清晰,成本与退役归属会扯皮            | 列出依赖,写进退出计划                      |
| 集群过大(接近节点/集群上限)           | 纳管后升级与整改的影响面巨大                | 评估拆分或先扩容                            |
| 无 release channel + 无维护窗口       | 升级会在业务高峰期打过来                    | 定义 maintenance window                     |
| 单集群同时跑 dev 与 prod              | ⛔ §9.1 硬要求,见 §4                        | 拆分                                        |
| 无备份,或备份未验证可恢复             | §6.3 契约项 5 要求**实测过的**恢复          | 建立并**演练**一次,留日期记录              |
| 无退出计划                             | §6.3 契约项 4 硬要求                        | 补一份                                      |
| 工作负载无归属标注                     | §6.3 契约项 6 要求清单**不得仅依赖人工声明** | 打标签,让 CaaS 能自动发现                 |

### 3.1 版本这一条要单独强调

**GKE minor 版本最长支持 24 个月**(14 标准 + 10 扩展,扩展需 Extended channel 且额外收费),
而且**这是 GKE 给的上限,不是你能争取到的**。过了就是强制升级,你的策略挡不住。

因此对存量集群纳管:

> **任何已过 EOL 的集群,不要交给 CaaS。**
> 让 CaaS 纳管一个即将被 GKE 强制升级的集群,等于让 CaaS 承担一次
> "你无权阻止、但你必须提前通知"的责任 —— 而 CaaS 根本不知道这个集群的存在。
>
> **先升版本,再谈纳管。顺序反了,你会同时失去版本控制和纳管进度两条线。**

## 4. ⚠️ 混用集群问题(DC 需要现在就决策的事)

RFC §9.1:

> 应用必须提供**相互独立**的非生产与生产集群实例。

**DC 若有"一套集群既跑 dev 又跑 prod"的现状,必须提前决定怎么办。**

| 选项                  | 成本                        | 何时选                                    |
| --------------------- | --------------------------- | ----------------------------------------- |
| **A. 拆成两个集群**    | 高:数据层、配置、CI/CD 都要拆 | 数据本身可以分离                          |
| B. 同一集群不同 namespace | 零                       | ⛔ **RFC 不接受,不要试图论证**            |
| C. 走安全例外          | 中:需安全架构师批准且限时    | 若 A 短期内不可行                        |
| D. 暂不纳管该集群      | 零                        | 保持现状,明确记录"不在 CaaS 范围内"      |

**我的建议:选 A 或 D。**
选项 C 会制造一个永久性的例外,而 RFC §5 明确要求例外"必须保持显式、已审批且有时限"——
一旦开了口子,后续所有 DC 都会来要。

**在 §9.1 就把 DC 的真实数量摆出来**(例:"现存混用集群 3 个,计划 Q4 拆分"),
**让 RFC 面对现实,而不是等 BYOC 阶段 3 评估时才发现。**

## 5. 八阶段交付清单

| 阶段            | 你的交付物                                                   | 卡点                                 |
| --------------- | ------------------------------------------------------------ | ------------------------------------ |
| 1 Register      | 集群台账(机器读)                                              | 归属方要能到人                       |
| 2 Discover      | **只读发现授权**(范围、有效期、撤销方式)                      | ⛔ 顺序强制                          |
| 3 Assess        | 已知差距清单(见 §3)                                           | 不要藏,藏了阶段 4 会更难            |
| 4 Remediate     | 整改计划:做什么 / 谁做 / 影响面 / 回滚                        | 升版本通常排在这里,周期最长         |
| 5 Integrate     | GKE 端权限、遥测出口、备份、云 API                             | 与 WP-4 的三身份模型对齐            |
| **6 Authorize** | **管理层签字**                                                 | ⛔ **最容易卡死的一步**,见 §6       |
| 7 Transfer      | 权限交接清单:**交什么 / 保留什么**                             | 保留 break-glass(见 §6)             |
| 8 Operate       | 接受 CaaS 变更流程的方式、变更窗口                            | 双方都要接受                        |

## 6. ⚠️ 第 6、7 步:签字权与 break-glass

### 6.1 第 6 步是组织问题,不是技术问题

RFC §9.2 阶段 6 的退出条件:

> **同时**留有现归属方与被授权的 CaaS 服务 Owner 的记录化批准。

**很多 BYOC 项目死在这里**:集群技术上完全符合,但**没有人有权签字把运维权交出去**。

**你要提前做的三件事:**

1. **确认 DC 侧谁有这个签字权** —— 按金额/风险分级的授权矩阵,不要临时找。
2. **确认签字人不会被"这是不是要走变更单"卡住** —— 如果流程上纳管算变更,
   那纳管窗口和变更窗口要对齐。
3. **确认签字人能代表的是"业务方"还是"技术方"** ——
   RFC 写的是"现归属方",如果业务方不同意交,技术方签了不算。

### 6.2 break-glass 必须书面保留

RFC §9.3:

> 移交之后,CaaS 成为期望集群状态的权威来源。原集群运维方**不得**再进行常规的带外(out-of-band)
> 集群变更;确需变更时须走 CaaS 流程。应急变更使用书面约定的 break-glass(打破常规)路径,
> 事后需被对账并接受审计。

**关键在"书面约定"四个字。**

> #### 🔴 我认为这是 BYOC 交接里最危险的一处
>
> 现实是:纳管之后,原运维方遇到紧急故障,**会直接上去改。**
> 这是本能反应,不是恶意。
>
> 如果 break-glass 没有书面约定,那么:
> - CaaS 看到漂移 → 自动对账修复 → **把原运维方刚做的紧急修复覆盖掉**
> - 而原运维方以为自己修好了,实际被回滚
> - 或者 CaaS 判定这是契约违反 → 集群进入 `Suspended` 状态(§9.4)
>
> **两种结果都很糟,而且第二种会引发 DC 与 CaaS 的组织冲突。**
>
> **你要坚持的**:break-glass 以书面形式写进 §9.3 移交契约,内容包括
> 谁能用、什么条件、走什么流程、事后多久内必须做对账。
> 你已有的 `caas-day2-ops.md` 里有 break-glass 流程设计,**可以直接引用进 RFC**。

## 7. 纳管结果四种状态的现实对照

把 RFC §9.4 的四种结果翻译成你会遇到的情况:

| RFC 状态                        | 你会怎么遇到它                                    | 你该做的                              |
| ------------------------------- | ------------------------------------------------- | ------------------------------------- |
| **Managed**                     | 一切正常,收 CaaS 的通告                          | 接受变更窗口                          |
| **Remediation required**        | 你还在运维它,但对外不能说是 CaaS 纳管            | 排整改。注意:**此时支持义务没转移**   |
| **Not supportable**             | 云厂商/配置/归属模式不满足前置条件                 | 记入"不在 CaaS 范围",不是失败       |
| **Suspended / management withdrawn** | CaaS 失去访问权、触及风险阈值、或契约被违反     | ⚠️ **最难的一种** —— 见下            |

### 7.1 `Suspended` 需要你提前想清楚

**被暂停意味着 CaaS 停止管控,而"期望状态的权威"瞬间回到原运维方手上。**

问题在于:这个瞬间,**谁在跑?** RFC 说"工作负载的连续性,以及运维责任的回归,必须事先规划并记录在案"。

**你要交的是这个"事先规划"**:在移交契约里写清

1. 什么情况会触发 `Suspended`(别让它变成"我们生气了")
2. 触发后多久内恢复
3. **恢复期间谁负责** —— 这条最容易漏
4. 触发条件在纳管期间如何被提前发现(而不是事后通知)

**你已有的 `caas-day2-ops.md` 里有关于 break-glass 与生命周期归属的内容,直接对接。**
