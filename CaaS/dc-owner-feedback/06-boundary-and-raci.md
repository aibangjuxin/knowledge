# 06 · 管理边界、R&R 与 RACI

> **对应 RFC**:§9.3 移交契约、§9.4 结尾「**[待补充]** —— 同一账号下集群与其他资源之间的边界需要评估。
> IAM 模型与 R&R(角色与职责)需要达成一致。」、§6.1「详细的 RACI……必须在生产上线前达成一致。」
>
> **这是你在整份 RFC 里最有杠杆的一份文件。**
> 因为边界不清导致的扯皮,代价远高于技术实现。

---

## 1. 为什么边界文档要由你写

| 谁知道什么                                                       |
| --------------------------------------------------------------- |
| app.caep Compute 知道 **CaaS 需要什么权限才能操作集群**          |
| **只有你知道什么权限在这个组织里可以被授予**                     |
| app.caep SRE 知道 **运维流程怎么跑**                             |
| **只有你知道谁有权批准、谁承担后果**                             |

**两个集合不一定相等。** 差集就是风险所在。

> **一条我建议写进 §9.3 的原则**:
> **"CaaS 要求的权限"与"DC 授予的权限"之间的差集,必须在纳管前显式列出并处理,
> 而不是等生产上发现缺失。** 补权限通常要停机。

---

## 2. §9.3 移交契约:必须写明的六件事

RFC 原文:

> 管理边界必须写明:云厂商账号 / 网络底座、工作负载层运维、备份与恢复、事件响应,
> 以及可能中断工作负载的变更,分别由谁负责。

### 2.1 边界表(逐项填空,不填不算完成移交)

| #  | 领域                            | 移交**前**          | 移交**后**        | 备注                          |
| -- | ------------------------------- | ------------------- | ------------------ | ----------------------------- |
| 1  | **云厂商账号 / 项目**           |                     |                    | 🔶 是否连 IAM 一起交?         |
| 2  | **网络底座**(VPC / 防火墙 / 路由) |                  |                    | ⚠️ 见 §3,这条最容易出事       |
| 3  | **集群层配置**                  |                     |                    | |
| 4  | **安全策略强制执行**             |                     |                    | |
| 5  | **版本升级**                    |                     |                    | 与 WP-3 联动                  |
| 6  | **工作负载层运维**              | **应用归属方**     | **应用归属方**     | 始终归业务方,不转移          |
| 7  | **备份与恢复**                  |                     |                    | 保留期与数据分级挂钩          |
| 8  | **事件响应**                    |                     |                    | oncall 归 SRE                 |
| 9  | **可能中断工作负载的变更**       |                     |                    | 变更窗口 + 谁批准             |
| 10 | **成本归属**                    |                     |                    | 与 `caas-finops.md` 联动      |
| 11 | **应急 / break-glass**          |                     |                    | ⛔ 书面保留,见 §4             |

> **第 6 行值得单独强调**:RFC §9.3 明确"集群归属方保留业务应用、工作负载与数据的所有权"。
> **工作负载层运维永远不转移。** 这条要写死,否则移交后 CaaS 会开始替业务方管 Pod,
> 而业务方会觉得"我的东西被接管了"。这通常是组织摩擦的起点。

### 2.2 双向覆盖(我的设计纪律)

**每一条边界都要同时回答两个方向:**

| 方向         | 问题                                             |
| ------------ | ------------------------------------------------ |
| **正向**     | 谁来做?需要什么权限?                             |
| **反向**     | 谁来监督?证据落在哪?出事了谁被通知?               |

只写正向的边界文档,上线三个月后必然出现"没人知道 CaaS 到底改了什么"的争论。

## 3. ⚠️ 网络底座边界 —— 我认为最危险的一条

RFC §9.4 留白里点到了:

> 同一账号下集群与其他资源之间的边界需要评估。

**这句话背后是一个具体的架构风险:网络底座常常是多集群共享的。**

```
DC 的 Shared VPC
   ├── 防火墙规则  ← 集群 A 需要开 22 端口
   ├── 路由 / 对等连接  ← 集群 B 依赖
   └── Cloud NAT  ← 集群 C 依赖其固定出口 IP

如果集群 B 被纳管,而 CaaS 顺手"优化"了共享 VPC 的规则:
   → 集群 A 的 SSH 断了
   → 集群 C 的出网 IP 变了,外部 API 白名单全部失效
```

**这类故障的爆炸半径远超单个集群。**

**你要坚持的三条边界规则:**

1. **CaaS 对网络底座的权限,默认是"只读"**,变更走独立审批流
2. **明确哪些网络资源是"共享的、不可由 CaaS 变更"** —— 写进 §9.3 边界表
3. **Cloud NAT 固定 IP 必须登记在册** —— 改了等于让所有依赖出网白名单的工作负载静默失败

> 💡 **建议**:在你的能力目录(03 号文件)里,把"共享 VPC / 跨项目网络"的
> `caveat` 明确写成"**存在集群间共享,变更影响面超出单集群**"。
> 让 CaaS 在读能力目录时就看到这一句,比在事故复盘时看到便宜得多。

## 4. Break-glass 条款(建议的完整文本)

这一段可以直接进 §9.3,拿去和 DC 法务 / 安全评审:

```markdown
### Break-glass 条款(建议稿)

**保留方**:原集群运维方(移交前归属方)

**保留范围**:仅限"恢复服务可用性"这一目的。
不保留常规变更权限 —— 常规变更一律走 CaaS 流程。

**触发条件**:
- 生产服务不可用,且 CaaS 的标准响应流程无法在约定时限内恢复
- 安全事件处置需要立即阻断

**使用流程**:
1. 通知 CaaS 服务 Owner(留时间戳记录)
2. 执行最小必要变更
3. 变更后 N 小时内提交变更说明(改了什么、为什么、影响面)

**事后对账**:
- CaaS 在收到变更说明后 M 小时内完成对账
- 若 CaaS 判定该变更为"应当固化进期望状态",由 CaaS 纳入基线
- 若判定为"不应存在",由原运维方在约定窗口内回退

**审计**:所有 break-glass 行为进入审计日志,并在证据包中单独标记。

**暂停联动**:break-glass 期间集群**不**进入 §9.4 的 Suspended 状态。
(原运维方使用约定的 break-glass 路径,不构成契约违反。)
```

> **最后一行是关键。** RFC §9.3 说"管理契约被违反"是 `Suspended` 的触发条件之一。
> **如果不显式豁免 break-glass,就会形成一个逻辑死结:**
> 你保留了 break-glass 权利 → 用了它 → CaaS 判定契约违反 → 集群被暂停 → 大家回头翻合同。
>
> **这个豁免必须写进 §9.3 原文,不能靠事后解释。**

## 5. RACI 草案(填 §6.1 那个空)

| 活动                          | App Owner | **CTOi 云工程(你)** | Compute | SRE | Cyber/Sec | CaaS 服务 Owner |
| ----------------------------- | :-------: | :-----------------: | :-----: | :-: | :-------: | :-------------: |
| 定义服务契约 / 边界           |    C      |         C           |    A    |  C  |     C     |       R         |
| 发布云厂商能力目录 §8         |    I      |         **R/A**     |    C    |  C  |     C     |       I         |
| 配额申请与容量包络             |    I      |         **A/R**     |    C    |  I  |     I     |       I         |
| 区域允许清单                   |    C      |         **A**       |    C    |  C  |     C     |       I         |
| IAM 模型(云侧)                |    I      |         **A/R**     |    C    |  I  |     C     |       I         |
| IAM 模型(集群内 RBAC)         |    C      |         C           |    C    |  A  |     C     |       R         |
| 网络底座 / Shared VPC 变更    |    I      |         **A**       |    I    |  C  |     C     |       I         |

| BYOC 纳管授权(签字)            | **A**     |         C           |    I    |  I  |     I     |       R         |
| BYOC 移交契约签署              | **A**     |         R           |    C    |  C  |     C     |       **A**     |
| Break-glass 条款约定            |    C      |         **R**       |    I    |  C  |   **A**   |       C         |
| 服务等级 / SLO 数值            |    C      |         I           |    I    | **A**|     I     |       R         |
| 证据留存与鉴证报告             |    I      |         C           |    C    |  C  | **A**     |       R         |
| 云侧事故响应(配额/区域/配额耗尽) |   I      |         **A/R**     |    I    |  C  |     I     |       C         |
| 退役与资源清理                 |    C      |         **R**       |    C    |  C  |     I     |       **A**     |

> A = Accountable(最终负责) · R = Responsible(执行) · C = Consulted(需咨询) · I = Informed(需知会)

### 5.1 表里有三处值得你特别确认

| 行                        | 为什么值得看                                                      |
| ------------------------- | ----------------------------------------------------------------- |
| **BYOC 纳管授权(签字)**   | **App Owner 是 A,CaaS Owner 是 R** —— 业务方拍板,技术方执行。对吗?|
| **网络底座变更**          | **你是唯一 A** —— 因为爆炸半径超出集群,CaaS 不该有这个权限        |
| **Break-glass 条款**      | **你是 R,Cyber 是 A** —— 涉及安全例外,必须有安全签字              |

### 5.2 关于 SLO 那一行

RFC §3 非目标明确:

> 在各责任方验证之前,就先行确定云厂商产品选型、区域允许清单、服务等级或数值化的 SLO。

**所以 SLO 数值是 SRE 的 A,你只是 I。** 你不要越过这条线去承诺服务等级 ——
一旦你在能力目录里写了"可用性 99.9%",那就是一个你没有权力兑现的承诺。
