## §15 开放问题(替换 RFC 现有内容)

| ID  | 问题                                                                                     | 未解决时的影响                                                                                          | 建议责任人        |
| --- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------- |
| O1  | 完整云厂商能力目录的 schema 如何定义?                                                    | **§7 工作负载放置校验无法实现。** CaaS 只能先上线后补,业务方将收到基于不完整规则的拒绝                 | app.caep Compute / CTOi 云工程 |
| O2  | 允许使用的区域与可用区清单是什么?                                                        | 业务方申请被无理由拒绝;或置备到未批准区域,引发合规问题                                                   | CTOi 云工程      |

| O4  | **网络底座的 CaaS 权限边界?**                                                           | **爆炸半径超出单集群。** 变更共享 VPC 或 Cloud NAT 出口 IP 将导致不在 CaaS 管辖内的集群静默故障           | CTOi 云工程      |
| O5  | 云厂商权限与集群内 RBAC 是否需要两套独立的授权与审批流?                                   | 补权限需停机;安全审计无法区分两类不同爆炸半径的风险                                                     | CTOi 云工程 / Cyber |
| O6  | DC 现存"非生产与生产混用"的集群如何处理?                                                | 与 §9.1 硬要求冲突。要么承担拆分成本,要么形成永久性例外,削弱基线的强制力                             | CTOi 云工程 / 应用归属方 |
| O7  | **加速器的"隔离性"如何定义?GCP 仅提供配额隔离,无独占拓扑。**                             | **§7 AI 工作负载准入画像无法判定。** 若已有对外的"GPU 独占"承诺,该承诺无法兑现                       | CTOi 云工程      |
| O8  | 服务网格立场:Cloud Service Mesh、自建,还是不提供?                                       | §7 准入画像缺失该维度;业务方各自选型,CaaS 无法统一治理与排期                                            | CTOi 云工程      |
| O9  | BYOC 只读发现授权在纳管**中止**时如何自动撤销?                                           | 形成长期只读敞口。CaaS 保留一个其已不再负责的集群的访问权,无任何机制自动清理                          | CTOi 云工程 / app.caep Compute |
| O10 | 进入 `Suspended` 状态后,运维责任回归给谁、由谁承接?                                      | 集群停在半托管状态而无人负责,业务连续性风险;恢复时间不可预测                                             | app.caep Compute / app.caep SRE |
| O11 | 证据留存周期、审计系统集成方式与鉴证报告格式?                                            | §11.2 全部悬空。审计要求无法落到 CaaS 的证据包设计,上线后补做成本高                                    | Cyber / 安全架构 |
| O12 | 数值化 SLO 与服务等级由谁在何时确定?                                                     | RFC §3 已列为非目标,但下游所有容量与告警设计都依赖它。不确定则 CaaS 无法设计容量模型                    | app.caep SRE      |
| **N1** | **BYOC 是否需要"批量/分档"模式?**§9.2 目前只描述单集群八阶段。 | **DC 侧有数十个存量集群要纳管。** 若只有单集群流程,评估与授权工作量会随集群数线性增长,周期不可控        | app.caep Compute / CTOi 云工程 |
| **N2** | **BYOC 阶段 3(Assess)的检查项能否自动执行?**§9.2 已定四态(pass/fail/N/A/unknown)。 | **人工评估无法规模化。** 数十个集群靠人填表,纳管周期被评估工作量拖死;且四态应自动产出而非人工判断    | app.caep Compute  |
| **N3** | **是否明确"永不纳管"是正常结局?**§9.4 有 Not supportable,但清单是否要求记录这类集群? | 反复为永远不合格的集群做评估,报告变成永远清不掉的待办;DC 侧责任边界也随之模糊                   | app.caep Compute / 应用归属方 |
| **N4** | **CaaS 的容量模型是否覆盖对有状态服务的连接数预算?** | **几十个集群共享一个 Cloud SQL / Memorystore 实例时,连接数比 GKE 集群配额更早成为瓶颈;且失败表现为"性能下降"而非明确报错,更难归因** | app.caep Compute / CTOi 云工程 |
| **N5** | **网络底座按 VPC-region 级共享资源建模,还是按集群级?** | **DC 实证:proxy-only subnet 每 VPC 每 region 只能有 1 个 active。**若 CaaS 按集群建模网络,该模型根本不成立 | app.caep Compute / CTOi 云工程 |
| **N6** | **mTLS 类需求如何在能力目录中表达"边缘终止"这一事实?** | **GLB / ALB 均在边缘终止 mTLS,后端拿不到完整客户端证书。**客户常预期"端到端 mTLS",不提前说明会在交付期产生预期落差 | CTOi 云工程 / Cyber |
| **N7** | **CaaS 是否覆盖 Cloud Run 等 serverless 形态?**若不覆盖,其与 CaaS 共用的身份、密钥、网络底座由谁治理? | **DC 已有 Cloud Run 流水线投产**(证书签发,依赖 GCS + Secret Manager + WI)。**RFC 完全不提 Cloud Run,这些共用资源就没有归属方** | app.caep Compute / CTOi 云工程 |
| **N8** | **GCP 服务的"私有访问方式"是否应作为能力目录的一个独立维度?** | **GCP 官方把服务分两类**:Google 生产基础设施 API(BigQuery 走 **PGA**)vs VPC-hosted 服务(Cloud SQL/Redis 走 **PSC**)。笼统写"支持 PSC"会误导。跨云对应物:阿里云内网 endpoint、AWS VPC endpoint/PrivateLink | **CTOi 云工程** |
| **N9** | **存量集群的镜像引用规范(当前大量使用 `:latest`)是否作为 BYOC 硬门槛?** | 若设为硬门槛,**数十个存量集群会集体不合规,导致 BYOC 批量受阻**;若完全不设,新集群会继承该习惯 | app.caep Compute / Cyber |
| **N10** | **§7 的「AI 与 Agent 工作负载」是否指"跑在 CaaS 纳管集群上的 AI"?** | **DC 的 AI 走 Vertex AI 托管服务(trainer/predictor/pipeline 三 SA 体系已建),不占 CaaS 集群。**若不澄清,CaaS 会为一个 DC 不用的场景设计准入画像与放置校验 | **CTOi 云工程** |
| **N11** | **GPU 场景是否纳入 CaaS 范围?若纳入,存量集群如何处理?** | **DC 当前不提供 GPU 场景(主动范围决策)。**若将来纳入且要求存量合规,存量集群几乎全部无法满足"机型明确 + 密度合适 + 配额覆盖"三条件。**建议 GPU 不参与 BYOC** | app.caep Compute / **CTOi 云工程** |
| **N12** | **Vertex AI 等托管 AI 服务是否与 CaaS 共用身份/密钥/网络底座?谁治理?** | **DC 已有 Vertex AI 流水线投产。**CaaS 与 Vertex AI 共用 GCS / Secret Manager / Workload Identity / 网络底座,但 RFC 只描述 K8s 集群 → **这些共用资源无归属方** | app.caep Compute / **CTOi 云工程** |
| **N13** | **CaaS 是否要求纳管集群满足最低可观测性基线?**(审计日志开启 / 告警策略存在 / 日志量预算) | **DC 现有可观测性实践成熟(审计、告警、降噪、跨项目聚合俱全),但都是针对"自己管的集群"。**CaaS 接管几十个集群生命周期后,无人对账日志量异常与审计缺口 —— 成本失控和合规缺口都要等出事才发现。**纳管前多看两眼的成本极低** | **CTOi 云工程** + app.caep Compute |
| **N14** | **跨项目日志可见性如何授权?** `roles/logging.viewAccessor` 是否属于 CaaS 权限模型的职责边界? | **DC 已选 Log Scopes(逻辑聚合,成本低),但它完全依赖 IAM。**现有 `06` 边界文档只覆盖 compute 和 IAM,**日志可观测权没有归属方**。另:知识库明确"共享 View"≠"共享 Bucket",后者是数据泄漏面 | **CTOi 云工程** |
| **N15** | **`_Default Bucket` 保留期与每集群日志预算归谁管?** | **保留期默认 400 天**;**无 per-cluster 日志预算** → 成本失控点在日志侧。Log Scopes 不翻倍,但**写入量仍计费**,跨项目后账单归属需明确 | **CTOi 云工程** |

## 建议标记为「评审会当场决」的三条

| ID  | 为什么必须当场决                                                                 |
| --- | ------------------------------------------------------------------------------ |
| **O3** | 版本窗口是硬约束且不可谈判。不决,就可能让试点集群带着 EOL 风险进生产。           |
| **O4** | 边界不清会在第一次跨集群事故时爆发,而不是在评审会上。                           |
| **O7** | 若已有客户被承诺"GPU 独占",这是一个**已经生效的对外承诺**。CaaS 接不住就是失信。  |
