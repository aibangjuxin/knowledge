# 13 · 缺口盘点 —— 还有什么没考虑到的

> **这份文件的定位(与前 12 份不同)**
>
> `01`~`12` 讲的是"**该做什么**"。本文件讲的是"**还有什么没考虑到**"。
>
> 你要的不是项目管理,是**一张待评估清单** —— 评估可以交给团队、可以写脚本取数、
> 可以下周再说。**它不是 block。**
>
> **怎么用这份清单**:
> - 每一条都是**问题**,不是**任务**。你需要的是"知道有这回事",不是"今天做完"
> - `自评` = 你自己看一眼就有答案的
> - `取数` = 需要查数据/问团队的(可脚本化)
> - `设计决策` = 需要 CaaS 或安全架构师一起定的
>
> **我会标注每条的"如果不考虑会怎样"** —— 这是判断要不要投入的唯一标准。

## 1. Q 系列 · 交付物的第二层(最缺)

> **这是本次盘点最重要的发现。**
> 前面 12 份文档交付物,基本都停在"填什么"。
> 但评审会上真正会发生的事是:**填完之后,别人会追问第二层。**

### Q1 · 每条"不支持"都会招来"那怎么办"

你已经准备交两条 `❌`(GPU 独占拓扑、其它)。评审会上一定有人问:

> "那客户要独占怎么办?能不能给个替代方案?"

**如果你只有 `❌` 没有替代路径,这一问会让你卡住。**

**每个 `❌` 都要配一个替代方案**:

| 不可支持的诉求       | 替代路径                                                    | 代价             |
| -------------------- | ----------------------------------------------------------- | ---------------- |
| GPU 独占拓扑         | 配额隔离 + 专用节点池(taint/affinity)+ 资源上限             | 弱隔离,需讲清   |
| 物理隔离             | sole-tenant nodes(但**不支持 Autopilot**,且需提额)         | 成本高,容量受限 |
| 使用中加密 + 独占    | **⚠️ 互斥,无替代** —— 必须二选一                           | 无,只能取舍     |
| Autopilot 特权工作负载 | 切 Standard,或申请 `WorkloadAllowlist`(GKE 1.35+)        | 需走审批         |

> **我的建议**:给 `❌` 加一列 `alternative`,没有替代的写"无,需取舍"。
> **显式承认"有些东西给不了",比被发现给不了好得多。**

### Q2 · 证据会过期,而你说了它会

`08-sources.md` 写了查阅日期 + D2 规则(12 个月过期)。**但没回答:谁来做复核?**

**不指定 owner 的自动流程 = 不会发生。**

**要补的**:
- 谁每 6 个月跑一次复核?(按 `03` 的维度拆分给几个人)
- 复核发现结论变了,怎么通知 CaaS?(需要一个"能力目录版本变更"的通告机制)
- DC 侧能否直接改 CaaS 里的能力目录,还是必须走 PR?

### Q3 · "能力"和"容量"是两回事,但 RFC 混用了

RFC §8 是"能力目录",§10 有"容量与配额"。**但两者的评估节奏完全不同**:

- 能力:随 GCP 产品迭代变(GKE 1.35 加了 privileged allowlist)
- 容量:随 DC 业务增长变

**你可能只准备了能力目录,没准备容量包络。** 而容量恰恰是**最容易突然咬人**的
(业务涨上来才发现配额不够,而提额要等一周)。

### Q4 · 存量集群纳管后,"退役"谁来做?

12 号文件讲了怎么纳管,但**没讲纳管后怎么退**。RFC §6.3 契约项 4 要求退出计划。

**没人负责的退役是定时炸弹**:
- 集群没人用了但还在跑 → 成本持续
- 退役时数据处置没定义 → 合规问题
- 谁有权决定退役?→ 归属方还是 CaaS?

**要补的**:退役的触发条件(成本?闲置?版本?)、谁决定、谁执行、数据怎么处置。

### Q5 · 失败了怎么办?(RFC 几乎没写)

§10 说"置备失败必须保持可见",但**没说重试策略**:

- 一个批量纳管中,10 个集群失败 2 个 → **那 2 个是被跳过,还是整个批次回滚?**
- 失败到第几次算"这个集群不适合纳管"?
- 谁来看失败报告?多久看一次?

**这是规模化纳管最常见的运维难题,而 RFC 完全没覆盖。**

### Q6 · 合规证据:"通过"和"没测"在报告里长得一样

你的 WP-4 提到 Data Access 日志需显式开启。但更深一层:

> 一个控制项显示"通过",可能是**真的通过**,也可能是**根本没测**。
> 在证据包里这两种情况长得一模一样。

**要补的**:证据包里每条控制项要有"本次是否真的检测了"的状态。
**这直接关系到 RFC §11.2 的可审计性** —— 审计师会问"你怎么证明你检测过"。

### Q7 · 现有 9 份 CaaS 文档和这套 RFC 的关系没对齐

`CaaS/` 下已有 9 份探索文档(概念、GKE 落地、跨云、合规、FinOps、Day-2、Portal、自建、CAPI)。
它们是自己推演的设计,**没有对过 RFC**。

**风险**:你交的能力目录可能和 `gke-caas.md` 的设计**互相矛盾**
(比如 CRD 字段命名、Provider 枚举值)。

**要补的**:把 RFC 约束反向校验一遍已有的 9 份文档。**这个我可以做,如果你要。**

## 2. R 系列 · 规模上来后才塌的地方

> 你有几十个存量集群。这些是**单集群看不出来,10 个才暴露**的问题。

### R1 · 等保/合规的审计视角,不是"技术上有没有"

前面所有讨论都是"能力支持不支持"。但合规评估问的是不同的东西:

> "这个集群**能否被证明**符合某个框架?"

两者差距很大。比如:Policy Controller 能审计,但
- 审计结果有上限(超出只计数不列明细)
- 被 admission 拒绝的违规**不写日志**

**这意味着你的证据可能是不完整的。** 而审计师要看的是完整性。

### R2 · 配额是"共享池",几十个集群会互相挤

DC 的 GKE 配额是**项目级**的。几十个集群共用一个池:

```
现有: 45/50 个集群(每 zone)
新纳管 10 个 → 55 > 50 → 置备失败
```

**但更隐蔽的是 GPU 和 CPU 配额** —— 集群数没超,但某个 AI 工作负载把 GPU 用完了,
**所有其他集群的扩容都受影响**。

**要补的**:纳管前跑一次"全局配额占用 vs 各集群需求"的预测。

### R3 · etcd 6GB 限制:集群越大越危险

每个集群 etcd 硬限 6GB。集群小的时候无所谓,但**纳管多个大集群时**,
如果 CaaS 的策略/CRD 数量膨胀,可能撞到这个限制。

**这条几乎没人会提前想到,但撞上时是硬失败。**

### R4 · API 配额:批量发现/对账会打爆

CaaS 要持续对账几十个集群。每轮对账 = 大量 API read。

**GKE 的 API reads / writes 是项目级配额。** 几十个集群持续对账,
可能撞上 API 配额,表现为**随机失败**(看起来像 bug,其实是配额)。

**要补的**:评估 CaaS 的对账频率 × 集群数,是否会超 API 配额。

### R5 · 多个集群归入 fleet 后的副作用

rollout sequencing、Config Sync、Policy Controller 都依赖 **fleet(Anthos)**。

- 几十个集群进同一个 fleet → 成员关系管理
- fleet 级别的配置变更会**同时影响所有集群**
- **一个集群配错 fleet 配置,可能波及其它所有** —— 这就是你 D6 说的"共享底座"问题的 fleet 版本

**这是你 D6(网络底座不进 CaaS 权限)最可能的被突破点** —— fleet 变更可能绕过你的防火墙规则边界。

### R6 · 批量授权的权限爆炸

几十个集群,每个要授三类权限。**手工授权出错率随数量上升。**

而且:第 20 个集群授权时,没人会再看一遍 scope。
12 号文件 §3.3 提了,这里补充:**建议用 Terraform / gcloud 脚本批量授权,不要手工**。

## 3. T 系列 · RFC 里我上一轮漏掉的 4 条

前一版 TBD 审计(02 号文件)覆盖了 14 条。重扫一遍,发现 4 条漏网:

| #  | 位置       | 漏掉的内容                              | 归属        | 不填会怎样                        |
| --- | ---------- | --------------------------------------- | ----------- | --------------------------------- |
| **T15** | §6.1       | **RACI 表格本身**(原文只有一段话描述)  | 全员        | 上线前无法签字                    |
| **T16** | §7         | **工作负载画像的 schema 和归属**未定义  | Compute     | 放置校验无法实现                  |
| **T17** | §11.2      | **证据包的具体格式**未定义              | 安全 + Compute | 审计要求无法落地              |
| **T18** | §3         | **非目标里"服务等级"的边界**与 §12 冲突 | 作者        | 评审时会被质疑自相矛盾            |

> **T18 特别说明**:RFC §3 非目标写了"不在各责任方验证之前先行确定服务等级或 SLO",
> 但 §12 又说运维要定义服务内容。**这两处需要作者明确边界** ——
> 哪些是"定义服务"(可以),哪些是"承诺 SLO"(不可以)。
