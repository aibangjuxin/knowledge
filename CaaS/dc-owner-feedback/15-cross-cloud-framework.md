# 15 · 跨云框架 —— 从 GCP 专篇到多云能力契约

> **触发**(2026-09-29):你指出真正的问题不是"接入 GCP",而是
> **多个云平台都要按 RFC 的标准交付能力契约**。
>
> **本文件做什么**:把 `03-gcp-capability-profile.md` 里**可复用的部分**抽出来,
> 变成"填任何一朵云都照着做"的框架 + 问题集。
>
> **本文件不做什么**:不替其它云填值(那些由各自的 Cloud Engineer 填)。
> 它定义**该问什么、怎么记录答案**。

## 0. 为什么单云专篇不够

我上一轮把 `03` 写成了 GCP 文档 —— 那在"只服务 DC"的语境下没问题,
但**一旦变成多云,它的结构就暴露了一个缺陷**:

> **能力目录的价值不在于填对了 GCP,而在于它逼你问对问题。**

一份填满 GCP 的表格,换到阿里云就没法用了。但**一份"该问哪些问题"的框架,能直接复用。**

所以本文件分三层:

| 层         | 内容                                   | 复用度 | 位置          |
| ---------- | -------------------------------------- | ------ | ------------- |
| **层 1**   | 能力 schema(字段定义)                  | ⭐⭐⭐ 完全复用 | 本文 §1      |
| **层 2**   | 能力维度 + 提问集(该问什么)            | ⭐⭐⭐ 完全复用 | 本文 §2      |
| **层 3**   | 云厂商取值(填什么)                      | ⭐ 每云一份 | `03` / 各云专篇 |

## 1. 层 1 · 能力目录 schema(跨云统一)

**这份 schema 建议直接写进 RFC §8**,由 app.caep Compute 拥有,各云工程师填值。

```yaml
capabilityEntry:
  # ── 标识 ─────────────────────────────────────────
  id: "network.pod-cidr"              # 稳定点分 ID,放置校验按它匹配
  dimension: "networking"             # 归入 §2 的 20 个维度之一

  # ── 作用域(⭐ 跨云最关键的字段)───────────────────
  scope:
    # 模式/发行轨:gcp 的 standard|autopilot;eks 的 standard|auto-mode
    mode: ["standard"]
    # 区域:all | [region...] | per-region
    region_scope: all
    # 发行通道:⭐ 每云的"版本通道"各不相同(见 §3)
    release_track: ["stable"]

  # ── 状态(RFC §8 强制的四态,不可自定义)──────────
  status: "limited"                   # supported|limited|unsupported|not-assessed
  caveat: "具体约束是什么"
  blocking: true                      # true = 不满足则拒绝放置

  # ── 替代路径(⭐ 2026-09-29 新增)──────────────
  # 评审会必被追问"那怎么办"。没有替代的,写"无,需取舍"
  alternative: "配额隔离 + 专用节点池"
  alternative_cost: "弱隔离,须讲清差别"

  # ── 证据(⭐ 各云统一)─────────────────────────
  evidence:
    source: "https://docs..."
    assessed_at: "2026-09-29"
    freshness: "fresh"                # fresh<6mo | aging<12mo | stale
  owner: "ctoi"                       # 谁对这条负责
```

### 1.1 三个跨云通用的 schema 决定

| 决定                | 跨云理由                                                                 |
| ------------------- | ------------------------------------------------------------------------ |
| **必须有 `scope`**  | GCP 有 Standard/Autopilot,EKS 有 Standard/Auto Mode,阿里云有托管/自管。**每家都有模式轴** |
| **必须有 `alternative`** | 每朵云都有"给不了的东西"。**这是评审会必问题**                    |
| **必须有 `freshness`** | GCP/阿里云迭代快,EKS 相对慢。**但都需要,因为文档会变**               |

> **`scope` 为什么是跨云最关键的字段**:
> GKE Autopilot 禁 hostNetwork,EKS Auto Mode 也限制 DaemonSet —— **不同云的"同一种模式"限制不同**。
> 不带 scope 的能力目录,跨云比单云更危险:**因为它看起来能用,实际在另一个模式上不能用。**

## 2. 层 2 · 能力维度 + 提问集(20 维度)

**这一节是本文件最有价值的部分。** 每朵云都照着这张表问一遍。

| #  | 维度         | 该问的问题                                                       | 常见"答不上来"的情形            |
| - | ------------ | ---------------------------------------------------------------- | -------------------------------- |
| 1  | **模式**     | 有哪几种托管模式?各自限制是什么?                                 | 只填"支持",不写限制              |
| 2  | **版本窗口** | 标准支持多久?长支持怎么收费?**默认开还是需申请?**                 | ⛔ 见 §3.1,默认值可能很贵        |
| 3  | **升级强制** | 有没有"到 EOL 强制升级"?能否阻止?需不需要提前通知?              | 只说"会通知",没说能不能挡        |
| 3b | **升级回滚** | 升级失败能回滚吗?控制面/节点分别怎样?                            | 混为一谈                         |
| 4  | **身份**     | 工作负载身份怎么绑?绑定可改吗?跨项目要怎么办?                    | 漏掉"跨项目要单独授权"           |
| 5  | **节点层**   | 谁能选机型?升级策略谁定?节点池谁收敛?                           | ⛔ 见 §3.2,这是最常被漏的        |
| 6  | **网络**     | VPC-native?私有集群?出网?跨项目?多集群入口?                     | 忘了"多集群入口有硬依赖链"      |
| 7  | **存储**     | 块/文件/对象各支持什么?加密?                                     | 漏了 CMEK 不覆盖所有服务          |
| 8  | **机密计算** | 使用中加密?限制?和哪些特性互斥?                                 | 漏了"和独占节点互斥"            |
| 9  | **加速器**   | 支持哪些?配额怎么算?**有没有独占拓扑?**                        | 漏了"只有配额隔离"              |
| 10 | **配额**     | 集群数/资源/操作数的硬限制?怎么提额?多久?                        | 只写了可调整的,漏了硬限制        |
| 10b | **隐式配额** | 云厂商自己施加的、你控制不了的?                                  | ⛔ 见 §3.3,最容易漏              |
| 11 | **策略**     | 准入控制?漂移检测?能审计既有资源吗?                             | 只说"支持 OPA",不说什么版本     |
| 12 | **可观测**   | 日志/指标/追踪?采集 agent 受限吗?                                | 忘了一定形态下装不了采集器        |
| 13 | **成本**     | 计费模型?什么按小时?什么按用量?                                 | 用云厂商报价当真实成本            |
| 14 | **退役**     | 怎么删?不可逆吗?数据怎么处置?                                   | 完全没设计                       |
| 15 | **服务网格** | 有没有?和 CaaS 什么关系?                                        | "到时再说"                       |
| 16 | **多集群**   | 跨集群编排?灰度升级?依赖什么前置?                                | 漏了 fleet 之类的隐式前提        |
| 17 | **Backup**   | 托管备份?能恢复到别的区域/账号?实测过吗?                         | 把"有快照"当"能恢复"            |
| 18 | **维护窗口** | 升级是否受限?能排除到什么范围?                                    | 不区分"节点排除"vs"集群排除"     |
| 19 | **区域差异** | 哪些能力只在部分区域?                                            | 藏在 caveat 里,没单列            |
| 20 | **支持边界** | 厂商支持到什么程度?出问题找谁?SLA 覆盖什么?                       | 把"SLA 覆盖"和"支持"混为一谈    |

### 2.1 怎么用这张表

1. 拿这张表问**每朵云**的负责人
2. 答案填进 `03` 那种格式的表
3. **横向对比填完之后,§4 的共性/差异分析自动浮现**

> **这张表的价值不在于它列了 20 个维度,而在于它逼你问"有没有隐式的东西"。**
> 10b(隐式配额)和 5(节点层)是两次真实踩坑换来的 —— 如果没踩过,你根本想不到要问。

## 3. 层 3 · 跨云共性与差异(填值时的重点)

> **这一节是给你用来"审别人填的表"的。** 填表的人未必知道这些。

### 3.1 ⚠️ 版本支持:三朵云的默认值不一样(最重要的一条)

| 云       | 标准支持 | 长支持              | **长支持默认开?**         | 长支持定价              |
| -------- | -------- | ------------------- | ------------------------- | ------------------------ |
| **GKE**  | 14 月    | ~10 月(Extended)   | ❌ **需主动加入**         | 按集群加收                |
| **EKS**  | 14 月    | 12 月               | ⚛️ **是,默认 EXTENDED**  | **控制面约 6 倍单价**    |
| **AKS**  | ~12 月   | ~12 月(LTS)         | ❌ 需选 LTS + Premium 层   | Premium 层包含            |

> #### 🔴 EKS 这条必须让每个 AWS 侧负责人知道
>
> **EKS 的 cluster upgrade policy 默认是 `EXTENDED`。** 也就是说:
>
> - 版本一过标准支持,**账单自动进入 6 倍控制面单价**,不需要任何人点同意
> - EKS 1.33 已于 2026-07-29 结束标准支持 → 那一刻起所有 1.33 集群开始被 6 倍计费
> - 到扩展支持结束,**控制面被强制升级,且不提前通知具体时间**
> - **只有控制面升,节点不动** → 控制面和节点版本拉开
> - 而这个自动升级**不能回滚**
>
> **这一条如果没人发现,就是一笔静悄悄的、持续一整年的成本超支。**
> 建议直接写成一条 DC 侧的运维要求:**核查所有 AWS 集群的 `upgrade policy`,确认是否需要改为 STANDARD。**

> **三朵云的共同规律(值得写进 RFC)**:
> 1. 长支持**都要额外付费**
> 2. 长支持到期后**厂商会强制升级**
> 3. **默认值不同** —— GCP 要你主动加,AWS 默认就给你加了
>
> **这正是 D2(证据新鲜度)的另一个理由**:默认值会变,能力目录里的结论会过期。

### 3.2 ⚠️ 节点层:模式决定谁干活

**这是跨云最容易漏的一条,因为它取决于"选了哪种模式"而不是"哪家云"。**

| 模式选择         | 谁管节点                        | CaaS 要编排什么                         |
| ---------------- | ------------------------------- | --------------------------------------- |
| **托管全托管**   | 云厂商全管(GKE Autopilot / EKS Auto Mode) | 少很多                                |
| **托管半托管**   | ⛔ **DC 管节点**(GKE Standard / EKS 传统)  | **升级策略/autoscaler 边界/节点池收敛** |

> **DC 的现状是 GCP `Standard`**(2026-09-29 确认)→ **落在"半托管"那一行。**
> 同理,AWS 侧如果没用 Auto Mode,也在半托管行。

**半托管模式下 CaaS 必须编排的清单**(每朵云具体工具不同,责任相同):
节点升级策略、Cluster Autoscaler 边界、NAP 开关、**节点池数量收敛**、Pod 密度规划。

> **"节点池数量收敛"是那个没人主动做、半年后没人知道钱花哪了的洞。**

### 3.3 ⚠️ 隐式配额:云厂商替你设的、你看不见的

| 云       | 隐式配额                        | 后果                                    |
| -------- | ------------------------------- | --------------------------------------- |
| **GKE**  | `gke-resource-quotas`(<100 节点)| 业务方申请不到资源,**CaaS 查不到**      |
| **EKS**  | 集群/节点配额、**IP 地址耗尽**   | VPC CNI 模式下 IP 耗尽 → Pod 起不来      |
| **通用** | API 调用速率、并发操作数         | 批量操作时随机失败                       |

> **这类配额有一个共同特征:失败时看起来像 bug,不像配额。**
> 建议在 RFC 的能力目录里给它**单独一个维度**,而不是塞进"配额"里。

### 3.4 加速器:每家都缺"独占"

| 云     | 有没有 per-cluster GPU 独占                                 |
| ------ | ----------------------------------------------------------- |
| **GKE** | ❌ **只有 quota 隔离**                                       |
| **EKS** | 🔶 有 GPU 资源,但**跨集群/跨账号的独占保证需要额外设计**    |
| **通用**| 需要独占的合规客户 → 通常是"专属节点池 + 配额 + 合同约束"    |

> **§7 对 AI 工作负载要求"隔离性"。这一条在**所有云**上都不是"开箱即用"。
> CaaS 的准入画像应该把它建模为**需要业务方明确选择的隔离等级**,而不是一个 yes/no。

> #### 🆕 跨云规律 4:「支持 GPU」和「支持 AI 工作负载」是两件事(2026-09-29)
>
> **DC 的实证**:`vertex-ai/` 有 4 篇生产文档(trainer/predictor/pipeline 三 SA 已建),
> **但 GKE 侧完全没有 GPU 规划**。
>
> **也就是说:AI 在跑,但不跑在 K8s 集群上。**
>
> | 云     | 托管 AI 服务     | 自建集群 GPU | CaaS 纳管的 AI      |
> | ------ | ---------------- | ------------ | ------------------- |
| **DC**  | ✅ Vertex AI      | ⬜ 无规划     | **无**              |
> | 通用   | 各云都有          | 多数团队会建   | 取决于是否自建      |
>
> **推论:能力目录里"AI 工作负载"这一维,不能只填加速器能力。**
> **它必须先回答"AI 跑在哪里"** —— 托管服务还是纳管集群?
> 这个问题比"支不支持 GPU"更前置,也更常被跳过。
>
> **对应开放问题 N10。** 评估实例见 [`18-gpu-ai-assessment.md`](./18-gpu-ai-assessment.md)。

### 3.5 身份:三家的绑定粒度不同

| 云     | 机制            | 绑定粒度                        | 可改?    |
| ------ | --------------- | ------------------------------- | -------- |
| **GKE** | Workload Identity | KSA 注解 + GSA binding            | ✅ 可改(但节点层改动触发滚动升级) |
| **EKS** | IRSA / Pod Identity | SA ↔ IAM Role                  | ✅ 可改  |
| **AKS** | Workload Identity / OIDC | 依版本而异                    | ⚠️ 需查   |

**跨云共性**:**改"绑定"通常可以,改"节点如何取凭证"通常触发节点重启。**
→ 这个边界对三家都成立,建议作为 CaaS 三身份划分的通用实例。

## 4. 给多云 CaaS 的三条架构建议

基于上面这些,你有比"填好四张表"更有价值的东西要说:

### 建议 1 · schema 必须带 `scope`,因为每家都有"模式轴"

GCP 有 Standard/Autopilot,EKS 有传统/Auto Mode。
**压成一行会在跨云时产生"看起来能用实际不能用"的条目。** 这比单云时更危险。

### 建议 2 · "长支持默认值"应该成为能力目录的一等条目

三朵云的长支持机制**结构相似但默认值不同**,而默认值决定了成本。
建议 schema 里有 `long_term_support: {available, default_enabled, cost_model}`。

### 建议 3 · 隐式配额要单列维度

GKE 的 `gke-resource-quotas`、EKS 的 IP 耗尽、通用 API 限流 ——
**它们的共同点是"失败时不像配额"**。混在"配额"维度里会被忽略。

## 5. 你这次能给 RFC 的新增价值

> **因为 DC 要对接多云,你比只服务单一云的工程师多一个视角:横向对比。**

| 你能提的                                     | 别人提不了的原因                                  |
| -------------------------------------------- | ------------------------------------------------- |
| **"默认值会咬人"**(EKS extended 默认开)      | 只有横向对比过三家的人才会发现                     |
| **"节点层责任随模式变,不随云变"**            | 单云视角会以为是该云的特性,其实是模式的特性      |
| **"隐式配额是跨云通病,不是 GCP 特有"**        | 单云视角会当成个别 bug                            |
| **"长支持都有,但默认值不同"**                | 需要同时读过三家的版本策略文档                    |

> **这四条建议进 RFC §15 开放问题或 §14 决策记录。**
> 它们不依赖任何一朵云的具体实现,是对**多云 CaaS 契约本身**的观察 ——
> **这正是 RFC §1 说"云厂商之间的差异应作为能力与约束被显式记录"想要的东西。**

## 6. 接下来各云该怎么推进

| 云     | 现状           | 下一步                                                   |
| ------ | -------------- | -------------------------------------------------------- |
| **GCP** | ✅ DC 主导      | `03` 已填大半,补 `🔶` 项                               |
| **AWS** | ❓ 未知         | 用 §2 提问集问一遍 AWS 负责人                            |
| **Ali** | ❓ 未知         | 同上;特别注意**RRSA 1.22+**、**ASM 是否为事实标准**     |
| **IKP** | ⛔ **完全未知** | 见 `14-doc-conflict-review.md` C8 —— **先问清形态**     |

> **我建议的顺序**:
> 1. **先解决 IKP**(`14` C8)—— 它的形态未知,可能改变整个 Adapter 层设计
> 2. **然后用 §2 提问集同时启动 AWS / Ali 的采集** —— 两个团队并行
> 3. **GCP 作为样板先走完全流程**,给另外两家一个可参照的模板
>
> **第 3 条是关键**:`03` 填完之后,它就是另外两家填表的模板。
> **所以 GCP 这份的质量,决定了另外两份的成本。**
