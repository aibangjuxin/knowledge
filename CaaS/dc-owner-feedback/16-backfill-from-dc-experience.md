## 1. 最重要的发现:你的知识库证实了 D6,也暴露了它不够

### 1.1 证实:D6(网络底座不进 CaaS 权限)是对的,而且比我想的更严重

`gcp/psa-psc/` 有 **13 篇**文档,`network/psc-subnet/` 有 **9 篇**。
`psc-nat-vs-proxy-only-subnet.md` 里记录了这些**强依赖**:

| 规则                                                | 后果                     |
| --------------------------------------------------- | ------------------------ |
| Service Attachment 的 `nat-subnets` 与 `forwarding-rule` **必须在同一 VPC** | 不同 VPC → **创建直接失败** |
| proxy-only subnet **每 VPC 每 region 只能有 1 个 active** | 建第二个 → 失败          |
| proxy-only subnet **必须 ≥64 个 IP**(官方硬约束)     | 小了 → 失败              |
| PSC NAT subnet 每 SA 最多绑 10 个                    | 超了 → 失败              |

> **这些全是"改错一个参数,整个链路起不来"的强依赖。**
> 如果 CaaS 拿着网络变更权,一次错误调整就可能同时打断多个集群的入口。
> **D6 不是一个理论上的谨慎,是对你这套架构的准确描述。**

### 1.2 ⚠️ 但 D6 有一个盲区:proxy-only subnet 是**每 VPC 每 region 唯一的**

**这条比"共享 VPC 会互相影响"更具体、更危险**:

```
一个 VPC + 一个 region
  └── 只能有 1 个 active proxy-only subnet
        └── 所有 GKE Gateway / Internal ALB 都依赖它
```

**这意味着**:

- **它是 VPC/region 级的单点**,不是集群级
- 任何调整(改大小、换 region、删了重建)都影响**该 VPC 该 region 下的所有集群**
- **CaaS 如果按"每集群管自己的网络"来做,这个模型根本不成立**

> **建议写进 §8 / §14**:
> `网络底座(VPC / 子网 / PSC / proxy-only subnet)是 VPC-region 级共享资源,
> 其生命周期与配额归 CTOi 云工程,CaaS 只读。`
>
> **这一条的措辞比 D6 原来的"共享 VPC"更精确,而且是实证的。**
> 建议把 D6 升级为这个更具体的版本。

### 1.3 你的知识库里已经有的那份排查文档,应该被 CaaS 知道

`psc-nat-vs-proxy-only-subnet.md` 里引用了:

> 日常 firewall 排查请走 `cross-project/cross-project-firewall-netpol/references/
> firewall-by-instance-path.md` —— 那份按"**实例视角 + 流量物理路径**"组织,跟你实际决策顺序一致。

**这是一份已经存在的、按物理路径组织的网络排查方法论。**

> **它对 CaaS 的价值**:CaaS 的网络对账逻辑应该采用**同样的组织方式**
> (按流量物理路径,而非按资源类型),否则生成的报告没人看得懂。
>
> **这是一件你能贡献、别人不能的事** —— 你手里已经有这个方法论了。

### 2.2 🆕 一条我完全漏掉、但你实战里存在的限制

`mtls/https-glb-pass-client.md` 记录:

> HTTPS GLB (Google Load Balancer) **不会直接传递完整的客户端证书**到后端服务。
> 这是一个重要的技术限制。

**这条在多云 CaaS 里很关键** —— 客户常说"我要 mTLS 端到端",但 GCP 的 LB 会在边缘终止。

> **建议在能力目录里单列**:
> `mTLS 端到端:有限支持 —— GLB 终止 mTLS,后端拿不到完整客户端证书。需业务方接受。`
>
> **而且这条跨云也成立** —— AWS ALB 同样在边缘终止。**这是个典型的"看起来能做,实际做不到"条目。**

### 2.3 Secret Manager —— 有个 64KB 硬限制

`secret-manage/secret-manage-ssl.md` 记录了 Secret 的体积问题:

| 项                        | 事实                                                       |
| ------------------------- | ---------------------------------------------------------- |
| **Secret 单值上限**       | **64 KB**                                                  |
| SSL 证书链典型大小        | 1–10 KB,异常时可达 180 KB                                  |
| 超限后果                  | 无法存储 → 需要拆分多个 Secret + 应用侧组合               |

> **这条必须进能力目录。** 因为:
> - 证书链大小**因客户而异**,一个客户正常不代表另一个正常
> - **拆分方案需要 CaaS 知道**,否则客户会来问"为什么我的证书存不进去"
> - 这是一个典型的 `有限支持 + 需要 caveat` 条目

**建议**:`Secret Manager:支持,但单值 64KB 上限;大证书链需拆分为多 Secret + 运行时组合(需 CaaS 模板支持)`

### 2.4 Cloud SQL —— 真实瓶颈是连接数,不是 CPU

`sql/gcp-postgresql.md` 是知识库里最长的一篇之一,核心发现:

> **GKE Pod → Cloud SQL 的瓶颈不是 CPU,是连接数。**
> `max_connections` 有限制(实例规格决定,例如 1500);多个服务的连接池总和可能超过它。

| 症状                                 | 根因                                     | 解法                        |
| ------------------------------------ | ---------------------------------------- | --------------------------- |
| 数据库性能下降 / 拒绝连接            | `max_connections` 打满                    | 连接池 + 限制单用户连接数  |
| 大量 `idle` 连接占用槽位             | 连接池配置不当                            | 限制 idle 生命周期          |
| 事务堆积                             | 缺 `statement_timeout` / `idle_in_transaction_session_timeout` | 配超时                       |

> **⚠️ 这条对 CaaS 是一个尚未被任何文档覆盖的架构要求**:
>
> **集群数 × 每集群 Pod 数 × 连接池大小 → 决定 Cloud SQL 能否承受。**
>
> 几十个集群共享 Cloud SQL 时,连接数是**全局共享池** —— 和 GKE 集群配额一样,
> **一个业务方打满,所有业务方受影响**。
>
> **这和我在 `13` 号文件 R2 说的"GKE 共享配额池"是同一类问题,但对象是数据库。**
> 建议新增一条 RFC 反馈:**CaaS 的容量模型必须包含"对有状态服务的连接数预算"。**

### 2.5 Vertex AI BYOC —— 和 CaaS 的 BYOC 概念撞名了

`vertex-ai/` 有 `byoc-training.md` / `byoc-prediction.md` / `byoc-iam-cicd.md`。

> **⚠️ 命名冲突风险**:
> - **Vertex AI 的 BYOC** = Bring Your Own **Container**(自带训练/预测容器)
> - **CaaS 的 BYOC** = Bring Your Own **Cluster**(自带集群)
>
> **同一个缩写在同一个组织里指两件事,而且 Vertex AI 的那个还更常用。**
>
> **建议**:RFC §9 的 BYOC 全称首次出现时明确标注,
> 并考虑 CaaS 侧是否要换个缩写(比如 `BYOK` = Bring Your Own Kubernetes)。

## 4. 这些回填对 CaaS 的三条实质影响

### 4.1 CaaS 的网络对账必须按"流量物理路径"组织

你已经有一份 `firewall-by-instance-path.md` 是这么做的。
**CaaS 生成的网络合规报告如果按资源类型组织,运维看不动。**

→ 建议作为一条反馈:**CaaS 的网络发现/合规报告结构参照流量物理路径组织。**

### 4.2 proxy-only subnet 是 VPC-region 级单点,CaaS 不能按集群建模

这是本次回填最重要的结构性发现。

→ **建议写进 §8 能力目录 + §14 决策(D6 升级版)**:
`proxy-only subnet 与 PSC NAT subnet 属 VPC-region 级共享资源,CaaS 只读不可写。`

### 4.3 有状态服务的连接数预算,CaaS 目前的模型里没有

`13` R2 只讲了 GKE 集群配额。**Cloud SQL / Redis 的连接数是同一类问题,但没人提。**

→ **建议新增开放问题**:`CaaS 的容量模型是否覆盖对 Cloud SQL / Memorystore 的连接数预算?`
—— 因为几十个集群共享一个实例时,这是比 GKE 配额更早爆的瓶颈。

## 6. 关于"GCP 当模板"这件事,我的看法

你问 GCP 能不能走完全流程当模板。基于这次回填,我的判断是:

> **GCP 这份的"结构"已经可以当模板了(15 号文件的 schema + 20 维提问集),
> 但 GCP 这份的"填充"还不够 —— 因为它现在只有我推演的通用能力,
> 缺你实战里的那些具体约束。**

**这次回填就是往"填充"里加料。** 剩下的:

| 待办                     | 成本  | 谁做                     |
| ------------------------ | ----- | ------------------------ |
| Cloud SQL / Redis 连接预算 | 半天  | 你(我已给出分析框架)     |
| GAR / Buckets 使用约定   | 半天  | 你                       |
| Cloud Run 是否在 CaaS 范围 | 1 小时 | 你 + Compute              |
| AWS / 阿里云填表         | 各 1-2 天 | 各自的 Cloud Engineer    |

> **GCP 走完全流程后,它就是另外两家的模板 —— 这个判断成立。
> 但"完全"的标准不是填满,是"每一条都有出处或实证"。**
