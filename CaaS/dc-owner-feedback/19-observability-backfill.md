## 1. DC 实际在用什么(实证,非推测)

| 层                | 实际做法                                                      | 证据                                        |
| ----------------- | ------------------------------------------------------------- | ------------------------------------------- |
| **日志写入**      | GKE 容器 stdout/stderr → Cloud Logging                       | `logs/log-limition.md`                     |
| **配额/成本监控**| `logging.googleapis.com/log_entry_count`、`byte_count` 自定义指标 | `logs/log-limition.md` §1.1               |
| **告警**          | Cloud Monitoring 告警策略 + 通知渠道                          | `logs/log-limition.md` §2.1                |
| **审计追溯**      | **Cloud Audit Logs**(`cloudaudit.googleapis.com/activity`)    | `logs/filter-health.md`                    |
| **跨项目聚合**    | **Log Scopes(逻辑聚合)** 为推荐方案                          | `logs/cross-project-sharing-logs.md` §2    |
| **日志降噪**      | 排除健康检查日志、应用层日志级别、Pod 日志轮转               | `logs/log-limition.md` §2                  |
| **辅助分析**      | Fluentd(`logs/docs/Fluentd.md`)、Splunk 格式适配             | `logs/` 目录                               |

> **这是一个成熟的实践。** 不是"有没有可观测性"的问题,是"CaaS 接入后如何保持"的问题。

## 2. 一个必须写进能力目录的结论:Log Scopes vs Log Sinks

**这条不是实现细节,是架构选型,而且直接影响成本。** DC 知识库已经做了选型并给了理由:

| 维度        | **Log Scopes(已选)**           | Log Routing / Sinks(备选)          |
| ----------- | ------------------------------ | --------------------------------- |
| 实现原理    | **逻辑聚合**,基于 IAM 跨项目检索 | **物理导出**,日志从源流到目标       |
| **存储成本** | **低**(仅源项目计费,**不产生副本**) | **高**(源 + 目标**可能双份计费**) |
| 配置复杂度  | 简单                            | 中等(需配 Sink + 目标项目权限)     |
| 适用场景    | **跨项目排障、统一运维视图**    | 合规归档、长期留存、BigQuery 分析   |

> ### 🔴 对 CaaS 的直接含义
>
> **CaaS 纳管几十个集群后,统一观测几乎必然走 Log Scopes(否则日志成本翻倍)。**
> 而 Log Scopes **完全依赖 IAM**:
>
> ```
> Master 项目 Log View
>   ├── filter: resource.labels.project_id="TENANT_A"
>   └── 需要 IAM: roles/logging.viewAccessor
>         ↓
> 谁能看哪个 Tenant 的日志 = 纯 IAM 问题
> ```
>
> **所以 CaaS 的权限模型必须包含 `roles/logging.viewAccessor` 这一维。**
> 现有的边界/RACI 文档(`06`)只覆盖了 compute 和 IAM,**没有覆盖日志可观测权**。
>
> **→ 建议在能力目录新增一维:`cross_project_observability`(见 §5)**
>
> **并且注意**:知识库明确建议**不要共享整个 Bucket,只共享 Log View**(用 filter 隔离)。
> **"共享 Bucket"和"共享 View"是两种不同的权限模型** —— 前者给的是全部日志,后者给的是过滤后的视图。
> CaaS 选哪种,决定了它是否会成为数据泄漏面。

## 3. 审计日志:DC 已经在用,而且用法正确

`logs/filter-health.md` 记录的是一个非常成熟的排查动作:

```bash
# 定位"谁删了我的 Health Check"
resource.type="audited_resource"
logName="projects/[PROJECT]/logs/cloudaudit.googleapis.com%2Factivity"
protoPayload.methodName="compute.healthChecks.delete"
# → 看 principalEmail(谁)、authorizationInfo[0].granted(是否授权)
```

**关键字段:`protoPayload.authorizationInfo[0].granted`** —— 区分"尝试"和"成功"。

> **这对 CaaS 的移交契约(`05`)有直接价值:**
> **BYOC 移交期间的每一次资源变更,都应该能从审计日志反查到 principalEmail。**
>
> **→ 建议:BYOC 移交清单增加一列「审计可追溯性」** ——
> 验证方式不是"文档里写了",而是"能否用一条 Log Explorer 查询回答
> 『这个集群上周有哪些变更、谁做的』"。

### ⚠️ 一条与 `13` 号文件 R2 同源的风险

| 事项                | 现状                                    | 风险                                       |
| ------------------- | --------------------------------------- | ------------------------------------------ |
| **Audit Logs 默认状态** | Admin Activity 默认开;**Data Access 默认关** | **纳管后如果没人开 Data Access,访问记录就是空的** |

> **Data Access 日志关闭 = 有人读了数据但查不到。**
> 这与 `13` 号文件里 Policy Controller 的问题**是同一类**:
> **"合规证据看起来齐全,实际是默认关闭导致的缺口。"**
>
> **两条合并成一条 DC 侧建议:纳管准入时校验审计日志覆盖率。**

## 4. ⚠️ 最大的缺口:CaaS 纳管后的可观测性归属

**这是本节的核心发现,也是我建议 DC 主动向 RFC 提出的问题。**

### 4.1 现状

DC 今天的可观测性是**针对自己管理的集群**建立的。纳管后出现三个新问题:

| 问题                                    | 为什么现在不存在                                  |
| --------------------------------------- | ------------------------------------------------- |
| **对账谁做?** 几十个集群的日志量、告警、审计健康度 | 之前是"我自己的集群",默认都会看                  |
| **业务方能看多少?** 是本项目全量,还是过滤视图    | 之前是同一个项目,不存在跨项目隔离                 |
| **成本归到谁?** Log Scopes 不翻倍,但**写入量仍计费** | 之前一个项目一个账单                              |

### 4.2 为什么这属于 CaaS 的契约问题,不是运维杂事

RFC §8 说 CaaS 提供能力目录与约束。但:

> **CaaS 接管了一个集群的"生命周期",却不接管"可观测性"——
> 就会出现"集群状态是 Ready,但没人知道它健康不健康"的情况。**

**具体到三十几个集群的规模,这个缺口会表现为:**

- 某个集群日志量异常飙升 → 没人告警 → 账单月底爆炸
- 某个集群 Audit Logs 被人关了 → 没人发现 → 出事时查不到
- 业务方看不到自己集群的日志 → 排查时反过来说"CaaS 不透明"

### 4.3 建议 DC 提出的内容

> **新增开放问题 N13:**
> **`CaaS 是否要求纳管集群满足最低可观测性基线?(审计日志开启 / 告警策略存在 / 日志量预算)`
> `若要求,由谁检查?若不要求,CaaS 的健康状态定义是否包含可观测性维度?**

**注意措辞:这不是"要求业务方多做事",而是"纳管前先确认基线,避免事后归因不清"。**

## 5. 能力目录建议新增的维度

> **这是本次回填给 `03` 的具体产出。**

### 5.1 `cross_project_observability`(跨项目可观测性)

| 项                | 状态 | 说明                                                                    |
| ----------------- | ---- | ----------------------------------------------------------------------- |
| Log Scopes 聚合   | ✅   | **DC 已选此方案**;逻辑聚合,不产生副本,成本低                          |
| Log Views 隔离    | ✅   | **按 `project_id` filter 隔离,不共享整个 Bucket**                       |
| 跨项目查询权限    | 🔶   | 依赖 `roles/logging.viewAccessor`;**CaaS 权限模型需覆盖这一维**           |
| Log Sinks 导出    | 🔶   | 仅在需要**归档/BigQuery 分析**时用;**成本双份,不可默认启用**           |
| 共享整个 Log Bucket | ❌   | **不推荐** —— 等于给全部日志访问权,是数据泄漏面                        |

### 5.2 `log_cost_governance`(日志成本治理)

| 项                | 状态 | 说明                                                                 |
| ----------------- | ---- | -------------------------------------------------------------------- |
| 写入量指标        | ✅   | `log_entry_count` / `byte_count`,DC 已在用                             |
| 写入量告警        | ✅   | DC 已有告警策略模板                                                     |
| **每集群日志预算** | ⬜   | **缺口** —— 无 per-cluster 预算,只能看总量                            |
| 降噪(排除健康检查)| ✅   | 知识库已有 exclude 规则                                                |
| 保留期策略        | 🔶   | `_Default Bucket` 默认 400 天(需确认 DC 实际);Sinks 可单独设         |

> **`_Default Bucket` 的 400 天默认保留期值得单独提一句:**
> **这是 Cloud Logging 成本里最容易被忽略的一项** —— 保留越久,存储越贵。
> DC 若没改过,就是 400 天。CaaS 若替 DC 接管集群,是否有权改这个值?**建议明确归属。**

## 6. 跨云对照(复用 `15` 的框架)

| 云       | 日志服务            | 跨项目聚合方式              | 关键坑                                    |
| -------- | ------------------- | --------------------------- | ----------------------------------------- |
| **GCP**  | Cloud Logging       | **Log Scopes**(IAM 驱动)   | **Data Access 日志默认关闭**              |
| **AWS**  | CloudWatch          | **Cross-account observability**(带费用分配) | **每 10K 指标/时 收费**,不是免费 |
| **AKS**  | Azure Monitor       | **Azure Monitor Workspace** | Log Analytics **按 GB 摄入计费**          |

> **跨云规律 5:「跨项目可观测」在三家都是 IAM/计费双重问题,不是纯技术问题。**
> 共同陷阱:**免费额度用完就开始收费,而这件事通常在第一次账单才被发现。**
>
> 能力目录里这一维应该**同时记能力和成本**,否则 CaaS 会给业务方一个"能看"的承诺,
> 而账单在另一本账上增长。

## 7. 给 RFC 的开放问题(建议加进 §15)

| ID   | 问题                                                                                   | 未解决时的影响                                                          |
| ---- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **N13** | **`CaaS` 是否要求纳管集群满足最低可观测性基线?**(审计日志开启 / 告警策略存在 / 日志量预算) | **几十个集群纳管后无人对账**;成本异常和审计缺口都要等出事才发现        |
| **N14** | **跨项目日志可见性如何授权?** `roles/logging.viewAccessor` 是否属于 CaaS 权限模型的职责边界? | 现有 `06` 边界文档只覆盖 compute 和 IAM,**日志可观测权没有归属方**     |
| **N15** | **`_Default Bucket` 保留期与每集群日志预算归谁管?**                                              | 保留期默认 400 天;**无 per-cluster 预算** → 成本失控点在日志侧         |

---

## 8. 一句话总结

> **DC 的可观测性实践是成熟的(审计、告警、降噪、跨项目聚合都有),不需要 CaaS 重新建设。**
>
> **真正缺的不是能力,是归属:**
> **CaaS 接管了几十个集群的生命周期,但"谁来看这些集群的日志健康度"没有写进契约。**
>
> **建议只提 N13 这一个问题** —— 把"纳管准入是否校验可观测性基线"交给 RFC 讨论。
> **它的成本很低(纳管前多看两眼),但避免的是几十个集群规模的归因不清。**
