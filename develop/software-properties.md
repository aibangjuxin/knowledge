# 软件系统的关键性质 · 开发者应该主动考虑的那几十个"性质"

> **副标题**：功能告诉我们"要做什么"，**性质**告诉我们"做到什么程度、在什么条件下成立"。
> 幂等性、原子性只是其中两个；真正拉开系统质量差距的，是能不能把剩下那几十个性质
> **逐条想清楚、逐条给出证据**。
>
> **一句话结论**
> **好的开发者不是"把功能实现了"，而是"声明了系统具有哪些性质，并且为每个性质给出了可验证的证据"。**
> 本文档给出一份性质清单 + 每条性质的判据 + 反模式 + 自查表，
> 并把「Argo CD / GitOps 门禁」场景下的原子性与幂等性推演完整收进来。

## 0. TL;DR

### 0.1 五组性质全景

| 组 | 性质 | 一句话 |
|---|---|---|
| **正确性** | 幂等性 | 做一次和做 N 次，效果一样 |
| | 原子性 | 中间态对外不可见，要么全成要么全不成 |
| | 线性一致性 | 每个操作看起来在某一瞬间原子生效，且与真实时间顺序一致 |
| | 顺序性 / 单调性 | 不倒退：版本、状态、读到的数据只往前走 |
| | 最终一致性 | 允许暂时不一致，但**一定**会收敛 |
| | 隔离性 | 并发事务互不干扰，隔离级别决定可见性 |
| | 活性 / 安全性 | 坏事永不发生（Safety）；好事最终发生（Liveness） |
| | 确定性 | 同样输入 → 同样输出 |
| | 可重入 | 同一执行流重入不破坏状态 |
| **并发 / 分布式** | 竞态（TOCTOU） | 读到的和写到的不再是同一份世界 |
| | 幂等键 / 去重 | 用一个键把"重复"折叠成"一次" |
| | 投递语义 | 至少一次 / 至多一次 / effectively-once（exactly-once 是幻觉） |
| | 超时预算 | 每个调用都有 deadline，超时必然可发生 |
| | 重试与退避 | 失败重试要退避、要抖动、要防重试风暴 |
| | 熔断 / 限流 / 背压 / 舱壁 | 把过载挡在系统之外，而不是让它雪崩 |
| | Saga / 补偿 / Outbox | 没有全局事务时的等价手段 |
| | 多数派 / 共识 | R + W > N，才能读到自己写的 |
| **失败恢复** | fail-closed / fail-safe / fail-open | 出错时往哪边倒，是设计决定不是默认行为 |
| | 优雅降级 | 降级路径必须存在且被演练过 |
| | 崩溃恢复 / 对账 | 进程死了，重启后系统能自己回到正确状态 |
| | 持久性 / RTO / RPO | 崩溃后数据还在，丢多少、恢复多久 |
| **工程交付** | 可观测性 | 出了问题能不能从外部看出"发生了什么" |
| | 可调试性 / 可审计性 | 能不能定位到具体那一次、那一条 |
| | 可测试性 | 能不能在 CI 里把"最坏情况"复现出来 |
| | 可回滚 / 向前兼容 | 出事能退；升级不打断在途请求 |
| | 可演进性 | 改一个需求，不需要重写三个模块 |
| | 安全性 | 认证、授权、最小权限、机密性、完整性、不可否认 |
| | 性能 / 成本 | 延迟分位、吞吐、单位业务成本 |
| | 可扩展性 / 弹性 | 水平扩、扛热点、扛单点 |

### 0.2 12 问自查（每个设计评审问一遍）

```
1.  这个操作重复执行会怎样？        → 幂等吗？幂等键是什么？
2.  执行到一半崩了会怎样？          → 原子吗？有中间态吗？谁来收拾？
3.  两个请求同时到达会怎样？        → 竞态吗？靠 CAS / 唯一约束 / 锁？
4.  事件乱序或丢失会怎样？          → 结论依赖顺序吗？有重扫/对账兜底吗？
5.  下游超时/挂掉会怎样？           → deadline 多长？重试几次？会不会雪崩？
6.  判断失败时默认放行还是拦住？    → fail-closed 还是 fail-open？谁定的？
7.  状态怎么回到正确？              → 重启后能自愈吗？靠事件还是靠对账？
8.  出问题怎么查？                  → 哪个指标/日志/审计能定位到这一条？
9.  怎么证明它是对的？              → 测试矩阵覆盖了乱序/并发/崩溃/配额吗？
10. 怎么上线、怎么退？              → 可回滚吗？老版本还在跑吗？兼容吗？
11. 谁能读写它？                    → 最小权限？凭据在哪？审计留痕吗？
12. 它凭什么是快的/便宜的？          → 瓶颈在哪？成本随什么增长？
```

## 1. 为什么用"性质"这套语言

### 1.1 功能 vs 性质

| | 功能（Feature） | 性质（Property / Quality Attribute） |
|---|---|---|
| 描述 | "提供批量导入接口" | "重复导入同一份文件，结果与导入一次相同"（幂等性） |
| 判定 | 有/没有，做没做 | **程度**：做到什么程度、在什么条件下成立 |
| 验证 | 演示一次 | 需要**证据**：测试、指标、演练、论证 |
| 失效方式 | 功能缺失（看得见） | **悄悄退化**（幂等性没了你不会立刻知道） |

**关键差别**：功能的 bug 会报错；性质的退化通常是**静默的**。
一个 API 依然返回 200，但你悄悄给它加了"每次调用都发一封邮件"——功能没坏，幂等性没了。

### 1.2 性质是可证伪的

写下来的性质必须能回答："**怎么证明它成立？**"
如果一个性质没法被任何测试、指标或演练证伪，它就不是性质，是口号。

```go
// ❌ 不是性质："系统很健壮"
// ✅ 是性质："同一个 delivery ID 重复投递 5 次，只产生 1 条 check run"
// ✅ 是性质："判定失败时写入 action_required，绝不写 success"
// ✅ 是性质："同一 PR 的 check 名称唯一，重放不产生第二个同名 check"
```

### 1.3 性质与技术栈无关

幂等性在 Go、Java、K8s、Argo CD、GitHub App、数据库、消息队列里是**同一件事**；
但每个栈的实现手段不同（唯一约束 / 幂等键表 / `kubectl apply` / `X-GitHub-Delivery`）。
所以性质清单是**可复用的思考框架**，比"最佳实践列表"更耐用。

### 1.4 性质之间会互相冲突

见 [§6](#6-性质之间的冲突与取舍)——这是"性质思维"最值钱的部分：
**没有免费的性质，只有被显式选择过的取舍。**

## 2. 正确性类性质

### 2.1 幂等性 Idempotency ★

**定义**
> 执行一次与执行 N 次（N≥1），对系统的**可观测状态**和**对外副作用**的影响相同。

数学上：幂等元 `f` 满足 `f(f(x)) = f(x)`。

**三个容易混淆的东西**

| | 含义 | 例子 |
|---|---|---|
| **幂等性** | 重复执行无额外效果 | `PUT /order/123 {status: paid}` 重复调 N 次，订单只被付一次 |
| **去重 Dedup** | 识别出"这是同一个请求"并跳过 | 用 `Idempotency-Key` 查到已处理过 → 直接返回上次结果 |
| **幂等律** | 代数意义的幂等（集合并、max） | `max(x, y) = max(y, x)` |

> **幂等 ≠ 去重**：幂等是"系统能承受重复"，去重是"系统能识别重复"。
> 最好的实现里两者同时存在：靠**幂等键**识别重复，靠**幂等设计**保证重复无害。

**为什么重要**

- 重试是分布式系统的**必需品**，而重试必然产生重复 → 没有幂等就不能安全重试
- 消息队列是**至少一次**投递，天生会有重复
- 用户双击按钮、网络超时后客户端重发、自动化脚本被反复跑
- GitOps 声明式 apply 本质就是"把期望状态反复应用"，**天然要求幂等**

**幂等键怎么选（三层键，通用范式）**

| 层 | 键 | 作用 | 例子 |
|---|---|---|---|
| **L1 传输层** | 事件/请求的唯一投递 ID | 挡"同一事件重复到达" | `X-GitHub-Delivery` / `message_id` / 请求 UUID |
| **L2 业务层** | 目标实体的业务唯一键 | 挡"同一目标被重复处理" | `(repo, check_name, head_sha)` / `(order_id)` |
| **L3 版本层** | 内容的版本指纹 | 让"内容变了"能被区分 | `policy_version`（blob SHA）/ `resourceVersion` |

**实现要点**

```go
// ✅ 单次原子写占位，不要"先查后写"（那是 TOCTOU）
res, err := db.Exec(`
  INSERT INTO processed(delivery_id, result, created_at)
  VALUES ($1, $2, now())
  ON CONFLICT (delivery_id) DO NOTHING
  RETURNING id`, deliveryID, result)
// res.RowsAffected() == 0 → 说明处理过了 → 走"返回上次结果"分支
```

```sql
-- ✅ 业务键唯一约束：数据库替你解决并发问题
CREATE TABLE check_runs (
  repo_id     text NOT NULL,
  check_name  text NOT NULL,
  head_sha    text NOT NULL,
  conclusion  text NOT NULL,
  PRIMARY KEY (repo_id, check_name, head_sha)   -- 并发写入天然收敛
);
```

**幂等键的语义约定（必须写进文档）**

| 情况 | 行为 |
|---|---|
| 同键 + 同载荷 | 返回**第一次**的结果，不重复执行副作用 |
| 同键 + **不同**载荷 | 报**冲突**（409），不能静默覆盖 —— 否则等于丢了幂等性 |
| 占位写入后进程崩溃 | 占位要有**短 TTL**；完成标记要**长 TTL**；否则坑永久占死 |
| 副作用（发通知 / 打标签） | 幂等键只能挡住"处理"，挡不住"副作用" → 副作用也要幂等（先查重 / 用状态位） |

**HTTP 语义对照**

| 方法 | 幂等 | 说明 |
|---|---|---|
| GET / HEAD | ✅ | 只读 |
| PUT | ✅ | 覆盖式写入，重复 PUT 等价 |
| DELETE | ✅ | 删第二次应当仍返回成功（幂等语义） |
| PATCH | ⚠️ | 视补丁内容，追加型补丁不幂等 |
| POST | ❌ | 天然不幂等 → 用 `Idempotency-Key` 头补 |

**反模式**

```
❌ 累加型写入：UPDATE t SET n = n + 1     → 重复执行会多加
❌ 生成随机 ID 写入：每次调用生成新 ID      → 产生两个"不同"的实体，业务上等于没幂等
❌ 先删后建：DELETE old; INSERT new       → 中途崩溃 → 数据没了
❌ 只在应用层判重，不加唯一约束          → 并发下两个请求同时通过判重
❌ 用"读到的版本"当幂等键                → 读一次写一次之间内容变了
```

**判据 / 怎么证明**

- 重放测试：同一 delivery ID 打 5 次 → 副作用只发生 1 次
- 并发测试：N 个相同 key 并发 → 数据库里只有 1 行，且只 1 个副作用
- 崩溃注入：写完占位就 kill → 重启后能补完或安全重做（**不能既不重做又不算完**）

### 2.2 原子性 Atomicity ★

**定义**
> 一个操作要么完整生效，要么完全不生效；**中间状态对外不可见**。

ACID 里的 A。要注意区分两种"原子性"：

| | 存储原子性 | 业务原子性 |
|---|---|---|
| 含义 | 写入不会"写一半" | 一个业务动作不会"做一半" |
| 保证者 | 文件系统 / 数据库 / 消息队列 | 你的设计（状态机 + 幂等 + 补偿） |
| 例 | `write tmp; fsync; rename` | "转账"要么两边都动，要么都不动 |

**为什么重要**

- 用户看到半成品 = 信任崩塌（"订单显示已支付但没发货"）
- 半成品状态会**污染后续所有判定**（这是幂等性被破坏的常见上游）
- 分布式系统里**没有全局原子性**，只能本地原子 + 全局最终等价

**常见实现手段**

| 场景 | 手段 |
|---|---|
| 写文件 | 临时文件 + `fsync` + `rename`（同一文件系统内 rename 原子） |
| 数据库 | 事务（单库 / XA / 两阶段提交） |
| 跨服务 | Saga + 补偿；Outbox（副作用原子化） |
| K8s | `kubectl apply` 是"声明式收敛"，近似原子但**不是**（见 §10.1） |
| 状态流转 | 单调状态机 + 只允许合法迁移（非法迁移直接拒绝，而不是"改回去"） |

**判据**

```
□ 任一时刻从外部观察，只能看到 all-or-nothing 的结果
□ 在任意一步崩溃，重启后要么是完整状态，要么是完整旧状态
□ 没有"部分成功但对外说成功"的状态
```

**反模式**

```
❌ 先发消息再写库（写库失败 → 消息已发 → 重复消费）
❌ 先扣款再发货
❌ 先删后建（非原子，且丢了旧数据）
❌ "失败就手工回滚"（没有补偿路径的伪原子）
```

### 2.3 线性一致性与一致性光谱

**线性一致性 Linearizability**：每个操作看起来在某个瞬间原子地生效，且这个顺序与真实时间顺序一致。
它要求"单一权威副本 + 共识"，代价最高。

真实系统大多达不到线性一致，但可以达到**弱一些但够用**的性质：

| 性质 | 保证 | 典型实现 |
|---|---|---|
| **线性一致性** | 全局实时序 | 单主 + Raft/共识 |
| **顺序一致性 Sequential** | 所有进程看到相同顺序（但不一定是真实时间序） | 共享内存锁 |
| **因果一致性 Causal** | 有因果关系的操作顺序一致 | 版本向量 / 混合逻辑时钟 |
| **读己之写 RYW** | 写完立刻能读到自己的写 | 会话级粘滞 / 版本戳 |
| **单调读 Monotonic Reads** | 读到的版本不倒退 | 会话缓存版本戳 |
| **单调写 Monotonic Writes** | 写按序生效 | 单写者 / FIFO 队列 |

**实践建议**：**先明确你需要哪一级**，而不是默认"数据库很强"。
门禁类系统通常只需要：*读己之写 + 单调读 + 结论单调收敛*。

**隔离级别（并发事务）**

| 级别 | 脏读 | 不可重复读 | 幻读 | 写偏斜 |
|---|---|---|---|---|
| Read Uncommitted | 可能 | 可能 | 可能 | 可能 |
| Read Committed | ✗ | 可能 | 可能 | 可能 |
| Repeatable Read | ✗ | ✗ | 可能（DB 各异） | 可能 |
| Serializable / Snapshot | ✗ | ✗ | ✗ | ✗ |

> **写偏斜（write skew）** 是最容易被忽略的一种：两个事务各读同一份快照、各自判断"没有别人做"，然后各写各的 → 违反了业务不变量。
> 例子：两个值班人同时看到"还有 1 个可用名额"，都认领 → 超卖。
> 对策：唯一约束 / `SELECT ... FOR UPDATE` / 把不变量做成数据库约束 / 用悲观锁或原子条件更新。

### 2.4 顺序性与单调性 Monotonicity

**定义**：系统的状态、版本、观测值**只朝一个方向走**，不倒退。

- 版本号单调递增（`policy_version`、`resourceVersion`、`head_sha` 序列）
- 状态机单调：`in_progress → completed`，不回到 `in_progress`
- 结论单调收敛：同一目标的新判定只会覆盖旧的，不会"复活"旧结论
- 时间相关判定必须用**单调时钟/版本**，而不是本地墙上时间（见 §2.8 确定性）

**为什么重要**：一旦允许倒退，"最终一致"就会变成"来回抖动"，
客户端看到 check 先红后绿再红，无法判断哪个是最终结论。

---

### 2.5 最终一致性与收敛 Convergence

**定义**：允许系统在一段时间内不一致，但保证**最终会收敛到唯一正确状态**。

> **一致性光谱**
> 强一致 ← 线性一致 → 顺序一致 → 因果一致 → 会话保证 → 最终一致 → 无保证
> 越右越便宜、越快，但"读到旧值"的窗口越大。

**收敛的三要素（GitOps 的核心公式）**

```
期望状态（Desired）  ──对比──▶  观测状态（Observed）
       ▲                          │
       └────── 应用/校正 ◀─────────┘
```

一个真正收敛的系统必须具备：

1. **期望状态是声明式的**（不是一串命令）
2. **比较是幂等的**（重复 apply 结果相同）
3. **收敛循环是持续跑的**（事件触发 + 定期重扫双保险）
4. **差异是安全的**（把 A 改成 B 不会先删掉 B 再建 A）

**判据**

```
□ 断开上游事件源，系统靠重扫仍能收敛吗？
□ 收敛到的是"正确状态"还是"最近一次写入的状态"？
□ 收敛过程本身幂等吗？
□ 收敛失败会重试还是卡死？能被观测到吗？
```

---

### 2.6 隔离性与 ACID

| | 保证 | 反例 |
|---|---|---|
| **原子性 A** | 全有全无 | 见 §2.2 |
| **一致性 C** | 事务前后都满足业务不变量 | 应用层校验漏了一条约束 |
| **隔离性 I** | 并发事务互不干扰 | 写偏斜、幻读 |
| **持久性 D** | 提交后崩溃不丢 | 提交只写了内存 / 只写了 page cache |

> **C 不是数据库替你保证的**：数据库只保证事务前后数据满足**声明的约束**（唯一键、外键、check）。
> "一个 PR 只能有一个有效结论"这种业务不变量，必须自己表达成数据库约束或状态机规则。

---

### 2.7 活性与安全性（Liveness / Safety）

形式化方法里的两个基本性质，几乎可以覆盖所有线上事故类型：

| | 形式 | 线上表现 | 对策 |
|---|---|---|---|
| **安全性 Safety** | 坏事**永不**发生 | 数据错乱、重复扣款、越权、门禁被绕过 | 约束、类型、状态机、幂等、fail-closed |
| **活性 Liveness** | 好事**最终**发生 | 任务卡住、永远 pending、check 不落终态 | 超时、重试、进度保证、重扫、接管 |

**例**：一个 check 永远停在 `in_progress`——
从 Safety 看无害（还没判通过，fail-closed 挡住了合并），但从 Liveness 看是**坏掉了**：
用户被永久阻塞。所以两者都要管。

**活性三件套**

```
□ 超时（这次尝试不会永远挂着）
□ 进度保证（系统整体在往前走，不会饿死某些请求）
□ 失败检测与接管（卡住的东西能被别的实例接手）
```

**形式化工具**：TLA+ / PlusCal（建模 + 模型检查）、Alloy、SPIN、Petri 网。
不一定在日常用，但"**用模型检查找 liveness bug**"在状态机密集的系统（订单、门禁、调度）里性价比极高。

---

### 2.8 确定性与可复现 Determinism / Reproducibility

**定义**：相同输入 → 相同输出；同样的故障 → 同样的现象。

**为什么重要**
- 可复现的 bug 才能定位
- 幂等的批量导入 = **顺序无关**（无论以什么顺序、什么批次到达，结果一样）
- 可复现构建 = 供应链可验证

**常见的非确定性来源**

| 来源 | 破法 |
|---|---|
| 读系统时钟 | **把 `now` 作为参数注入**（`func(now time.Time)`），不读系统时钟 |
| 随机数 | 注入随机源（seed 可控） |
| Map 遍历顺序 | 排序后再遍历；或用有序结构 |
| 并发交错 | 用可控的调度点；单测里串行化 |
| 依赖外部时间/时区 | 固定 IANA 时区 + 固定时间戳；DST 场景显式测 |
| 依赖外部服务返回值 | 录放（record/replay）、契约测试固定样本 |

**判据**

```
□ 同一个输入重跑 100 次，输出完全一致（except 显式声明的字段）
□ 时间、随机数、网络都是可注入的依赖
□ 批量导入 10 万条，分 3 个批次、乱序到达 → 结果与一次性导入一致
```

---

### 2.9 可重入 Reentrancy / 可重试 Retryable / 线程安全

三个常被混为一谈：

| 概念 | 问题 | 对策 |
|---|---|---|
| **可重入** | 同一执行流**重入**同一函数会不会破坏状态 | 局部变量、不可变状态；把共享状态参数化 |
| **可重试** | 失败后**再调一次**会不会更糟 | 可重试的错误类型 + 退避 + 幂等兜底 |
| **线程安全** | 多线程并发访问会不会竞态 | 同步原语、无共享状态、原子操作 |

> **可重试 ≠ 幂等**：一个不幂等的操作也可以重试（只要你接受"可能重复"）；
> 一个幂等的操作不一定可重试（可能代价太高）。
> 实践中：**凡是你打算自动重试的，先确认幂等**。

## 3. 并发与分布式类性质

### 3.1 竞态与 TOCTOU（Time-Of-Check to Time-Of-Use）

**定义**：检查条件和使用结果之间，状态已经变了。

```go
// ❌ TOCTOU：两个请求都能通过判重
if _, err := store.Get(key); err == nil {
    return nil // 已被处理
}
if err := store.Do(work); err != nil { ... }

// ✅ 交给数据库/缓存的原子原语
ok, err := store.SetNX(key, result, ttl)   // 只有一个赢家
```

**消除 TOCTOU 的四种手段（按优先级）**

1. **唯一约束 / 主键冲突**（数据库替你解决，最可靠）
2. **原子原语**：`SETNX`、`INSERT ... ON CONFLICT DO NOTHING`、CAS
3. **乐观锁 + 版本号**（读版本 → 写时校验版本，失败则重试）
4. **悲观锁 / 串行化队列**（代价最高，但语义最简单）

---

### 3.2 乐观并发：CAS、版本号、唯一约束

| 机制 | 适用 | 代价 |
|---|---|---|
| **CAS / compare-and-swap** | 单个值的高频更新 | 失败要重试 |
| **版本号（乐观锁）** | 整行/整对象更新 | 需要携带版本号 |
| **唯一约束** | "只能有一个"的业务不变量 | 冲突要转成可处理的错误 |
| **`UPDATE ... WHERE version = ?`** | 状态机流转 | 同上 |

**要点**：乐观锁不是"没有锁"，是把冲突**推迟到写的时候**检测，且必须有明确的失败分支（重试 / 报错 / 走别的路径）。

---

### 3.3 锁、租约与 fencing token

| | 语义 | 失效模式 |
|---|---|---|
| **互斥锁** | 同一时刻只有一个持有者 | 死锁、持有者崩溃 → 死锁 |
| **租约 Lease** | 有 TTL 的锁，过期自动释放 | **时钟漂移**导致提前释放 |
| **fencing token** | 每次持锁发一个单调递增号，存储侧拒绝旧号 | 需要存储侧配合校验 |

> **分布式环境不要依赖本地墙上时间做租约判断**——节点时钟不同步，租约可能提前过期，
> 于是两个持有者同时写。要么用中心化租约服务，要么用 **fencing token**，
> 要么干脆**避免用锁**（改成幂等 + 单调收敛）。

**死锁避免**：全局固定加锁顺序；单次拿锁带超时；不用嵌套锁；锁粒度尽量粗。

---

### 3.4 投递语义 Delivery Semantics

| 语义 | 保证 | 现实 |
|---|---|---|
| **至多一次 At-most-once** | 可能丢，绝不重 | 丢事件 = 门禁失效 |
| **至少一次 At-least-once** | 绝不丢，可能重 | **最常见**（消息队列、Webhook） |
| **恰好一次 Exactly-once** | 不丢不重 | **端到端做不到**（网络 + 非事务副作用） |
| **Effectively-once** | 效果上恰好一次 | **现实最优解**：靠幂等 + 业务键收敛 |

**"恰好一次是幻觉"的原因**：网络会超时、副作用可能发生在事务之外。
分布式事务最多保证**一次原子提交**，无法保证**跨系统的恰好一次效果**。

**实践路线**

```
接受重复 → 用幂等键识别 → 用业务唯一键收敛 → 用副作用幂等补齐最后一块
```

---

### 3.5 乱序、缺失与重复

| 现象 | 成因 | 对策 |
|---|---|---|
| **乱序** | 并发发送 / 多分区 / 重试回退 | 结论**不依赖顺序**（幂等 + 单调）；带版本号比较后再写 |
| **缺失** | 丢包 / 投递失败不重试 / 过期 | 定期**重扫**对账；拉取式兜底；健康检查 |
| **重复** | 至少一次投递 | 幂等（见 §2.1） |
| **延迟** | 队列积压 / 下游慢 | 超时预算 + 背压；先 ACK 再异步 |

**关键设计原则**：**让结论与事件顺序无关**。
如果结论依赖顺序，就必须在消费端维护顺序（代价高且难保证），更好的做法是：
收到事件后**重新读取当前状态**（拉模型）再判定，而不是**用事件里的快照**判定。

> 这一条在 §10 会再次出现，它是 §10.5 的核心技巧：
> **判定输入 = 当前快照（重新 GET），不是事件 payload。**

---

### 3.6 超时预算 Timeout Budget

**定义**：每个跨边界调用都有 deadline；**超时是必然事件，不是异常**。

**规则**

```
□ 所有出站调用必须设超时（没有"默认无限等"）
□ 超时值有依据：上游 SLA × 剩余预算，而不是"给个 30s 拍脑袋"
□ 有剩余预算时向下游传递（deadline propagation）
□ 超时错误要能区分于业务错误（否则会触发错误的重试）
□ 重试的总耗时必须在原始 deadline 内（不能"重试 3 次 × 30s"超过预算）
```

**常见坑**：网关 10s 超时 → 你的服务 30s 超时 → 用户已经收到 504，
你的服务还在傻等并可能事后写入成功状态 → **调用方看到失败，副作用却生效**（非幂等的危险组合）。

---

### 3.7 重试、退避与重试风暴

**要素**

| 要素 | 为什么 |
|---|---|
| **指数退避** | 避免持续压力 |
| **抖动 Jitter** | **避免惊群**（否则所有客户端同时重试 = 自己制造风暴） |
| **重试预算 / 比例** | 只让一部分请求重试（Google SRE 的"重试预算"） |
| **可重试错误白名单** | 5xx/超时可重试；4xx 业务错误重试无意义 |
| **最大次数 + 总时长上限** | 有界 |
| **幂等兜底** | 重试的前提 |

**重试风暴（Retry Storm）**：下游抖动 → 上游全部重试 → 下游更抖 → 雪崩。
**缓解**：抖动 + 预算 + 熔断 + 舱壁 + 队列削峰。

---

### 3.8 熔断、限流、背压、舱壁

| 性质 | 解决什么 | 典型实现 |
|---|---|---|
| **限流 Rate Limit** | 单位时间请求数上限 | 令牌桶 / 漏桶 / 配额 |
| **并发限制 Concurrency Limit** | 同时在途请求数上限 | Semaphore / worker pool |
| **熔断 Circuit Breaker** | 下游持续失败时快速失败 | closed → open → half-open |
| **背压 Backpressure** | 下游慢时让上游感知并减速 | 有界队列 + 阻塞 / 拒绝 |
| **舱壁 Bulkhead** | 一个依赖故障不拖垮整体 | 独立线程池/连接池/配额分区 |
| **负载卸载 Load Shedding** | 过载时主动拒绝低优先级请求 | 优先级 + 拒绝策略 |

> **有界一切**：队列必须有界。无界队列 = 把"过载"翻译成"内存溢出 + 延迟无限增长"。

---

### 3.9 分布式事务：Saga、补偿、Outbox

| | 解决 | 代价 |
|---|---|---|
| **2PC / XA** | 真正的跨资源原子 | 阻塞、吞吐低、协调者是 SPOF |
| **TCC** | 资源预留式 | 每方都要实现 try/confirm/cancel |
| **Saga** | 每步本地事务 + 失败时**补偿** | 补偿必须幂等；中间态对外可见 |
| **Outbox** | **副作用原子化**：业务数据和"要发的事件"同一事务落库，后台再投递 | 延迟；投递器本身要幂等 |

**Outbox 模式（最常用的一招）**

```
事务内:  UPDATE order SET status='paid';
         INSERT INTO outbox(event_type, payload, created_at) VALUES (...);
提交后:  投递器轮询 outbox → 发 MQ → 标记已发（失败可重试）
```

它把"改数据"和"发消息"从**两个不可控的系统**变成**一个本地事务 + 一个可重试的投递器**。

**补偿 = 逆向业务动作**，且必须幂等（补偿也可能被执行多次）。

---

### 3.10 多数派与共识

| 概念 | 要点 |
|---|---|
| **Quorum** | 读 R、写 W、N 个副本，需 `R + W > N` 才能保证读到最新写 |
| **CAP** | 一致性 / 可用性 / 分区容错**不可兼得**（分区必然发生，所以是 CP 还是 AP 的选择） |
| **PACELC** | CAP 只说分区时；**E（否则）**下还要在延迟与一致性间选 |
| **Split Brain** | 网络分区导致两个"领导者" → 用多数派/租约/fencing token 防止双写 |
| **时钟假设** | 分布式里不要用墙上时间做唯一判据；用版本号/逻辑时钟/单调时钟 |

**共识不是免费的**：如果你只需要"幂等地写一个状态"，唯一约束就够了，不需要 Raft。

## 4. 失败与恢复类性质

### 4.1 fail-closed / fail-safe / fail-open

**失败时往哪边倒，是设计决定，不是默认行为。**

| 姿态 | 含义 | 例子 |
|---|---|---|
| **fail-closed** | 判定不了就**拦住** | 门禁 check 写不出结论 → 不允许合并；合规校验失败 → 拒绝 |
| **fail-open** | 判定不了就**放行** | 推荐系统的降级推荐；只读看板 |
| **fail-safe** | 失败时不造成额外损害（最小爆炸半径） | 写操作失败不产生半成品；限流而不是崩溃 |
| **fail-fast** | 立刻报错，不重试 | 参数非法、编程错误 |

> **危险默认值**：判定失败时写 `success`（fail-open）—— 这是门禁类系统最致命的写法。
> 对应到实现：**只允许显式写 `success`，任何异常路径都落到 `action_required` / `failure`**。

**判据**：把所有异常路径列出来，逐条问"这条路上我写了什么结论？"。

---

### 4.2 优雅降级 Degradation

**层次**（从好到差）：

```
完整功能 → 部分功能 → 缓存/近似结果 → 只读 → 明确报错 → 限流/排队
```

**要点**：降级路径必须**存在且被演练过**；降级状态必须**对外可见**（否则用户以为拿到的是真结果）；
降级不能破坏幂等性（"降级期间不写结论"比"降级期间写个假结论"安全）。

---

### 4.3 崩溃恢复与对账 Reconciliation

**定义**：进程/节点死亡后，系统能**自动**回到正确状态，不需要人工介入。

**两条恢复路径，通常都要有**

| 路径 | 机制 | 特点 |
|---|---|---|
| **事件驱动** | 队列重投 / webhook 重投 | 快，但可能丢 |
| **对账驱动（reconciliation）** | 定时重扫全量并比对 | 慢，但兜底、**必需** |
| **自愈** | 检测卡死并接管 | 防止"永远 pending" |

> **"定时重扫是必需品，不是可选项"**——因为上游"不重投"是常态（见 §10.4）。

**对账的三要素**

```
□ 权威状态从系统外部重建（不依赖进程内存里的名单）
□ 有轮转游标（避免每次从头扫、避免饿死尾部）
□ 有预算（一次全扫的配额/时间上限，超了分批）
```

**指标**：重扫发现了多少条"事件没送达导致的结论缺失"——这是**事件丢失率的直接度量**。

---

### 4.4 部分失败与补偿

分布式里"部分失败"是常态而非例外。

```
□ 每个跨系统写操作都有补偿路径（或明确声明"不可补偿"并写进文档）
□ 补偿动作本身幂等
□ 补偿失败怎么办（重试 → 人工工单 → 告警）
□ 用户能看到"部分成功"的中间态吗（还是系统假装没发生）
```

---

### 4.5 持久性、备份与 RTO/RPO

| | 定义 | 决定什么 |
|---|---|---|
| **持久性 Durability** | 提交的数据在崩溃后还在 | 同步刷盘 / WAL / 复制因子 / 持久卷 |
| **RPO** | 能容忍丢多少数据（时间） | 备份频率、复制方式 |
| **RTO** | 能容忍多久不可用（时间） | 恢复流程、是否多区/多活 |

**别把"有备份"当成"能恢复"**：备份必须**演练过恢复**（restore drill），否则它是安慰剂。

---

### 4.6 错误模型与错误传播

```
□ 错误分类：可重试 / 不可重试 / 业务错误 / 系统错误 / 未知
□ 每类错误的默认动作是什么（重试 / 降级 / 拒绝 / 告警）
□ 错误信息带上下文（哪个 ID、哪个阶段）
□ 不要吞异常（catch 后什么都不做 = 静默失败）
□ 未知错误 → fail-closed + 告警，而不是猜一个"大概没事"
```

---

## 5. 工程交付类性质

### 5.1 可观测性 Observability

**三支柱**

| 支柱 | 回答 | 要点 |
|---|---|---|
| **指标 Metrics** | 有没有发生、有多少 | 低基数、可聚合；**能定位到维度**的指标才有价值 |
| **日志 Logs** | 具体那一条发生了什么 | 结构化；必须带**关联 ID**（delivery_id / request_id / trace_id） |
| **追踪 Traces** | 跨服务怎么串起来 | 传播上下文；采样策略 |

**别只记"结果"，要记"过程"**

```
✅ check_runs_written_total{repo, action}      —— 写了多少
✅ check_runs_per_sha                           —— 同一目标是否写了多个（幂等性回归的探针）
✅ stuck_in_progress                             —— 活性探针
✅ verdict_flip_total                            —— 结论被改写的次数（不一致探针）
✅ duplicate_suppressed_total                    —— 幂等拦截次数
✅ rechecks_flipped                              —— 重扫发现的"事件丢失量"（覆盖率探针）
```

**RED / USE 方法**：Rate / Error / Duration；Utilization / Saturation / Errors。

### 5.2 可调试性与可审计性

| | 区别 |
|---|---|
| **可调试** | 能定位问题出在哪（面向当下） |
| **可审计** | 能还原"谁在什么时候做了什么、依据是什么"（面向事后与合规） |

**审计记录最小字段**：时间、操作者（主体）、对象（PR / 订单）、**输入指纹**（head_sha / policy_version）、
命中的规则、结论、判定时刻、有效期。

> 审计记录里**必须带"依据的版本"**：只记"通过"不记"依据哪版策略通过"，事后无法解释。

### 5.3 可测试性 Testability

**可测性是设计出来的，不是测出来的。** 设计手段：

```
□ 依赖注入：时间、随机数、网络、存储都可替换
□ 时间作为参数（§2.8）
□ 无隐藏全局状态（进程内 map 缓存要考虑多副本）
□ 契约测试固定上下游样本
□ 可重放：录制的输入能复现失败
```

**故障注入 / 测试矩阵**（幂等类系统的最小矩阵）

```
□ T1 同一 delivery 重放 N 次   → 只处理 1 次
□ T2 同一业务键、不同载荷      → 冲突报错
□ T3 事件乱序到达              → 结论与顺序无关
□ T4 并发到达                  → 只有 1 个结果
□ T5 处理中途崩溃              → 重启后能补终态
□ T6 下游超时/5xx              → 退避重试，绝不写"成功"
□ T7 配额耗尽                 → 降级，绝不写"成功"
□ T8 结论写失败                → 有告警，能被重扫修复
```

**绕过测试（安全类系统必做）**：不经过你的系统直接改数据，**能不能破坏你的不变量**？
如果能，说明你的门禁只是"建议"不是"强制"。

### 5.4 可回滚、向前兼容与可演进

| 性质 | 含义 | 手段 |
|---|---|---|
| **可回滚 Rollback** | 出事能退回去 | 版本化部署、数据迁移可逆、feature flag |
| **向前兼容 Forward Compat** | 新版本能读旧数据 | schema 演进规范、只加不改、默认值 |
| **向后兼容 Backward Compat** | 旧版本能读新数据 | 版本化 API、字段只增不删不语义变 |
| **可弃用 Deprecation** | 老的能优雅退休 | 标注 → 告警 → 移除的完整流程 |
| **可演进 Evolvability** | 改需求不用重写 | 模块边界清晰、契约先行、开关隔离变更 |

> **数据迁移是最难回滚的部分**：schema 回滚容易，**数据回滚极难**。
> 迁移设计要回答："执行到一半崩溃了怎么办？"（向前兼容 + 双写 + 回填 + 切读 + 清理）

### 5.5 安全性

安全性是**性质集合**，不是功能：

| 性质 | 内容 |
|---|---|
| **认证 Authentication** | 你是谁（OAuth / mTLS / App JWT / SA token） |
| **授权 Authorization** | 你能做什么（RBAC / ABAC / 最小权限） |
| **机密性 Confidentiality** | 敏感信息不泄露（加密、脱敏、密钥管理） |
| **完整性 Integrity** | 数据不被篡改（签名、验签、防重放） |
| **不可否认性 Non-repudiation** | 事后能证明谁做的（审计、签名日志） |
| **隔离性 Isolation** | 租户之间不互相影响（namespace / 行级安全 / 独立凭据） |
| **抗抵赖/防重放** | 相同请求重复提交无效（nonce / timestamp / 幂等键） |

**工程要点**

```
□ 验签用常数时间比较（hmac.Equal），防时序攻击
□ 权限最小化：能读就别给写；★ 绝不授予"能改代码"的权限（否则能绕过自己的门禁）
□ 凭据不进 Git、不进镜像、不进日志；用 Secret Manager + External Secrets
□ 授权检查在服务端做，不能只靠前端隐藏
□ 敏感操作要审计
□ 默认拒绝（deny by default），白名单显式放行
```

### 5.6 性能与成本

| 性质 | 指标 |
|---|---|
| **延迟 Latency** | **分位数**（P50/P95/P99），不是平均值；区分排队 vs 处理 |
| **吞吐 Throughput** | QPS / 并发数 |
| **资源效率** | 每次请求的 CPU / 内存 / 网络 / API 配额 |
| **成本 Cost** | 单位业务成本；配额消耗速率；日志/存储/出网费用 |

**性能相关的性质**：可伸缩（水平扩）、弹性（有突发能扛）、可预测（有背压）。
**成本相关的性质**：可预算（配额可告警）、可优化（能定位到成本大头）。

> 云上特有：**API 配额就是硬性并发上限**。设计重试时必须把配额算进去——
> 否则重试会把自己打死（§3.7）。

### 5.7 可维护性与可演进性

SOLID / 简约原则的**性质视角**解读：

| 原则 | 对应的性质 |
|---|---|
| **单一职责 SRP** | 可演进：一个需求只改一个地方 |
| **开闭 OCP** | 可扩展：加新规则不改老流程 |
| **里氏替换 LSP** | 可替换：实现可互换 |
| **接口隔离 ISP** | 可测试：依赖小而具体 |
| **依赖倒置 DIP** | 可替换：换实现不改业务 |
| **DRY / KISS / YAGNI** | 可维护：改动半径小、理解成本低 |
| **纯函数 / 引用透明** | 可测试、可并发、可推理 |
| **显式优于隐式** | 可观测：状态写在数据里而不是进程内存 |

> 特别提醒：**纯函数 + 显式状态**是幂等性的朋友。
> "状态在数据库里"比"状态在进程内存里"可靠得多——前者重启后还在，后者需要重扫重建。

## 6. 性质之间的冲突与取舍

**关键认知：性质不能全要。** 下面是最经典的取舍：

| 冲突 | 取舍 |
|---|---|
| **一致性 ↔ 可用性** | CAP / PACELC（§3.10） |
| **一致性 ↔ 延迟** | 强一致要多副本确认；最终一致先返回后修正 |
| **幂等 ↔ 性能** | 幂等要存键、要查重；高频路径可只在业务键层做 |
| **可重试 ↔ 成本/配额** | 重试放大流量；配额有限 |
| **可观测 ↔ 成本/隐私** | 日志越全越好？敏感信息与费用都要算 |
| **安全性 ↔ 易用性** | 强认证 vs 接入成本 |
| **可回滚 ↔ 性能/复杂度** | 保留双版本 = 多一份资源与心智负担 |
| **抽象 ↔ 简单** | 多一层抽象换扩展性；但可能掩盖问题 |
| **自动化 ↔ 人的判断** | 门禁全自动 vs 紧急通道（break-glass） |

**取舍的写法（避免"既要又要"）**

```
✅ "判定链路要求 fail-closed（一致性优先）；读取链路允许最终一致（延迟优先）"
❌ "系统要非常一致，同时也要高可用和高性能"
```

> 每当设计评审里出现"都要"，把它拆成**按路径/按场景**分别声明。

## 7. 开发自查清单

### 7.1 通用 12 问（每个需求过一遍）

```
1.  幂等：重复执行会怎样？幂等键是什么？同键不同载荷怎么办？
2.  原子：中途崩溃会怎样？有没有中间态？谁来收拾？
3.  并发：两个请求同时到会怎样？靠什么互斥（唯一约束/CAS/锁）？
4.  顺序：事件乱序/丢失会怎样？结论依赖顺序吗？有重扫兜底吗？
5.  超时：出站调用的 deadline 多少？重试总耗时会不会超预算？
6.  过载：下游慢/挂/配额耗尽会怎样？熔断/限流/背压/舱壁在哪？
7.  失败姿态：判定不出来时默认放行还是拦住？
8.  自愈：重启后能自己回到正确状态吗？靠事件还是靠对账？
9.  可观测：出问题时哪个指标/日志能定位到这一条？
10. 可验证：测试矩阵覆盖乱序/并发/崩溃/配额了吗？
11. 可交付：怎么上线怎么退？老版本还在跑吗？兼容吗？
12. 权责：谁能读写？凭据在哪？审计留痕吗？
```

### 7.2 各类性质的最小检查

**正确性**
```
□ 幂等键唯一约束在数据库层，不在应用层
□ 原子写用事务/原子原语，没有"先删后建"
□ 乱序不影响结论（判定用最新快照）
□ 时间/随机数可注入
```

**并发与分布式**
```
□ 没有裸的"先查后写"
□ 锁有超时与固定顺序；跨节点用 fencing token 或避免用锁
□ 重试有指数退避 + 抖动 + 预算 + 幂等兜底
□ 队列有界
□ 跨系统写用 Outbox 或 Saga
```

**失败与恢复**
```
□ 所有异常路径都写明了"写什么结论"
□ 有定时重扫/对账，且有预算与游标
□ 备份做过恢复演练
□ 部分失败有补偿路径
```

**工程交付**
```
□ 关键路径有指标（含"退化探针"如 stuck / flip / duplicate）
□ 日志带关联 ID
□ 有契约测试 + 故障注入测试
□ 变更有 feature flag 或可回滚路径
□ 权限最小化，凭据外置
```

## 8. 反模式清单

| # | 反模式 | 后果 |
|---|---|---|
| 1 | 在应用层判重，数据库无唯一约束 | 并发下重复处理 |
| 2 | 判定失败写 `success` | 门禁被绕过（fail-open） |
| 3 | 结论依赖事件顺序 | 乱序即错 |
| 4 | 只做事件驱动，不做重扫 | 丢事件 = 永久卡死 |
| 5 | 重试无退避无抖动 | 重试风暴雪崩 |
| 6 | 重试总耗时超过上游 deadline | 调用方看到失败但副作用已生效 |
| 7 | 无界队列 | 过载变 OOM |
| 8 | 状态只存在进程内存 | 重启丢状态、多副本不一致 |
| 9 | `先删后建` 改配置 | 中途崩溃 → 服务裸奔 |
| 10 | 用本地墙上时间做分布式判定 | 时钟漂移 → 提前过期 / 误判 |
| 11 | 凭据进 Git / 镜像 / 日志 | 泄露 |
| 12 | 授予过宽权限（如能改代码） | 能绕过自己的门禁 |
| 13 | 无退避的无限重试 | 配额打爆 |
| 14 | 只有平均值监控 | P99 问题看不见 |
| 15 | 状态机允许回退（completed → in_progress） | 结论抖动，用户无所适从 |
| 16 | "先上线再说，测试后面补" | 性质无法证伪 |

## 9. 怎么把性质变成证据

**每条性质都要落到四类证据中的至少一类**

| 证据类型 | 形式 | 适合证明 |
|---|---|---|
| **论证** | 设计文档里的推理 + 边界条件列举 | 难以直接测试的性质（线性一致性、活性） |
| **测试** | 单测 / 契约测试 / 故障注入 / 混沌 | 可枚举的失败场景 |
| **观测** | 指标、告警、日志、审计 | 运行中的持续性（活性、退化） |
| **演练** | 恢复演练、绕过演练、限流演练、故障切换 | "系统撑不撑得住"类性质 |

**实践模板：在设计文档里为每条性质写一行**

```markdown
| 性质 | 本设计如何满足 | 证据 | 失效时的表现 |
|---|---|---|---|
| 幂等性 | delivery_id 唯一约束 + ON CONFLICT | T1 重放测试 | 重复处理 → 指标 duplicate_suppressed 上升 |
| 原子性 | 单库事务写 check 与 outbox | 崩溃注入 T5 | 孤儿事件 → 对账扫描修复 |
| 活性 | 每 5 min 重扫 + 卡死接管 | 线上 stuck_in_progress 指标 | 卡住 → 告警 + 接管 |
| fail-closed | 判定失败只写 action_required | T6/T7 故障注入 | 判定不出 → 拦住合并 |
```

> 有"证据"列的性质才是被承诺的性质；没有证据的一栏，多半只是愿望。

## 10. 案例：GitOps 门禁场景下的原子性与幂等性

> 本节收编自对 **Argo CD / GitHub App 门禁**场景的探索（原始文档见
> [how-to-atomic-idempotency.md](../gcp/ucp/argocd-topics/how-to-atomic-idempotency.md)）。
> 保留其核心推演，并把它接到本文的性质框架上。

### 10.1 先看清模型：这是"收敛"问题，不是"请求-响应"问题

**Level-based（声明期望状态，持续对比校正）** vs **Edge-triggered（收到事件才动作）**：

| | Level-based | Edge-triggered |
|---|---|---|
| 描述 | 声明"我要什么"，系统持续比对直到一致 | 收到"发生了什么"事件，做一次对应动作 |
| 丢事件 | 下次比对会发现并纠正 | **永久丢失** |
| 乱序 | 不影响（比对的是当前状态） | 可能得出过时结论 |
| 幂等要求 | 天然需要（反复 apply 同一目标） | 天然需要（重试同一事件） |
| 经典例子 | Kubernetes / Argo CD | 事件驱动的 CI |

> **结论：GitOps 门禁系统 = Level-based 主体（声明期望）+ Edge-triggered 触发（加速收敛）。**
> 这就是为什么"**定期重扫**"是必需品而不是可选项——
> Edge 部分随时可能丢事件，Level 部分必须能独立把系统拉回正确状态。

### 10.2 六个投递契约（外部接口从 pull 变 push 后新增的义务）

```
① 至少一次投递 + 必须幂等
② 10 秒超时预算 → 必须"先 ACK，再异步处理"
③ 事件可能乱序、可能缺失
④ 投递失败不会自动重试
⑤ 我们变成了一个公网服务（暴露面 + 验签 + 限流）
⑥ 出站配额与并发限制（调 GitHub API 的硬上限）
```

### 10.3 三层幂等键

| 层 | 键 | 挡什么 | 实现 |
|---|---|---|---|
| L1 | 投递 ID（`X-GitHub-Delivery`） | 同一事件重复到达 | 原子 `SET NX` 占位（**不是**"先查后记"） |
| L2 | 业务键 `(repo, check_name, head_sha)` | 同一目标被处理多次 | 写进 check 的 `external_id` |
| L3 | 版本键 `policy_version` | 策略变了要重判 | 写进 `output.summary` |

**同键不同载荷 → 报冲突，不静默覆盖。**
**占位短 TTL + 完成标记长 TTL** → 崩溃不永久占坑。

### 10.4 崩溃恢复：状态不能卡死

```
□ 判定前先写 in_progress → 再写 completed（两段式，fail-closed）
□ in_progress 不是"通过"，只是"未判定"
□ 卡死检测 + 接管（别的实例接手）
□ 定期重扫是必需品（上游不重投 + 结论会过期）
□ 受管对象名单从 GitHub 重建，不依赖进程内存
□ 重扫有配额预算 + 轮转游标（不饿死尾部）
```

### 10.5 判定输入 = 当前快照，不是事件 payload

**这是整份推演里最值钱的一条技巧**：

```
❌ 用事件里的 payload 判定（事件到达时的世界可能已经变了）
✅ 收到事件 → 重新 GET 当前 PR 快照 → 用快照判定
```

好处：一次性消除**乱序**、**过期**、**事件缺失**三个问题的绝大部分影响——
因为结论只取决于"现在是什么样"，不取决于"消息是什么时候到的"。

### 10.6 写入侧：TOCTOU 与状态机

```go
// ❌ TOCTOU：两个并发请求都能通过判重
if !seen(key) { seen(key); createCheck() }

// ✅ 靠幂等写原语 + 唯一业务键收敛
upsertCheckSuite(repoID, checkName, headSHA)   // 同名 upsert
```

**状态机（单调，不可回退）**

```
in_progress ──▶ completed(conclusion)
      │                ▲
      └──▶ action_required / failure / error
```

> `in_progress` 与 `completed` 之间**不允许回退**；
> 只允许"结论被新版本结论覆盖"（通过 L3 版本键判断是否该覆盖）。

### 10.7 副作用的原子性：Outbox

判定结果要写 check，可能还要发评论 / 打标签 / 通知。
**这些副作用不在同一事务里** → 用 Outbox：

```
事务内: 写 check 结果 + INSERT outbox(副作用事件)
事务后:  投递器轮询 outbox → 执行副作用 → 标记已执行（幂等）
```

副作用自身也要幂等（先查重 / 用状态位 / 优先用"状态"而不是"动作"表达结果——
例如**打 label** 比**发评论**更容易做到幂等）。

### 10.8 策略版本化

```
□ 结论里带上 policy_version（策略的 blob SHA / resourceVersion）
□ 策略变更后要重判：靠版本比对触发，而不是靠"记忆"
□ 策略读取要带版本/ETag，避免"读到一半的策略"
```

### 10.9 配额、背压与降级

```
□ 出站调用有超时 + 退避重试 + 预算
□ 重扫有配额上限与轮转
□ 配额耗尽 → 降级（少扫、只扫高优先级），但绝不写"通过"
□ 429/403 要能被区分并告警
```

### 10.10 怎么证明实现真的幂等（测试矩阵）

| 用例 | 期望 |
|---|---|
| T1 同一 delivery 重放 5 次 | 只处理 1 次，只有 1 个 check run |
| T2 同业务键不同载荷 | 冲突报错 |
| T3 事件乱序 | 结论与顺序无关 |
| T4 并发到达 | 只有 1 个 check run |
| T5 判定中途 kill | 重启后能补终态，不永久 in_progress |
| T6 下游 5xx / 超时 | 退避重试，**绝不写 success** |
| T7 配额耗尽 | 降级，**绝不写 success** |
| T8 结论写失败 | 有告警，能被重扫修复 |

**配套指标**：`check_runs_per_sha` / `stuck_in_progress` / `verdict_flip` / `duplicate_suppressed` / `recheck_flipped`。

## 附录 A：一句话速查

```
幂等：做一次 = 做 N 次
原子：中间态不可见
一致：读到的是最新真相（线性一致最强，最终一致最弱）
单调：只往前走，不倒退
收敛：最终一定对，且靠持续比对而非事件触发
活性：好事最终发生（超时 + 进度 + 接管）
安全性：坏事永不发生（约束 + 幂等 + fail-closed）
投递：至少一次 + 幂等 = effectively-once（exactly-once 是幻觉）
顺序无关：判定用当前快照，不用事件 payload
超时：每个跨边界调用都有 deadline，且总预算有界
重试：退避 + 抖动 + 预算 + 幂等兜底
过载：有界队列 + 限流 + 熔断 + 舱壁 + 背压
跨系统写：Outbox（副作用原子化）或 Saga（补偿）
恢复：事件驱动 + 定时对账，双保险
证据：论证 / 测试 / 观测 / 演练，至少一种
```
