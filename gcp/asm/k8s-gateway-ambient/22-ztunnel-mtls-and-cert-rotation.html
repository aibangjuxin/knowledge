ztunnel L4 mTLS 工作机制与证书轮转深度解析

Istio 1.30.3 ambient · in-pod netns · HBONE tunnel · SecretManager · Background rotation @ 50% TTL

HBONE 协议栈

  • HTTP/2 — 多路复用业务流,一条隧道承载多 conn
  • CONNECT method — RFC 7231 标准隧道,`:authority` = dst Service IP:port
  • mTLS 1.3 — AES-256-GCM / AES-128-GCM,双向 SPIFFE 身份验证
  • SNI 不带 — 用 dst IP 选 server cert(由 iptables redirect 保留原 IP)
  • listen port 15008 — Istio convention,任何 HBONE-aware 代理都监听此端口

证书轮转三件套

  • SecretManager — ztunnel 进程内的公开 API,提供 `fetch_certificate_pri(id, pri)`
  • Worker (后台 task) — 真正做 CSR + 续期 + cache swap
  • CertFetcher — workload 出现就 Warmup prefetch,workload 离开就 Forget
  • 3 优先级:RealTime(阻塞)/ Warmup(预取)/ Background(50% TTL 续期)
  • per-identity 指数退避 — 一个 cert 失败不影响其他

可调旋钮(istiod side)

  • DEFAULT_WORKLOAD_CERT_TTL = 24h(默认)
  • MAX_WORKLOAD_CERT_TTL = 48h(istiod 接受上限)
  • TTL 上限硬约束 = 90d(FQ 文档明确)
  • per-workload: proxyMetadata.SECRET_TTL override
  • SECRET_GRACE_PERIOD_RATIO = 0.5(寿命过半触发)
  • SECRET_GRACE_PERIOD_RATIO_JITTER = 0.01(防雪崩抖动)

关键不变量(invariant)

  • istiod 强制:ztunnel 只能替运行在自己 node 上的 workload 申请证书(impersonation check)
  • SAN ≠ IP:SAN 是 SPIFFE URI,IP 变了 pod 重启不影响身份
  • 业务无感:HBONE 连接复用,cert 轮转期间无 drain、无 reload
  • Pod 内网 plaintext:应用进程始终发明文,mTLS 只在 ztunnel↔ztunnel 之间
  • PEERAUTHN 不作用于 waypoint:waypoint 上 PeerAuthn 是 no-op

ZDS 握手 (v2 新增)

  • istio-cni ⇄ ztunnel 通过 UDS `/var/run/ztunnel/ztunnel.sock` 通信
  • SCM_RIGHTS — Linux 跨进程传递打开的文件描述符的机制,直接把 Pod netns fd 递给 ztunnel
  • setns() — ztunnel 拿到 fd 后切换进去,绑 15008/15006/15001/15053
  • 失败症状:Pod 内 iptables 已加,但无 ztunnel socket → 流量黑洞(应用 connect 立即 reset)
  • 排查命令:nsenter -t <pid> -n ss -tlnp \| grep -E '1500[168]'(空 = ZDS 失败)
  • RBAC 关键:serviceaccounts/token: create(ztunnel 默认有,验证:kubectl auth can-i)

ztunnel vs Waypoint 能力分工 (v2 新增)

  • ztunnel 设计哲学:"aggressively small feature set is the key feature" — 只做 L4
  • ztunnel 能:mTLS / SPIFFE principal / L4 AuthZ (namespace+ipBlocks+ports) / TCP metrics
  • ztunnel 不能:HTTP method/path/header / JWT 校验 / 重试超时 / Header 改写 / Body 限制 / L7 metrics / WASM
  • 以上全部归 waypoint(Envoy / agentgateway)。HBONE 隧道建立后是裸 TCP 字节流
  • 业务含义:File upload / Header filter / Kong→Runtime L7 鉴权 —— 全都强制经过 waypoint(或 Kong),不能依赖 ztunnel
  • 机制根据:ztunnel 的 Rust 进程不解析 L7,L7 是 waypoint Envoy 的领地

CSR SAN 不被信任 + RBAC 边界 (v2 新增)

  • CSR 里写的 SAN:istiod 不信任,完全依据 TokenReview 拿到的 JWT sub 重写 URI SAN
  • 私钥:ztunnel 内存生成 ECDSA P-256,不落盘、不进 Secret、不挂 hostPath
  • RBAC 关键权限:serviceaccounts/token: create(cluster-scoped,ztunnel 被攻破 = 可冒充任意 SA)
  • 撤销机制:无 CRL/OCSP,靠短 TTL(默认 24h)自然过期
  • Root CA:每次 CreateCertificate 响应附带完整 bundle,ztunnel 内存信任库自动更新
  • STRICT = 关 15006:ztunnel 拒绝明文入,只接受 15008 HBONE。**部署时必须先把 mesh 内所有调用方纳管再开 STRICT**

完整端口表 (v2 扩展)

  • 15001:出站 — Pod 出站流量入口,iptables redirect 到此
  • 15006:入站 plaintext — 非 HBONE 的入站(STRICT 模式下拒绝)
  • 15008:入站 HBONE — mTLS over HTTP/2 CONNECT 隧道终点
  • 15053:出站 DNS 捕获 — ISTIO_META_DNS_CAPTURE=true 时启用
  • 15020:metrics — Prometheus scrape 端点 (/stats)
  • 15021:readiness probe — K8s 探活

Sidecar vs Ambient 关键差异 (v2 强化)

  • sidecar 时代:每个 pod 有 pilot-agent → Envoy SDS 推 cert
  • ambient 时代:每个节点一个 ztunnel → 自管多 cert(替本节点所有 pod)
  • sidecar 时代:Pod 内有 sidecar container 容器化
  • ambient 时代:Pod 无注入,in-pod netns listener(由 istio-cni 建 via ZDS)
  • 三种代理证书路径:Sidecar Envoy (istio-agent SDS) / waypoint Envoy (istio-agent SDS) / ztunnel (直连 gRPC 到 istiod CA :15012)
  • 15006 / 15001 / 15090 在 sidecar 内;15006 / 15001 / 15008 / 15053 / 15020 在 ztunnel pod 内 + pod netns 镜像

高频 Pitfall

  • impersonation 失败:自定义 SA 替换 ztunnel-sa → 所有 mTLS 失败
  • CSR 风暴:pod 抖动 → 大量新 cert 预取 → istiod CA 压力峰值
  • TTL 太短:分钟级轮转 → istiod + Prometheus 双倍压力
  • ZDS 失败黑洞:CNI/ztunnel 启动顺序错 → Pod 内有 iptables 但无 socket
  • STRICT 提前开:mesh 外的调用方被拒 → 业务断线(先纳管再开 STRICT)
  • NetworkPolicy 误配:15008 被挡 → ztunnel 报错带 "maybe a NetworkPolicy is blocking HBONE port 15008"
