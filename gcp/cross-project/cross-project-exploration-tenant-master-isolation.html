Cross-Project Exploration — Tenant Ingress + Master Backend

Goal: keep user-facing ingress, certificate, URL map, and Cloud Armor in the Tenant project; run real services in the Master project; enforce tenant isolation at the LB chain boundary. 8 candidate architectures below — each is runnable, not just conceptual.

Hard constraints (from your requirement):
  • Tenant project holds: domain, public IP, TLS cert, External LB, Cloud Armor policy bound to Tenant Backend Service
  • Master project holds: real workload (MIG / GKE / Cloud Run) + the LB that dispatches into it
  • Two projects, separate VPCs (or one VPC shared via Shared VPC); no Peering required but may be used
  • Tenant isolation = Tenant decides who reaches its own Backend Service; Master cannot bypass

Architectures — 8 runnable options

#01 VPC Peering + Private LB Classic
Talent needs
  • Global Static IP / SSL Cert
  • External HTTPS LB chain
  • Backend Service + Cloud Armor
  • ZONAL NEG (NON_GCP_PRIVATE_IP_PORT)
  • pointing to Master ILB VIP
Master needs
  • Internal LB (L4 or L7 ILB)
  • Backend Service + HC
  • MIG / GKE backend
  • Master VPC firewall: allow Tenant HC range
vpc-peering armor @ tenant
Same model as cross-project-success-two.md (you already validated it). Caveat: flat IP space, 25 peering limit per VPC, overlapping CIDRs impossible, source IP = Tenant ILB proxy IP.
#02 PSC NEG + Service Attachment Verified
Talent needs
  • External HTTPS LB chain
  • Backend Service + Cloud Armor
  • PSC NEG (PRIVATE_SERVICE_CONNECT)
  • PSC NAT subnet (e.g. /27)
  • Org Policy: allow EXTERNAL_MANAGED
Master needs
  • ILB (L7) + Backend Service + MIG
  • Service Attachment (ACCEPT_MANUAL)
  • consumer-accept-list = Tenant project
  • Producer forwarding rule: --allow-global-access
psc armor @ tenant
Google's recommended model (your public-tls-cross-project-implementation.html proves it). Overlapping IPs supported, no peering, clean isolation, no HC needed at Tenant side.
#03 Serverless NEG → Cloud Run in Master Cloud Run
Talent needs
  • External HTTPS LB chain
  • Backend Service + Cloud Armor
  • Serverless NEG
  • Serverless NEG ↔ Cloud Run ARN
Master needs
  • Cloud Run service
  • IAM: roles/run.invoker
  • granted to Tenant service account or allUsers
  • No LB, no VPC, no NEG
serverless-neg armor @ tenant
Only works if Master workload is Cloud Run / Cloud Functions / App Engine. Cheapest, no infra in Master. No MIG/GKE.
#04 Hybrid NEG → On-prem / other cloud Hybrid
Talent needs
  • External HTTPS LB + Backend Service
  • Cloud Armor on Backend Service
  • Hybrid NEG (zonal)
  • NEG endpoint = private IP of on-prem
Master (or off-GCP)
  • Cloud VPN / Cloud Interconnect
  • Cloud Router + BGP
  • On-prem / AWS / Azure workload
  • firewall: allow Tenant HC range
hybrid-neg + vpn armor @ tenant
Use case: Master is actually on-prem or another cloud. Listed for completeness — doesn't apply if Master is a GCP project with MIG/GKE.
#05 Shared VPC + Cross-project Internal LB Shared VPC
Talent needs
  • Service project role on host project
  • External HTTPS LB chain
  • Backend Service + Cloud Armor
  • Zonal NEG to Master VM IP
Master needs
  • Service project role on host project
  • MIG / GKE using shared subnet
  • HC source range allowed
  • No ILB needed if direct NEG works
shared-vpc armor @ tenant
Simplest if both projects are already service projects of a host project. Caveat: Shared VPC admin (org-level) is required — not always available; isolation at L7 only via Cloud Armor + routing rules.
#06 Multi-tenant PSC (N Tenants → 1 Master) Multi-Tenant
Per Tenant needs
  • External HTTPS LB + Cert + Domain
  • Backend Service + Cloud Armor
  • PSC NEG pointing at shared SA
Master needs (shared)
  • One Service Attachment
  • consumer-accept-list = all Tenant projects
  • ILB + Backend Service + MIG
  • Quota: PSC NEG per region
psc n:1 armor @ tenant
True multi-tenant SaaS model. Each tenant owns its own CA + domain; Master is a shared service. Quota: PSC endpoint per project per region (default 25, raise to 100+).
#07 GKE Gateway API → KSA → GSA → Master K8s Native
Talent GKE needs
  • GKE cluster + Gateway CRD
  • GCPBackendPolicy (Cloud Armor)
  • KSA ↔ GSA binding
  • GSA: roles for Master's network
Master GKE needs
  • GKE Service + NEG annotation
  • (or standalone MIG + NEG)
  • Allow Tenant GSA in IAM
  • Master GSA: networkUser on Tenant subnet (if Shared VPC)
gke-gateway-api armor @ tenant
K8s-native — no PSC, no Peering. Cloud Armor attached via GCPBackendPolicy. Caveat: both sides must be GKE; combined with PSC (#2) for cross-region.
#08 Global Ext LB + Multi-Region PSC NEG Global
Talent needs
  • Global Static IP + SSL Cert
  • Global Ext HTTPS LB (anycast)
  • Backend Service + Cloud Armor
  • 1 PSC NEG per Master region
Per region needs
  • ILB + Backend Service + MIG
  • Service Attachment per region
  • Tenant project in accept-list
  • Regional SA → Tenant Backend
psc multi-region armor @ tenant
Production-grade HA. Tenant LB does global anycast + region-aware routing; Master replicates. Cost: 2× ILB + 2× SA per region. Already proven in your existing PSC template.

Decision — which to pick

If Master is single-region GCP (MIG/GKE)

Pick #02 (PSC). Same pattern you already validated in public-tls-cross-project-implementation.html. Source-IP preserved end-to-end via PSC SNAT, Cloud Armor enforced at Tenant side, zero VPC Peering, overlapping CIDRs OK.

#01 fallback if PSC quota is the blocker — your cross-project-success-two.md already shows it's runnable, just adds a Tenant-side HC and a Master firewall rule.

#05 only if both projects are already service projects of a host project. Shared VPC makes isolation weaker (same VPC).

If multi-tenant SaaS (many Tenants → 1 Master)

Pick #06 (Multi-tenant PSC). Each Tenant owns domain + cert + Cloud Armor + URL Map; Master has one Service Attachment with Tenant projects in consumer-accept-list. Best isolation, best scaling story.

#08 (multi-region PSC) if Tenants must be served globally — it's #06 + regional replication.

Avoid #01 at scale: per-tenant VPC peering doesn't survive past ~10 tenants.

If Master is Cloud Run / serverless

Pick #03 (Serverless NEG). No Master LB, no Master VPC, just IAM roles/run.invoker. Cheapest path.

For multi-tenant SaaS on Cloud Run, stack with #06: per-Tenant Serverless NEG + shared Cloud Run service + IAM allowlist per Tenant identity.

If both sides are GKE

Pick #07 (GKE Gateway API + WIF). Everything stays in K8s manifests; Cloud Armor via GCPBackendPolicy. Workload Identity bridges KSA→GSA→Master IAM.

For cross-project Service exposure, combine #07 + #02: GKE Gateway at Tenant, PSC NEG pointing at Master Service.
