一张 API 一张 cert — 怎么走完全程?

给团队新 API 申请 client 证书,需要从"写好身份信息"走到"GLB 认这张证书"。

1. 触发:用户说"我要给 apiname1 申请证书"

用户是某个 Team 的开发者,要为新域名下的某一个 API(例如 team-a 下的 apiname1)申请一张 client cert(客户端证书)——这张 cert 就像通行证,GLB 看到它才知道"哦,这是 apiname1 的请求"。

↓

2. 写好"我是谁":用 OpenSSL 生成 CSR

CSR = 证书申请表——里头要填一张"扩展表",最关键一行: URI:spiffe://caep.example/tenant/team-a/apiname1。URI 写错就等于通行证姓名写错,GLB 后面无法识别。同 Team 不同 API 必须 URI 不同。

↓

3. Venafi 让 CA 盖章

CSR 提交到 Venafi(企业证书管家),它让 CA(权威发证机构)在申请表上盖章。私钥始终留在用户电脑里不发出去——Venafi 只盖公开那部分。批准后,用户拿到 cert(公开)和 key(私有)两份文件。

↓

4. 上线:配置 GLB TrustConfig 接住这张 cert

CA 的根证书必须先放进 GLB 的 TrustConfig(信任仓库)。这样 GLB 看到任何"这张 CA 签过的 cert"都认。用户把 cert + key 配到自己的客户端(curl/SDK)里,正式发起 mTLS 请求。

↓

5. 结局:URI-SAN 对得上,API 拿到服务

GLB 验 cert 链 → 把 URI 写到 X-Client-Cert-URI-SANs 头 → 转发到 GKE → HTTPRoute 比对 URI 与路由声明。team-a/apiname1 的请求只进team-a/apiname1 的服务。team-a 的另一个 API 用别的 cert 申,跨 cert 调用直接 404 漂移拒绝。

↓

6. 反向:谁能撤销?谁来审计?

cert 不是永久的。Venafi Admin 可以在后台一键吊销,GLB 下次收到就拒。CA 根证书坏了也能批量废掉所有子 cert。所有签发/吊销动作都进 Venafi 审计日志——谁、什么时候、给哪个 API、签了/吊了哪张 cert,全程可追溯。
