ADR-011 · GKE Pod 跨项目访问 Bucket 完整链路

Workload Identity Federation + 跨 project IAM · 4 视角 · 配套 ADR-011-pod-bucket-flow.md

① 4 层抽象 —— 从 Pod 到 Bucket 的完整链路

业务方只接触 L1 + L2 (Pod + KSA 名字),L3 + L4 (WIF + IAM)由平台 + GCP 自动处理。

② 时序图 —— Pod 创建 → 写 Bucket 成功(10 步)

业务方只关心 ① 和 ⑤;中间 5 步(②-④ + ⑥-⑩)由 K8s + WIF + IAM + GCS 自动完成。

③ 跨 project IAM policy —— 业务方完全无感,平台配

KSA principal 格式 + 最小权限 + condition 限定 prefix。

④ 决策树 —— 4 路径(A/B/C/D)

A 是 Google 推荐主路径;C SA key 不推荐。

核心结论

  • • Pod ↔ Bucket = 4 层抽象 + 1 条 IAM 数据通路
  • • 凭据 0 静态(WIF 短期 token)
  • • 业务方只写 serviceAccountName
  • • 跨 project IAM policy 由平台配
  • • GCP Audit Logs 自动记录(不可关闭)

vs NAS 关键差异

  • • NAS:挂文件系统,凭据=SMB user/pass
  • • Bucket:调 API,凭据=WIF 短期 token
  • • NAS 数据物理位置 = 公司内网
  • • Bucket 数据物理位置 = GCP 内(跨 project)
  • • Bucket 合规压力远高于 NAS(档 1 红线)

禁用方案

  • • ❌ SA key 挂 Secret
  • • ❌ KSA + Editor role
  • • ❌ Bucket 公共 ACL
  • • ❌ 关闭 Cloud Audit Logs 数据访问
  • • ❌ KSA + roles/owner
