# 02 · 高可用架构

> 目标：Argo CD 在 GKE 上单点故障不中断，且状态不丢。
> 事实来源：上游 `docs/operator-manual/high_availability.md` 与
> `manifests/ha/base/redis-ha/chart/values.yaml`。

---

## 1. HA 组件全貌

官方 HA 清单（`manifests/ha/install.yaml`）相对单实例版本的变化：

| 组件 | 单实例 | HA | 变化点 |
|---|---|---|---|
| `argocd-server` | 1 | **3** | 需同步设置 `ARGOCD_API_SERVER_REPLICAS` |
| `argocd-repo-server` | 1 | **3** | 注意 manifest 生成锁 |
| `argocd-application-controller` | 1 | **3** | StatefulSet，按 shard 分片 |
| `argocd-applicationset-controller` | 1 | 1 | 单实例即可 |
| `argocd-dex-server` | 1 | **1** | 内存数据库，多副本数据不一致 |
| `argocd-redis` | 1（Deployment） | **3 master + 3 sentinel + HAProxy** | 换成了独立的 redis-ha 子 chart |

## 2. 三条必须知道的硬约束

### 约束 1：Redis 只能是三个节点

上游原文：

> `argocd-redis` is pre-configured with the understanding of only three total redis servers/sentinels.

sentinel 数量在 HA chart 中**写死为 3**。想加到 5 个需要改 chart 模板并自行验证
sentinel 仲裁逻辑——不要在生产环境做这个实验。

### 约束 2：`argocd-dex-server` 不要多副本

上游明确警告：`argocd-dex-server` 使用**内存数据库**，
两个以上实例之间**数据可能不一致**。

推论：**登录态可能不均匀**——用户这次登录被路由到 dex-A，下次刷新被路由到 dex-B，
可能需要重新登录。这不是 bug，是内存库的固有行为。

**保持 1 副本。** 如果确实需要 HA dex，正确做法是**换成外部 OIDC 提供商**
（Keycloak / Okta / Entra ID / Google），把 dex 从架构里去掉。

### 约束 3：`argocd-server` 副本数与 `ARGOCD_API_SERVER_REPLICAS` 必须同步

上游 HA 文档说明：登录请求限流阈值 `ARGOCD_MAX_CONCURRENT_LOGIN_REQUESTS_COUNT`
会被**按 `ARGOCD_API_SERVER_REPLICAS` 的值平均分配**。

```yaml
# server Deployment
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: argocd-server
        env:
        - name: ARGOCD_API_SERVER_REPLICAS
          value: "3"        # ← 必须等于 replicas
        - name: ARGOCD_MAX_CONCURRENT_LOGIN_REQUESTS_COUNT
          value: "50"      # 每副本实际限额 = 50/3
```

**只改 `replicas` 不改环境变量**的后果：Argo CD 认为有 3 个副本，
把限额按 3 分配，但实际只有 1 个副本在服务 → 单副本承受 3 倍限流压力 → 
**登录被误判为超限而拒绝**。

## 3. application-controller 的分片

多副本的 controller 通过 **shard** 机制分摊 Application：

```yaml
kind: StatefulSet
metadata:
  name: argocd-application-controller
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: argocd-application-controller
        command:
        - argocd-application-controller
        - --status-processors
        - "$(ARGOCD_CONTROLLER_REPLICAS)"
        - --shard
        - "$(POD_NAME)"
```

- 每个副本按自己 Pod 名的哈希决定处理哪些 Application
- **副本数变化后，分片分布会变** → 部分 Application 会被"换"到另一个副本，
  短时间内状态同步延迟增加，属正常
- `ARGOCD_CONTROLLER_PROCESSES` 控制单副本内的并发进程数

### 3.1 repo-server 的单实例锁

`argocd-repo-server` 内部对 manifest 生成有互斥机制
（同一时间一个 repo-server 实例只处理一个 manifest 生成请求，
配合 `ARGOCD_REPO_SERVER_XXX` 系列参数调优）。

推论：**repo-server 副本数增加不等于 manifest 生成吞吐线性增加**，
它主要提升的是"不同仓库之间"和"不同请求之间"的并行度。
如果你的瓶颈是单个大仓库的 manifest 生成速度，加副本帮助有限，
应该调 `ARGOCD_REPO_SERVER_ALLOW_OUTSIDE_SIZE_LIMIT`、
`ARGOCD_REPO_SERVER_MAX_CONCURRENT_REPO_INDEXING` 等参数，
或改用 monorepo 拆分。

## 4. 部署方式

### 4.1 用上游 HA 清单

```bash
kubectl create namespace argocd
kubectl apply -n argocd -f \
  https://raw.githubusercontent.com/argoproj/argo-cd/master/manifests/ha/install.yaml

# 等待所有 Pod 就绪
kubectl -n argocd wait --for=condition=Available deployment --all --timeout=300s
kubectl -n argocd get pods
```

### 4.2 用官方 Helm Chart（推荐，可维护性更好）

```bash
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update

helm install argocd argo/argo-cd \
  --namespace argocd --create-namespace \
  --set global.domain=argocd.example.com \
  --set global.image.tag=v3.5.6 \
  --set controller.replicas=3 \
  --set server.replicas=3 \
  --set repoServer.replicas=3 \
  --set dex.replicas=1 \
  --set redis.enabled=true \
  --values examples/ha-values-override.yaml
```

覆盖示例见 [`examples/ha-values-override.yaml`](./examples/ha-values-override.yaml)。

### 4.3 验证

```bash
# ① 各组件副本数
kubectl -n argocd get deploy argocd-server argocd-repo-server argocd-dex-server -o custom-columns='NAME:.metadata.name,REPLICAS:.spec.replicas'
kubectl -n argocd get statefulset argocd-application-controller -o custom-columns='NAME:.metadata.name,REPLICAS:.spec.replicas'

# ② 副本数与 API_SERVER_REPLICAS 是否一致（约束 3）
kubectl -n argocd get deploy argocd-server -o jsonpath='{.spec.replicas}{"\n"}'
kubectl -n argocd get deploy argocd-server -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="ARGOCD_API_SERVER_REPLICAS")].value}{"\n"}'
# 两个数字必须相同

# ③ Redis HA 是否就绪
kubectl -n argocd get pods -l app.kubernetes.io/name=redis
kubectl -n argocd exec argocd-redis-0 -- redis-cli -p 26379 SENTINEL masters

# ④ 滚动更新不中断服务
kubectl -n argocd rollout restart deployment/argocd-server
kubectl -n argocd rollout status deployment/argocd-server --timeout=180s
```

## 5. 故障域设计

| 维度 | 建议 |
|---|---|
| **节点分布** | 依赖 PodAntiAffinity（官方清单已带 `preferredDuringSchedulingIgnoredDuringExecution`）。高要求时改成 `required` |
| **可用区** | 跨 zone 部署，但**注意 Redis sentinel 的仲裁**：3 节点跨 3 zone 时，一个 zone 挂掉剩 2 个，sentinel 仍能仲裁（2/3 多数存活）。可以接受 |
| **区域** | GKE 集群本身是区域级的（regional cluster）。zonal cluster 无跨 zone 能力 |
| **Argo CD 自身** | `argocd-server` 3 副本跨 zone；入口用 GKE Ingress + Cloud Armor 或 IAP |

**风险提示**：跨 3 个 zone 时，**Redis 3 master 分布在 3 个 zone**，
意味着 1 个 zone 整体故障 → 1/3 数据分片不可用。Redis Cluster 模式会继续服务
剩余 2/3 分片，但依赖该分片的功能受影响。评估是否值得。

## 6. 备份与恢复

### 6.1 备份什么（这是最容易搞错的地方）

**不备份 Redis。** Argo CD 的 Redis 是缓存，备份它没有意义。

真正的 source of truth 只有三处：

| 备份对象 | 内容 | 方式 |
|---|---|---|
| **Git** | 所有 Application / AppProject / ApplicationSet 的定义 | 本来就在 Git 里，天然有版本 |
| **`argocd-cm`** | 全局配置（URL、extensions、customizations） | `kubectl get cm argocd-cm -o yaml > argocd-cm.yaml` |
| **`argocd-rbac-cm`** | RBAC 策略 | `kubectl get cm argocd-rbac-cm -o yaml > argocd-rbac-cm.yaml` |
| **`argocd-secret`** | 仓库凭据、集群凭据、Webhook 密钥 | `kubectl get secret argocd-secret -o yaml > argocd-secret.yaml` ⚠️ 敏感 |
| **CRD 状态** | Application 的 sync history / health status | `argocd admin export` |

### 6.2 用 `argocd admin export` 导出全部 Argo CD 资源

上游 `docs/operator-manual/disaster_recovery.md` 的标准流程：

```bash
# 导出
docker run -v ~/.kube:/home/argocd/.kube --rm \
  quay.io/argoproj/argocd:v3.5.6 argocd admin export > backup.yaml

# 导入（灾难恢复）
docker run -i -v ~/.kube:/home/argocd/.kube --rm \
  quay.io/argoproj/argocd:v3.5.6 argocd admin import - < backup.yaml
```

### 6.3 两种导出模式（上游新特性）

上游文档明确区分了两种用途：

| 命令 | 是否含 `status` 字段 | 用途 |
|---|---|---|
| `argocd admin export` | **含** | 温备 / 灾难恢复：保留最后一次已知的 sync history 和 health 状态 |
| `argocd admin export --strip-status` | **不含** | 干净清单：可直接 `kubectl apply`，或用于播种新集群、存进 Git |

**语义要点**（上游原文）：

> `--strip-status` only affects the export. On update, `argocd admin import` only
> overwrites the live resource's status when the backup manifest actually contains
> a status field.

即：**导入一个 `--strip-status` 的备份，不会清空现有资源的 status**。
在已有 status 的资源上做 update 时，只有备份里带 status 才会覆盖。

### 6.4 恢复演练清单

```bash
# ① 演练前：记录当前状态
kubectl -n argocd get applications -n argocd -o name | wc -l
argocd app list --output wide

# ② 导出并检查内容
argocd admin export > /tmp/argocd-backup.yaml
grep -c '^kind: Application' /tmp/argocd-backup.yaml
grep -c '^kind: AppProject' /tmp/argocd-backup.yaml

# ③ 在测试集群恢复
kubectl create ns argocd-dr
docker run -i -v ~/.kube:/home/argocd/.kube --rm \
  quay.io/argoproj/argocd:v3.5.6 argocd admin import - < /tmp/argocd-backup.yaml

# ④ 验证恢复后的 Application 能正常同步
kubectl -n argocd-dr get applications
```

## 7. 容量规划参考

| 指标 | 单副本参考值 | 说明 |
|---|---|---|
| `ARGOCD_MAX_CONCURRENT_LOGIN_REQUESTS_COUNT` | 50 | **总**限额，按 API_SERVER_REPLICAS 平均分配 |
| `ARGOCD_GRPC_MAX_SIZE_MB` | 200 | gRPC 消息上限。大 manifest 或大 diff 时需要调高 |
| `server.glob.cache.size` | 10000 | 全局缓存条目数 |
| `ARGOCD_CONTROLLER_PROCESSES` | 视 CPU | 单副本内并发 reconcile 数 |
| `ARGOCD_REPO_SERVER_MAX_CONCURRENT_REPO_INDEXING` | 视内存 | repo-server 并发索引数 |

> 调大 `ARGOCD_GRPC_MAX_SIZE_MB` 会增加 server 内存占用。
> GKE 上 server 3 副本建议每副本至少 1 核 1Gi，manifest 复杂时给 2Gi+。
