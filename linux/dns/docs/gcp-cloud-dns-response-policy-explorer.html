*.team.caep.uk 范解析 → 链路 / Longest Suffix / Pod 出口分流

① 解析链路:Pod 发出 query 到 RP 返回 IP

VPC Resolver (169.254.254.254) 按 ① ② ③ ④ ⑤ 顺序匹配。RP 是 ②,在所有 Private Zone / Forwarding / Peering 之前。

② Longest Suffix Match:同一 RP 内谁优先命中

一个 RP 内多条 rule 同时存在时,按 selector 最长后缀命中。exact > wildcard;wildcard 内层级越深越优先。

③ Pod 内 Pod-to-Pod 通信:为什么必须用 *.svc.cluster.local

复用 *.team.caep.uk 在 Pod 内做服务发现,会被 RP 劫持到 GLB/ILB,绕一圈且 NetworkPolicy 失效。推荐 cluster.local 直连。

核心: RP 是"前置拦截器"

  • • 在所有 Private Zone / Forwarding / Peering 之前匹配
  • • 命中 localData → 直接返回,短路后续所有层
  • • 每个 VPC 只能 attach 一个 RP
  • • 仅支持 A / AAAA / CNAME (不允许 SOA / NS)
  • • behavior 当前只有 bypassResponsePolicy

Longest Suffix 自动排优先级

  • • exact match 比 wildcard 优先
  • • 同一后缀层级下,层级越深的 wildcard 越优先
  • • 方案 A (1 条 wildcard) + 方案 B (逐条 exact) 共存
  • • bypass 是"白名单"机制,比 wildcard 后缀长就放行
  • • 不需要手动排优先级 — longest suffix 自动裁决

关键陷阱 & 验证

  • • Pod 内复用 *.team.caep.uk → 被 RP 劫持,绕路 + 打破 NetworkPolicy
  • • 推荐 Pod 内用 *.svc.cluster.local (kube-dns 权威,不经过 RP)
  • • RP 改 IP 生效时间 = TTL (默认 300s);生产关键切换先调低 TTL
  • • 必须从 Pod 内 dig 验证,不要只在工作站上测
  • • cluster.local 后缀的查询完全旁路 RP,这是天然的"安全通道"
