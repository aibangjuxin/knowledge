## 0. TL;DR

### 三个最重要的结论（先看这个）

**结论 1 —— Dependabot 修不了你们的 alpine EOL 和镜像 OS 漏洞。**

官方生态矩阵实测：**`docker` / `helm` / `terraform` 的 "Security updates" 一栏是 ❌ Not supported。**
Dependabot 的 `docker` ecosystem 只做 **version updates**（升 base image 的 tag），**不做基于 CVE 的安全更新**。

```
你们的问题                                    Dependabot 能做吗
─────────────────────────────────────────────────────────────
alpine 3.21 EOL → 升到 3.24                   ✅ 能（docker version update，改 Dockerfile FROM）
镜像内 openssl 等 OS 包 CVE                   ❌ 不能（docker 无 security update）
Go modules 依赖 CVE                           ✅ 能（gomod 支持 security update）
Java/Maven/Gradle 依赖 CVE                    ✅ 能（maven/gradle 支持 security update）
Go stdlib / JRE 自身 CVE                      ❌ 不能（属 base image / toolchain）
应用代码 CWE                                   ❌ 不能（不是它的领域）
```

**结论 2 —— Dependabot 停在了"PR"，而你们的闭环需要"镜像级验证"。**

Dependabot 的产出 = **一个改好 manifest（+ lockfile + vendor）的 PR**。它**不构建镜像、不推 GAR、不调 Artifact Analysis、不验证漏洞是否真的消失**。这部分必须由你们自己的 CI 补上（见 §6.3，那里有完整的链、三个坑、和最小可用版本）。

**结论 3 —— GitHub 现在原生支持"把 Dependabot alert 分配给 AI agent 自动出修复 PR"。**

实测官方文档：

> *"When you assign an alert to an AI agent, the agent automatically creates a session and opens a draft pull request with a proposed fix."*
> 可分配给：**Copilot**（内置）或第三方 agent（**Codex、Claude** 等，需在仓库设置里启用）。
> 分配时还可以：加自定义 prompt、选模型、选自定义 agent。

这正好是你想要的"AI 自动修 CVE"，而且**有现成入口**。

### 建议的使用姿势

```
Dependabot            =  「发现 + 提 PR」的引擎（白嫖 GitHub 的漏洞库和生态解析）
你们自己的 CI/GAR 闭环  =  「构建 + 推镜像 + 扫镜像 + 验证 + 更新 manifest」的引擎
AI agent              =  「评审 + 处理 breaking change + 兜底修复」的脑子
```

## 1. Dependabot 是什么：三件不同的东西

很多团队把 Dependabot 当成一个"自动升级工具"，然后发现用错了地方。GitHub 官方把它拆成**三件独立开关**的东西：

| 产品 | 是什么 | 在哪开 | 产出 |
|---|---|---|---|
| **Dependabot alerts** | 扫描依赖图，对照 **GitHub Advisory Database (GHSA)** 找出有已知漏洞的依赖 | Settings → Advanced Security → Dependabot alerts | 一条条 alert（可分派、可 dismiss） |
| **Dependabot security updates** | 针对 alert **自动开 PR** 修到"最小含补丁的版本" | Settings → Advanced Security → Dependabot security updates | PR（链接到对应 alert） |
| **Dependabot version updates** | 定期检查有没有新版本，**即使没有漏洞也升** | `.github/dependabot.yml` | PR |

**关键差异：**

- **alerts 和 security updates 在 Settings 里开**（不在 `dependabot.yml` 里）；
- **version updates 在 `.github/dependabot.yml` 里开**；
- `dependabot.yml` **只能微调** security update 的 PR（labels / assignees / reviewers / 私有 registry / PR 数量上限），**不能控制"要不要为某个 alert 开 PR"**。

> 官方原文（实测）：
> *"There is no interaction between the settings specified in the dependabot.yml file and Dependabot security alerts, other than the fact that alerts will be closed when related pull requests generated by Dependabot for security updates are merged."*

**如果你们想"只对高危 alert 开 PR"**，官方给的路子是**关掉 security updates，改用 auto-triage rules**：

> *"If you prefer to customize which alerts Dependabot opens pull requests for, you should leave Dependabot security updates disabled and create an auto-triage rule."*

### 2.1 针对你们技术栈的三条解读

**① Go (`gomod`) —— 支持，但有一个坑**

- ✅ 版本更新、安全更新都支持；
- ✅ **vendor 目录自动识别**（官方原文：*"For Go modules, any vendored dependencies are automatically identified and maintained as if vendor was enabled"*）→ 你们的 `vendor/` 不用额外配置；
- ✅ 支持 `dependency-type: indirect`（**Go 是少数能更新间接依赖的生态之一**，见下）；
- ❌ **不支持 private registry**（表格里 "Private registries" 一列是 ❌）→ 如果你们用内部 GOPROXY / Artifactory 代理 Go module，Dependabot 拉不到，**需要额外配置**，见 §4.5。

**② Java —— Maven 直接可用，Gradle 有前提**

- Maven：官方明确 *"Dependabot doesn't run Maven but supports updates to pom.xml files."*（不跑 Maven，只改 pom.xml → **快，但不做真实的依赖解析**）
- Gradle：官方有一句很关键的话 ——

  > *"For Dependabot security updates, Gradle support is limited to manual uploads of the dependency graph data using the dependency submission API."*

  意思是：Gradle 的**依赖图**默认不容易自动生成，要靠 **Dependency Submission API 手动上传**才有 alert。
  并且手动上传时"所有传递依赖都会被上传"，而 **Dependabot 无法为传递依赖生成 security update**（它只在父依赖是显式声明的直接依赖时才开 PR）。

  → **如果你们用 Gradle，务必接上 Dependency Submission API**，否则 Gradle 这条线基本是瞎的。

**③ Docker / Helm —— 只能升版本，不能修 CVE**

这是最需要想清楚的一条：

- ✅ `docker` ecosystem 会更新 Dockerfile 里的 `FROM` 基础镜像 tag（**这正好能解决 alpine EOL**）；
- ❌ **不会**因为镜像里有 OS 包 CVE 而开 PR；
- ✅ **`docker` ecosystem 还能更新 Kubernetes manifest / Helm chart 里的 image tag**（官方原文：*"Dependabot can update Docker image tags in Kubernetes manifests. ... Kubernetes manifests can be Kubernetes Deployment YAML files or Helm charts."*）→ **这条对你们非常有用**，见 §6.2；
- ⚠️ **digest 固定的写法（`FROM alpine:3.24.3@sha256:...`）不在 Dependabot 的更新范围内** —— 它按 tag 的 SemVer 解析，digest 场景通常需要 Renovate。**⚠️ 需实测**（在你们仓库上放一个 digest-pinned 的 FROM 试一次）。

### 2.2 间接（传递）依赖能不能自动修？

官方实测数据 —— **这是各生态差异最大的地方**：

| 生态 | 能否为间接依赖开 PR |
|---|---|
| npm | ✅ 会升父依赖；如果只有这一条路，还会"移除父依赖已经不需要的子依赖" |
| NuGet（PackageReference） | ✅ 先升父依赖；没有兼容的父版本时，会**加一条直接引用把传递依赖钉到安全版本** |
| **其他所有生态（含 gomod、maven、gradle）** | ❌ *"Dependabot can't update an indirect or transitive dependency if doing so would also require updating the parent dependency."* |

**实际影响：** Go/Java 项目里，如果漏洞在一个三方库内部传递进来的依赖上，Dependabot 通常**开不出 PR**，只在 alert 上报错。这不是 bug，是设计——它避免乱改依赖图。

**解法：** 保持版本更新常态化（依赖不过时 → 漏洞出现时能简单升一个 patch 就解决）。官方建议原文：

> *"Stay up to date with the most recently released versions, for example, by enabling version updates. This increases the likelihood that a vulnerability in one dependency can be resolved by a simple upgrade that doesn't break the dependency graph."*

### 2.3 其他实测到的限制

- **Dependabot 只扫默认分支**；
- **只有经 GitHub 审核过的 advisory 才会产生 alert**；
- **新漏洞进入 GHSA 需要时间**，不是实时的；
- **Dependabot 不扫描已归档（archived）的仓库**；
- **GitHub Actions 的 alert 只对用 SemVer 版本号的 action 生效**，用 commit SHA 的不产生 alert；
- **Dependabot alerts 覆盖的是依赖图里的漏洞**，不是所有安全问题（官方原文：*"Alerts can't catch every security issue."*）。

## 3. 安装与启用（从零到跑起来）

### 3.1 前置条件

| 条件 | 说明 |
|---|---|
| 代码托管在 GitHub | Dependabot 是 GitHub 的功能。**GitLab / Gitea / 内网 GitLab 都不支持**（除非自建 `dependabot-core`，见 §7.3） |
| 仓库不是 archived | archived 仓库不扫 |
| 仓库有 manifest/lock 文件 | 没有可识别的 manifest，什么都不会发生 |
| **私有仓库：alerts 需要 GitHub Code Security / GHAS 许可** | 官方原文（分配 alert 部分）：*"Assigning alerts requires a license for GitHub Code Security or GitHub Advanced Security, including for public repositories."* → 私有仓库要开 alerts，得先有许可。**version updates 本身不需要许可** |
| 组织所有者开启相关设置 | 组织级可以统一开/关 |

> 你们现有仓库在 `github.com/aibangjuxin/*` → ✅ 平台匹配。

### 3.2 启用 Dependabot alerts（UI）

```
仓库 → Settings → "Security and quality" 侧边栏 → Advanced Security
  → "Dependabot alerts" 一行 → Enable
```

组织级批量开启：
```
Organization → Settings → Advanced Security → Dependabot alerts → Enable all
              （可选 "Enable by default for new repositories"）
```

**开启后行为（官方实测）：**
- 立即生成 dependency graph 并为已识别出的漏洞创建 alert；
- **首次开启不会把历史所有漏洞都通知一遍**，只通知"开启后新发现的"（避免邮件风暴）；
- 之后每当 GHSA 新增漏洞、或你的依赖图变化（推了新 commit）时重新扫描并告警。

**API 方式**（适合批量治理）：

```bash
gh api -X PUT repos/OWNER/REPO/vulnerability-alerts -H "Accept: application/vnd.github+json"
# 查询
gh api repos/OWNER/REPO/vulnerability-alerts
# 列出 alert
gh api "repos/OWNER/REPO/dependabot/alerts?state=open&per_page=100"
```

### 3.3 启用 Dependabot version updates

在仓库里新增 **`.github/dependabot.yml`**（**必须放在默认分支**，路径只能是 `.github/dependabot.yml` 或 `.github/dependabot.yaml`）：

```yaml
version: 2
updates:
  - package-ecosystem: "gomod"
    directory: "/"
    schedule:
      interval: "weekly"
```

**最小必填 5 个字段（官方实测）：**

| 字段 | 位置 | 作用 |
|---|---|---|
| `version` | 顶层 | 配置语法版本，**永远写 `2`** |
| `updates` | 顶层 | 各个生态的配置列表 |
| `package-ecosystem` | `updates` 下 | 要监控的包管理器 |
| `directories` / `directory` | 每个 ecosystem 下 | manifest 所在目录（相对仓库根） |
| `schedule.interval` | 每个 ecosystem 下 | 检查频率 |

### 3.4 启用 Dependabot security updates

```
仓库 → Settings → Advanced Security → "Dependabot security updates" → Enable
```

或用 REST API（实测端点存在）：

```bash
# 开启 vulnerability alerts（Dependabot alerts 的开关）
gh api -X PUT repos/OWNER/REPO/vulnerability-alerts

# 查询是否已开启（204 = 已开启，404 = 未开启）
gh api repos/OWNER/REPO/vulnerability-alerts

# 关闭
gh api -X DELETE repos/OWNER/REPO/vulnerability-alerts
```

> ⚠️ 注意别和 `private-vulnerability-reporting`（那是**私有漏洞报告** / 私密披露功能）搞混 —— 两者是完全不同的功能。

> ⚠️ **需实测**：私有仓库若没有 GHAS 许可，Security updates 这一项在 UI 里可能直接不可用。

### 3.5 验证是否生效

| 检查项 | 位置 / 命令 |
|---|---|
| alerts 是否开启 | 仓库 → Security and quality → Advanced Security |
| alert 列表 | 仓库 → Security and quality → Findings → Dependabot → Vulnerabilities |
| version update 是否在跑 | 仓库 → **Insights** 标签 → **Dependency Graph** → **Dependabot** 标签 |
| 最近的 job 日志 | Dependency Graph → Dependabot → 对应 manifest → **Recent update jobs** → view logs |
| 私有仓库访问权限 | 组织 Settings → Advanced Security → 允许 Dependabot 访问私有仓库 |

## 4. `dependabot.yml` 配置详解

### 4.1 官方完整选项清单（实测，共 22 项）

**必填**：`version` / `updates` / `package-ecosystem` / `directories`/`directory` / `schedule.interval`

**可选项**（括号内为官方实测的默认值或支持范围）：

| 选项 | 作用 | 关键默认值 / 备注 |
|---|---|---|
| `allow` | 精确指定要维护哪些依赖 | 与 `ignore` 配合；**同时匹配 allow 和 ignore 的 → 被 ignore** |
| `assignees` | PR 指派人 | 需有写权限 |
| `commit-message` | commit / PR 标题格式 | `prefix`（≤50 字符）、`prefix-development`、`include`（只支持 `scope`） |
| `cooldown` | 冷却期 | **默认 3 天，只对 version updates 生效，security updates 不受冷却期影响** |
| `directories` / `directory` | manifest 目录 | `directories` 支持 glob 和 `*`；`directory` 不支持 |
| `enable-beta-ecosystems` | — | 官方标注"当前未使用" |
| `groups` | 把多个依赖合并成一个 PR | ⭐ 强烈建议开，见 §4.3 |
| `ignore` | 忽略某些依赖/版本 | 见 §4.4 |
| `insecure-external-code-execution` | 允许执行 manifest 里的外部代码 | **仅 bundler / mix / pip**；`allow` |
| `labels` | PR 标签 | 默认有 `dependencies` + 生态标签 + SemVer 标签；`labels: []` 可全关 |
| `milestone` | PR 关联 milestone | 填数字 ID |
| `multi-ecosystem-groups` | 跨生态合并 PR | 2026 新增 |
| `open-pull-requests-limit` | version update 的 PR 上限 | **默认 5**；security update 的上限是**固定的 10，不可配** |
| `package-ecosystem` | 包管理器 | 见 §2 矩阵 |
| `pull-request-branch-name` | 分支名格式 | 默认 `dependabot/PACKAGE-MANAGER/DEPENDENCY`；可配 `separator`/`prefix`/`max-length`(20–244，默认 100)/`template`(≤200) |
| `rebase-strategy` | 是否自动 rebase | 默认开启；`disabled` 停止（**已开的 PR 会在 30 天内继续被 rebase**） |
| `registries` | 私有 registry | 顶层定义 + 各生态引用；每个 updates 块最多引用 100 个 |
| `schedule` | 频率 | `interval`: daily/weekly/monthly/quarterly/semiannually/yearly/**cron**；可配 `day`/`time`/`timezone`/`cronjob` |
| `target-branch` | 指定目标分支 | **只对 version updates 生效**；security updates 永远走默认分支 |
| `exclude-paths` | 排除路径 | glob 列表（2026 新增） |
| `vendor` | 维护 vendored 依赖 | **仅 bundler 和 gomod**；Go 实际上自动启用 |
| `versioning-strategy` | 改 manifest 的策略 | **仅 bundler/cargo/composer/helm/mix/npm/pip/pub/uv**；`auto`(默认)/`increase`/`increase-if-necessary`/`lockfile-only`/`widen` |

### 4.2 针对你们技术栈的推荐配置（可直接用）

```yaml
version: 2

# ---------- Go 服务 ----------
updates:
  - package-ecosystem: "gomod"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "Asia/Shanghai"
    # 全部 Go 依赖合并成一个 PR，避免 PR 洪水
    groups:
      go-deps:
        patterns: ["*"]
        update-types: ["minor", "patch"]
      go-major:
        patterns: ["*"]
        update-types: ["major"]
    open-pull-requests-limit: 5
    labels: ["dependencies", "go"]
    commit-message:
      prefix: "chore(deps)"

  # ---------- Java 服务 ----------
  - package-ecosystem: "maven"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      java-deps:
        patterns: ["*"]
        update-types: ["minor", "patch"]
    labels: ["dependencies", "java"]

  - package-ecosystem: "gradle"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      java-deps:
        patterns: ["*"]
        update-types: ["minor", "patch"]
    labels: ["dependencies", "java"]

  # ---------- 基础镜像（解决 alpine EOL 的主力）----------
  - package-ecosystem: "docker"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      base-images:
        patterns: ["*"]
    open-pull-requests-limit: 3
    labels: ["dependencies", "docker"]

  # ---------- K8s manifest / Helm 里的镜像 tag ----------
  - package-ecosystem: "docker"
    directory: "/k8s"          # 指向放 Deployment YAML 的目录
    schedule:
      interval: "weekly"

  - package-ecosystem: "helm"
    directory: "/charts"
    schedule:
      interval: "weekly"

  # ---------- GitHub Actions ----------
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
```

> **`groups` 的重要性**：Dependabot 默认是**一个依赖一个 PR**（实测原文：*"Open a single pull request for each dependency"*）。一个 200 个依赖的 Java 项目一周能刷出 100+ 个 PR —— 没人会看，等于没开。**分组是必配项，不是可选项。**
>
> **注意 `groups` 的两个坑：**
> 1. 一个依赖匹配多条规则时，**归入第一条匹配的规则**；
> 2. `groups` 里**默认只作用于 version updates**。要作用于 security updates，要显式写 `applies-to: security-updates`。

### 4.3 分组（groups）进阶

```yaml
groups:
  # 只针对安全更新分组
  security-critical:
    applies-to: security-updates
    patterns: ["*"]
    dependency-type: "production"     # 仅 bundler/composer/mix/maven/npm/pip
  # 跨目录按依赖名分组（monorepo）
  cross-dir:
    group-by: "dependency-name"        # 仅 version updates 生效
  # 排除某些依赖不进组
  go-deps:
    patterns: ["*"]
    exclude-patterns: ["github.com/xxx/internal-*"]
  # 按 SemVer 级别拆组
  patch-only:
    patterns: ["*"]
    update-types: ["patch"]
```

### 4.4 忽略策略（allow / ignore）

**默认行为（实测）：**
- version updates：manifest 里**显式声明**的依赖全部保持最新；
- security updates：**lock 文件里**定义的、有漏洞的依赖会被更新。

**写规则时注意：先 allow 再 ignore；同时命中 allow 和 ignore 的 → 被 ignore。**

```yaml
updates:
  - package-ecosystem: "maven"
    directory: "/"
    schedule:
      interval: "weekly"
    allow:
      - dependency-name: "org.springframework.boot:spring-boot-starter-web"   # Maven/Gradle 用 groupId:artifactId
      - dependency-name: "*"
        dependency-type: "production"
    ignore:
      # Maven 版本范围语法
      - dependency-name: "com.example:legacy-lib"
        versions: ["[1.0,)"]
      # Docker：填完整仓库名，不含 tag
      - dependency-name: "europe-west2-docker.pkg.dev/myproject/containers/dex"
      # 忽略所有 major 更新
      - dependency-name: "*"
        update-types: ["version-update:semver-major"]
```

> ⚠️ **强烈建议：不要在 `dependabot.yml` 里长期 ignore 漏洞依赖。**
> `ignore` 是**永久**的（直到你改配置），**没有到期时间**。这跟我们前一版方案里 "ignore 必须带 `fix-state` + 到期时间" 的原则冲突。
>
> **更好的做法**：用 **PR 评论命令**做临时忽略（见 §5.4）—— 那个是可追溯、可撤销的；或者在配置里加注释写明"谁批准的、什么时候复审"。
>
> **Maven/Gradle 的 `dependency-name` 格式必须是 `groupId:artifactId`**，写错了静默不生效。

### 4.5 私有 registry —— GAR 用 OIDC（重点）

**实测：Google Cloud Artifact Registry 是 GitHub 官方支持的 Dependabot 私有 registry 类型**，且**支持 OIDC（Workload Identity Federation）短时凭证**，不需要长期 SA key。

```yaml
version: 2
registries:
  my-gar:
    type: docker-registry
    url: https://REGION-docker.pkg.dev
    workload-identity-provider: projects/PROJECT-NUMBER/locations/global/workloadIdentityPools/POOL/providers/PROVIDER
    service-account: SA-NAME@PROJECT-ID.iam.gserviceaccount.com   # 可选
    audience: MY-AUDIENCE                                            # 可选

  my-artifactory:
    type: maven-repository
    url: https://acme.jfrog.io/artifactory/my-maven-registry
    username: octocat
    password: ${{ secrets.MY_ARTIFACTORY_PASSWORD }}

updates:
  - package-ecosystem: "docker"
    directory: "/"
    registries: "*"        # 或 "my-gar"
    schedule:
      interval: "weekly"

  - package-ecosystem: "maven"
    directory: "/"
    registries: "my-artifactory"
    schedule:
      interval: "weekly"
```

**关键要点（实测）：**

1. **`registries` 必须在顶层 `dependabot.yml` 声明**，光写在 `.npmrc` / `nuget.config` 里**不行**（那样 Dependabot 的网络出口不���许访问该主机）；
2. **即使 registry 允许匿名访问，也要声明**（声明的作用是"放行 egress"）；
3. 私有 registry 一旦配置，**外部代码执行默认被关闭**（安全默认），某些 version update 会失败 —— 需要时开 `insecure-external-code-execution: allow`（**仅 bundler/mix/pip**，且有被投毒包窃取凭证的风险）；
4. **Go modules 不支持 private registry**（§2.1）。如果你们用内部 GOPROXY：⚠️ 需实测 —— 大概率需要走 self-hosted runner（§5.5）或干脆用 Renovate；
5. **组织级也可以配 registry**（Settings → Advanced Security），支持 Token / 用户名密码 / OIDC，**组织级配置对全组织生效，比逐仓库配更省事**。

### 4.6 冷却期（cooldown）—— 控制"刚发布的版本"的干扰

```yaml
cooldown:
  default-days: 7
  semver-major-days: 30
  semver-minor-days: 14
  semver-patch-days: 3
  include: ["*"]
  exclude: ["github.com/aibangjuxin/*"]   # 内部包不等冷却
```

**实测要点：**
- **默认就有 3 天冷却**（version updates），写不写都有；
- **冷却期不作用于 security updates** → CVE 修复不会被延迟（这正是你想要的）；
- `exclude` 优先级高于 `include`；
- 没定义 `semver-*-days` 时用 `default-days` 兜底；
- `include` / `exclude` 最多各 150 项。

## 5. 在 CI 里配合 Dependabot 使用

### 5.1 dependency-review-action —— PR 门禁（强烈建议第一个装）

作用：**在 PR 阶段就拦住"新引入的漏洞依赖"**，而不是等合并后才发现。

```yaml
# .github/workflows/dependency-review.yml
name: 'Dependency Review'
on: [pull_request]
permissions:
  contents: read
jobs:
  dependency-review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/dependency-review-action@v4
        with:
          fail-on-severity: high          # 只在 high/critical 时失败
          # deny-licenses:                 # 可同时做 license 门禁
          #   - GPL-3.0
          # comment-summary-in-pr: on-failure
```

> **注意**：dependency review 是看 **PR 的依赖 diff**，比"扫描整个仓库"精确得多 —— 能避免"仓库里本来就有 100 个漏洞，导致 PR 永远过不了"这种经典困境。
> 官方还提到 GHEC + GitHub Code Security 可以做**企业级 license 策略**（集中管理 + ruleset 强制）。

### 5.2 ⚠️ Dependabot 触发的 workflow 的权限限制（最大的坑）

**官方实测原文：**

> *"For workflows initiated by Dependabot (`github.actor == 'dependabot[bot]'`) using the `pull_request`, `pull_request_review`, `pull_request_review_comment`, `push`, `create`, `deployment`, and `deployment_status` events, these restrictions apply:*
> - *GITHUB_TOKEN has **read-only permissions** by default.*
> - *Secrets are populated from **Dependabot secrets**. GitHub Actions secrets are not available."*

**这对你们的直接后果：**

Dependabot PR 触发的 CI **拿不到** `GCP_SERVICE_ACCOUNT_KEY` 这类 Actions secret → **没法直接推 GAR**。

**三个解法：**

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **A. OIDC（推荐）** | 用 Workload Identity Federation，`permissions: id-token: write` 换短时 GCP 凭证，不需要静态 key | 最安全；**需确认 `id-token: write` 在 Dependabot 触发的 workflow 里可用** ⚠️ 需实测 |
| **B. Dependabot secrets** | 把必要的 secret 配成 **Dependabot secrets**（组织/仓库 Settings → Secrets → Dependabot secrets），Dependabot 触发的 workflow 能读到 | 官方明确支持；但仍是长期凭证 |
| **C. 不让 Dependabot 触发构建** | CI 跳过 `dependabot[bot]` 的 PR 构建，推 GAR 交给合并后的 `main` 分支流水线 | **最简单、最稳**，推荐做默认 |

```yaml
# 方案 C 的写法：Dependabot 的 PR 只跑测试，不推镜像
on:
  pull_request:
    branches: [main]
jobs:
  build:
    if: github.actor != 'dependabot[bot]'      # ← 关键
    runs-on: ubuntu-latest
    steps: [...]
```

> **推荐组合**：C 做默认（Dependabot PR 只验证不发布），A 用于"我们确实想让 bot PR 直接进 staging"的场景。

### 5.3 自定义 PR 外观（让 PR 更容易被评审）

```yaml
labels: ["dependencies", "go", "auto-review"]
assignees: ["your-team"]
reviewers: ["your-team"]
commit-message:
  prefix: "chore(deps)"
  prefix-development: "chore(deps-dev)"
  include: "scope"
pull-request-branch-name:
  separator: "-"
  prefix: "deps"
  max-length: 60
```

**Dependabot 自己会签 commit**（官方实测：*"Dependabot signs its own commits by default, even if commit signing is not a requirement for the repository."*）→ 你们仓库的"必须 sign-off"策略不会挡住它。

### 5.4 PR 评论命令 —— 最好用的 triage 工具

在 Dependabot 的 PR 里留言（实测完整清单）：

| 命令 | 作用 |
|---|---|
| `@dependabot rebase` | 重新 rebase 到最新 base |
| `@dependabot recreate` | 重建 PR（丢弃你对 PR 的手工修改） |
| `@dependabot ignore this dependency` | 关闭 PR，且以后不再为这个依赖开 PR |
| `@dependabot ignore this major version` | 忽略该依赖的大版本更新 |
| `@dependabot ignore this minor version` | 忽略小版本 |
| `@dependabot ignore this patch version` | 忽略补丁版本 |
| `@dependabot show DEPENDENCY_NAME ignore conditions` | 查这个依赖当前所有 ignore 条件（返回表格） |
| `@dependabot ignore DEPENDENCY_NAME`（分组 PR） | 忽略分组 PR 里的某个依赖 |

> **用法建议**：这比在 `dependabot.yml` 里写 `ignore` 好，因为**每一次忽略都会在 PR 历史里留下可审计的记录**（谁、什么时候、为什么）。这正好解决了 §4.4 提到的"永久 ignore 没有到期时间"的问题。

### 5.5 self-hosted runner —— 当 registry 在内网时

**官方实测要求：**

| 类别 | 要求 |
|---|---|
| 系统 | Linux + x64 + 装了 Docker（推荐 rootless）；**一台 2C8G 机器成功跑过 20 个并发 runner** |
| Docker | runner 用户需免 root 访问 Docker；>14 个并发 runner 时要调 `daemon.json` 的 `default-address-pools` |
| 网络 | 需能访问公网、GitHub.com、以及所有内部 registry；**必须放行 `dependabot-actions.githubapp.com`**（否则 security update job 会失败）；要限制 runner VM 对内网的访问面 |
| 证书 | 自签证书要装到 runner 上**并且配到 Node.js**（actions 是 JS 写的，不读 OS 证书库） |

> **对你们的现实意义**：如果内部 Maven / Go proxy 只能内网访问，Dependabot 的公网 runner 就跑不了 → 必须上 self-hosted runner，或者换 Renovate（可自托管在你们自己的网络里）。

## 6. 接入你们的 GCP / GAR / GKE 闭环

> **核心认知：Dependabot 只负责第 1 步（改 manifest），第 2–5 步是你们的活。**

### 6.1 完整闭环图

```
  ①依赖图 + GHSA
        │
        ▼
  ②Dependabot alert ◄─────────────────────────────┐
        │                                        │
        ├──► ③ Dependabot security update PR ─────┤（同一份改动）
        │         (改 go.mod / pom.xml / FROM)    │
        │              │                          │
        │              ▼                          │
        │    ④ 你们的 CI：                         │
        │       ├ build 镜像                      │
        │       ├ test / smoke                    │
        │       ├ push → GAR (staging tag)        │
        │       ├ gcloud artifacts docker images scan --remote
        │       ├ 差分 baseline vs candidate      │
        │       └ 门禁：新漏洞 > 0 → 拒            │
        │              │                          │
        │              ▼                          │
        │    ⑤ 合并 → main 流水线 → release digest│
        │              │                          │
        │              ▼                          │
        │    ⑥ K8s manifest 换 digest → 灰度      │
        │              │                          │
        └──────────────┴────── SCC finding 关闭 ◄──┘
```

### 6.2 Dependabot 能帮你做的两件"镜像相关"的事

**① 更新 Dockerfile 的 base image tag** —— 解决 alpine EOL 的主力：

```dockerfile
# Dependabot 会把这一行改成 alpine:3.24.x（前提：仓库里只有这一处 FROM，
# 且 Dockerfile 在被配置的 directory 下）
FROM alpine:3.24.3@sha256:be26... AS stager
```

⚠️ **需实测**：
- digest 固定的 `FROM` 是否会被更新（大概率不会，Dependabot 按 tag 的 SemVer 解析）；
- **多阶段 Dockerfile 里多个 `FROM`** 会被怎样处理；
- **`ARG BASE_IMAGE=alpine` 这种间接写法**（你们的 dex 就是这种！）**大概率抓不到** —— Dependabot 解析不了 build arg 的值。

> 👉 **你们的 dex 镜像正好踩在这个坑上**：`ARG BASE_IMAGE=alpine` + `FROM $BASE_IMAGE`，Dependabot 的 docker ecosystem 很可能**完全看不到** alpine 这个依赖。
> **解法**：把 base image 显式化，例如在 Dockerfile 里同时保留一行注释形式的依赖声明，或改用 Renovate（支持 `ARG` 解析），或在 `dependabot.yml` 里对 `docker` 生态加 `allow`/`ignore` 配合定期巡检。

**② 更新 K8s manifest / Helm chart 里的 image tag**（官方实测支持）：

```yaml
# dependabot.yml
updates:
  - package-ecosystem: "docker"
    directory: "/k8s"     # ← 指向放 Deployment YAML 的目录
    schedule:
      interval: "weekly"
```

它会直接改 `spec.template.spec.containers[0].image` 里的 tag。
⚠️ **但你们用的是 digest 固定** → digest 场景仍然不被覆盖，需要 Renovate 或自建。

### 6.3 Dependabot 触发的 PR → 构建 → 推 GAR 的正确姿势

#### 6.3.0 先把认知对齐：Dependabot 的产出边界

这是整章的前提，先说清楚：

> **Dependabot 的产出 = 一个改好 manifest 的 PR。它不构建镜像、不推 GAR、不调 Artifact Analysis、不验证漏洞是否真的消失。**
> 这一步之后的所有事情，都必须由你们自己的 CI 补上。

**它到底改了什么（不只是"配置文件"，是三层）：**

| 生态 | Dependabot 实际改动的文件 |
|---|---|
| `gomod` | `go.mod` + `go.sum` + **`vendor/` 目录（自动识别，无需配 `vendor: true`）** |
| `maven` | `pom.xml`（官方明说"不跑 Maven，只改 pom.xml"） |
| `gradle` | `build.gradle` / `build.gradle.kts` / `libs.versions.toml` / `gradle.lockfile` |
| `npm` | `package.json` + `package-lock.json` |
| `docker` | Dockerfile 的 `FROM` 行 **+ K8s manifest / Helm chart 里的 image tag** |
| `github-actions` | `.github/workflows/*.yml` 里的 action 版本 |

> ⚠️ **Go vendor 化的坑**：如果你们的 Go 服务是 vendor 化的，Dependabot PR 的 diff 会包含整个 `vendor/` 目录 → 评审体验很差。务必开 `groups`（§4.3）把它合并成单个 PR。

**它验证了什么 vs 没验证什么 —— 这是理解 CI 要补哪一段的关键：**

| 环节 | Dependabot 做了？ | 说明 |
|---|---|---|
| 依赖图能解析 | ✅ | 算出新 lockfile，保证升级不会解析失败 |
| 应用能编译 | ❌ | |
| 应用能跑（单测/冒烟） | ❌ | |
| 镜像能构建 | ❌ | |
| **漏洞在最终镜像里真的消失** | ❌ | |
| **没引入新漏洞** | ❌ | |
| 镜像可部署（推 GAR / 换 K8s digest） | ❌ | |

> **一句话：Dependabot 保证的是"依赖图层面正确"，不是"运行时正确"，更不是"安全目标达成"。**

#### 6.3.1 你们要补的那条链

```
Dependabot PR
 │
   ├─▶ CI：build → test → push 到 GAR 临时 tag
   │        → gcloud artifacts docker images scan <新digest> --remote --location=europe
   │        → 轮询 get-operation 等扫描完成
   │        → 差分：新 digest 的 finding 集合 vs 旧 release digest 的 finding 集合
   │        → 门禁：目标 CVE 消失 ✅ 且 新增 finding == 0 ✅
   │
   └─▶ 通过 → 打标签 "verified" → 人工评审 → 合并
              │
              └─▶ main 流水线：构建 release digest → **再扫一次** → 更新 K8s manifest digest → 灰度
```

#### 6.3.2 三个会咬人的坑

**坑 1：digest 不一致 —— 验证的对象 ≠ 部署的对象**

最常见的翻车：PR 阶段构建验证的是 digest A，合并后 main 流水线重建产出 digest B，部署的是 B。**你验证过的和你部署的不是同一个东西。**

最稳的解法不是想办法让它们一致，而是接受"**验证两次**"，但守住一条不变式：

> **不变式：每一个被部署到生产的 digest，都必须有一条 Artifact Analysis 扫描记录，且该记录里目标 finding 不存在。**

| 阶段 | 验证什么 | 基线是谁 |
|---|---|---|
| PR 阶段 | "这个改动逻辑上是对的" | 当前 release digest |
| main 阶段 | "最终产物是干净的" | 上一个 release digest |

两段用**同一套差分代码**，只是基线不同。这样既不追求 digest 相同，又能保证不变式成立。

**坑 2：Dependabot PR 触发的 workflow 拿不到 secrets**

`GITHUB_TOKEN` 只读 + Actions secrets 不可用（官方实测，见 §5.2）→ **推 GAR 需要 GCP 凭证的那一步会失败**。

推荐默认做法：**Dependabot PR 只跑 test + 验证扫描到临时 tag，不推 release tag；推 release 交给合并后的 main 流水线。**
需要 GCP 凭证的地方用 OIDC（`id-token: write`）而不是静态 SA key。

**坑 3：扫描失败 ≠ 没问题**

扫描超时、DB 降级、扫描器报错 —— 这些情况下**不能**判定成"没有新增漏洞"。
必须 **fail-closed**：扫不出来 = 未验证 = 不许合并。
这条一旦松了，整条链就开始产出假绿灯（和 `shipyard` 的 sentinel 机制是同一个道理，见 [how-to-autofix-cve.md](./how-to-autofix-cve.md) §4.1）。

#### 6.3.3 最小可用版本（建议第一版就做这个）

别一上来就做全套。**第一版只做一件事**：

1. Dependabot PR 触发 → build → push 到 GAR 的 `cve-check` 临时 tag
2. 扫描 → **只检查一件事**：这个 PR 声称要修的那条 CVE，在新镜像里**消失**了吗
3. 没消失 / 扫描失败 → 在 PR 上留评论说明，不合并

**先不加"新漏洞差分"**（因为基线扫描要额外跑一次，成本翻倍），跑两周看看真实数据再补上。

> 这样你有了一个**低风险、可回滚、信号明确**的第一版：
> Dependabot 负责改代码，你们负责判断"改完到底行不行"。

### 6.4 GAR 权限怎么给 Dependabot

如果 Dependabot 需要读你们私有 GAR 里的镜像（比如 `docker` ecosystem 要解析 tag），按 §4.5 配 OIDC：

```yaml
registries:
  my-gar:
    type: docker-registry
    url: https://europe-west2-docker.pkg.dev
    workload-identity-provider: projects/PROJECT-NUMBER/locations/global/workloadIdentityPools/POOL/providers/PROVIDER
    service-account: dep-bot@myproject.iam.gserviceaccount.com
```

需要做的事：
1. 在 GCP 建一个 Workload Identity Pool + Provider，**信任 GitHub 的 OIDC issuer**（`https://token.actions.githubusercontent.com`）；
2. 属性条件里限定 `repository`（例如 `repo:aibangjuxin/myrepo`），别开成通配；
3. 映射到 SA，**只授予 `artifactregistry.reader`**（不要给 writer）；
4. 把 provider 路径填进 `dependabot.yml`。

> ⚠️ **需实测**：Dependabot 用 OIDC 时，`workload-identity-provider` 是否需要同时在**组织级**配置里声明（组织级支持 OIDC，仓库级也支持 —— 官方两处都提到了）。

### 6.5 和 SCC / Artifact Analysis 的分工

| 工具 | 覆盖 | 盲区 |
|---|---|---|
| **Dependabot alerts** | **源码层**依赖（Go modules、Java、npm…），对照 GHSA | **看不到镜像里的 OS 包**；看不到 base image EOL；看不到 Go stdlib / JRE 自身 |
| **Artifact Analysis** | **镜像层**：OS 包 + 语言依赖（GO/MAVEN/NPM…） | 不知道"哪个源码仓库对应这个镜像" |
| **SCC** | 汇总 + 影响面 + 状态流转 | 不产生新数据 |

**结论：两者互补，必须同时用。**
Dependabot 覆盖了 Artifact Analysis 覆盖不到的一半（因为 Artifact Analysis 只能看到镜像里实际存在的依赖，而**被 build 阶段排除掉的依赖、间接依赖图、以及源码里已声明但镜像里没有的依赖**，两边视野不同）。

## 7. AI + Dependabot（你最关心的部分）

### 7.1 方案 A：GitHub 原生 —— 把 alert 分配给 AI agent

**官方实测流程（2026 新能力）：**

```
仓库 → Security and quality → Findings → Dependabot → Vulnerabilities
   → 点开某个 alert
   → 右侧 "Assignees" 下拉 → 选 AI agent（或直接点 "Assign to Agent"）
       ├─ 可选：加自定义 prompt（补充修复上下文）
       ├─ 可选：换一个仓库
       ├─ 可选：选 AI 模型
       └─ 可选：选你自己配置的 custom agent（推荐用于专门任务）
```

**效果（官方原文）：**

> *"When you assign an alert to an AI agent, the agent automatically creates a session and opens a **draft pull request** with a proposed fix. If the agent can't generate a fix, it remains as an assignee of the alert. You can click View Session on the alert timeline to review the agent's log and understand why no pull request was created. **Only a user can remove the agent as an assignee.**"*

**可用的 agent（官方实测）：**
- **Copilot**（GitHub 内置）；
- **第三方 agent：Codex、Claude 等**（需在仓库设置里启用）。

**前提条件：**
- 需要 **GitHub Code Security 或 GitHub Advanced Security** 许可（公开仓库也要）；
- Agent 只能开 **draft PR**，**不能自动合并**（这正符合我们的安全原则）。

**这条路径的价值评估：**

| 维度 | 评价 |
|---|---|
| 覆盖范围 | 只覆盖 **Dependabot alerts 能发现的**（即源码依赖），**不覆盖 OS/base image EOL** |
| 适合你们的 T3（语言依赖 CVE） | ⭐⭐⭐ 非常合适 |
| 适合你们的 T1/T2（OS 层） | ❌ 完全不覆盖 |
| 质量 | ⚠️ 未知，**建议先在 1–2 个低风险仓库试点**，人工评估 draft PR 的可用率 |
| 与我们自建方案的关系 | **互补**：它管源码依赖，我们的 `gcp-cve-fix` 管镜像级验证和 OS 层 |

> **注意 agent 分配不会覆盖 Dependabot 自己的 security update PR** —— 两条路会同时产生 PR（一个是 Dependabot 的机械升级，一个是 agent 的智能修复）。**需要用 `groups` / `ignore` 规则避免重复劳动**，或者干脆对某些仓库只开一条路。

### 7.2 方案 B：自建 —— Dependabot PR 喂给 AI 评审

```
Dependabot PR
   │
   ├─ CI 跑测试（失败 → 直接 close，AI 都不用叫）
   │
   └─ 测试通过 → 调 AI（Claude Code / Codex / OpenCode + skill）
         ├─ 读 PR diff
         ├─ 读 changelog / release notes
         ├─ grep 真实代码调用点，判断 API 破坏
         ├─ 产出结构化结论：{breaking: bool, risk: low|mid|high, recommendation: approve|review|reject}
         └─ 结论为 approve → 打标签 / 自动 approve（不是自动 merge）
```

**这条路的价值：** 它补的是 Dependabot 完全没有的能力 —— **判断这次升级会不会炸**。

刚好我们上一份文档里评估过的 `vtmocanu/skills/upgrade-advisor`（读 changelog + grep 代码调用点 → 输出 safe/stay-put/blocked 判定）就是干这个的。

> ⚠️ **别让 AI 自动 merge。** 官方给 agent 的权限也只是开 draft PR。同理，你的 AI 也应该只到 "approve + 打标签" 为止，合并走人。

### 7.3 方案 C：Dependabot CLI —— 自托管跑（不依赖 GitHub 服务）

**官方开源 CLI：<https://github.com/dependabot/cli>**

```bash
# 安装（三选一）
brew install dependabot
go install github.com/dependabot/cli/cmd/dependabot@latest
# 或从 releases 下预编译二进制

# 跑一次更新任务（需要 Docker）
export LOCAL_GITHUB_ACCESS_TOKEN=ghp_xxx        # 访问私有仓库/包用
dependabot update go_modules aibangjuxin/myrepo
dependabot update maven        aibangjuxin/myrepo -d /service
```

**实测的关键特性：**

| 特性 | 说明 |
|---|---|
| **默认不创建 PR** | 官方原文：*"This does not create PRs, but outputs data that could be used to create PRs."* → 输出结构化数据，PR 由你自己开（示例见 `dependabot/example-cli-usage`） |
| 支持的 provider | GitHub / GitHub Enterprise / **Azure DevOps / GitLab / Bitbucket / AWS CodeCommit** |
| 完整 job 描述文件 | `dependabot update -f job.yaml`，可指定 `security-advisories`、`security-updates-only: true`、registry 凭证等 |
| 镜像签名校验 | 默认**强制校验** updater / proxy 镜像的 GitHub build attestation（SLSA provenance + Cosign 签名），**校验失败直接中止**。这个安全默认值很好，别用 `--skip-image-verification` 绕过 |

**什么时候考虑自托管 CLI：**
- 代码不在 GitHub（GitLab / 内网）；
- 想要在**自己的 CI 里**跑 Dependabot，产出结构化结果后接到你自己的流水线（而不是 GitHub 的 PR 流程）；
- 需要控制"扫哪些仓库、什么节奏"。

### 7.4 选型决策表：Dependabot vs shipyard cve-fix vs 自建

| 你的需求 | 用什么 |
|---|---|
| Go 依赖 CVE，自动开 PR | **Dependabot**（`gomod` 支持 security update + vendor 自动识别）✅ 更简单 |
| Go 依赖 CVE，需要"改完自动验证 + 回滚 + 拒绝引入新 CVE" | **shipyard cve-fix**（它有 rescan gate + 回滚 + ignore 过期机制）|
| Java 依赖 CVE | **Dependabot**（maven/gradle 支持）+ Renovate 兜底 |
| **base image EOL / OS 层 CVE** | **都不行** → 自建（`gcp-cve-fix`，见上一份文档） |
| **镜像级验证**（推 GAR → 扫 → 差分） | **自建** → 这就是我们的核心增量 |
| 判断升级会不会破坏 API | `upgrade-advisor` skill / AI agent |
| 让 AI 自动提修复 PR | GitHub 原生「alert → Assign to Agent」 |

> **一句话**：
> **Dependabot 是"依赖层"的免费引擎，shipyard cve-fix 是"Go 依赖层"的深度引擎，我们自建的是"镜像层"的引擎。三者互补，不是替代。**

## 8. 常见问题与排查

### 8.1 Dependabot 报错速查（官方实测清单）

| 报错 | 原因 | 处理 |
|---|---|---|
| `Dependabot cannot update DEPENDENCY to a non-vulnerable version` | 升到安全版本会破坏依赖图 | **保持版本更新常态化**，让依赖不过时；或手动升父依赖 |
| `Dependabot cannot open any more pull requests` | 达到 PR 上限 | version updates 默认 5（可配 `open-pull-requests-limit`）；**security updates 上限固定 10，不可配** |
| `Dependabot tries to update dependencies without an alert` | 在更新显式声明的传递依赖 | 正常现象 |
| `No security update is needed as DEPENDENCY is no longer vulnerable` | 依赖图数据陈旧 | 手动刷新依赖图 / 检查实际版本 |
| `Dependabot timed out during its update` | 仓库太大（几百个 package.json 的 monorepo） | 拆分成多个 `directories` 配置；用 `groups` 减负 |
| `Cannot update to the required version as there is already an open pull request` | 已有开到最新版的 PR | 先合/关掉那个 PR，再手动触发新的 security update PR |

### 8.2 "alert 没有关联的 PR" 的三个原因（官方实测）

1. 仓库没开 Dependabot security updates；
2. **该 alert 是间接/传递依赖，且没有显式出现在 lock 文件里**；
3. 有错误挡住了 PR 的创建（错误详情在 alert 详情页）。

### 8.3 其他排查入口

| 问题 | 去哪看 |
|---|---|
| version update 的 job 失败 | Insights → Dependency Graph → Dependabot → 对应 manifest → **Recent update jobs** → view logs |
| security update 被挡 | Security and quality → Findings → Dependabot → 点开 alert（有错误信息） |
| 配置写错了 | 提交 `dependabot.yml` 后 GitHub 会直接在 PR 里提示配置错误 |
| 内网 registry 连不上 | 需 self-hosted runner；确认放行 `dependabot-actions.githubapp.com` |
| 自签证书报错 | 证书装到 runner **并配到 Node.js** |
| 私有 registry 连不上 | 必须在顶层 `dependabot.yml` 声明 `registries`（只写 `.npmrc` 无效）|

### 8.4 Dependabot 停止工作

官方有专门的"updates stopped"文档：仓库维护者长期不处理 Dependabot 的 PR 时，Dependabot 会**自动暂停**并通知。
**解法：** 定期处理或 close 掉积压的 PR（`@dependabot recreate` 可以重建）。

## 9. 成本与许可

| 项目 | 免费？ | 说明 |
|---|---|---|
| Dependabot **version updates** | ✅ 免费 | 所有仓库（含私有）都可用 |
| Dependabot **alerts**（公开仓库） | ✅ 免费 | |
| Dependabot **alerts**（私有仓库） | ⚠️ 需 **GitHub Code Security / GHAS** 许可 | 官方在"分配 alert"处明确要求许可（含公开仓库） |
| Dependabot **security updates** | ⚠️ 依赖 alerts 的许可条件 | |

| self-hosted runner | ✅ 免费（但要自己出机器） | |

> **成本建议**：先确认你们组织有没有 GitHub Code Security / GHAS 许可。**如果没有，私有仓库的 Dependabot alerts 和 agent 自动修复都用不了** —— 那就直接走"Dependabot version updates（免费）+ 自建 gcp-cve-fix"这条路，别在许可上耗时间。

## 10. 落地清单（建议顺序）

### 第 1 步（半天，零风险）：先摸清现状

```bash
# 列出组织下所有仓库 + 是否有 dependabot.yml + 是否开了 alerts
gh repo list aibangjuxin --limit 100 --json name,visibility,isArchived \
  | jq -r '.[] | "\(.visibility)\t\(.name)"'

# 查某个仓库的漏洞告警
gh api "repos/aibangjuxin/REPO/dependabot/alerts?state=open&per_page=100" \
  | jq -r '.[] | "\(.security_advisory.severity)\t\(.dependency.package.ecosystem)\t\(.dependency.package.name)\t\(.security_advisory.vulnerable_version_range)"'
```

### 第 2 步（1 天）：给 1 个低风险 Go 仓库开试点

1. 仓库 → Advanced Security → 开 **Dependabot alerts**（如果没许可就跳过这步）；
2. 加 `.github/dependabot.yml`，**只开 `gomod` + `docker` 两个生态**，都配 `groups`；
3. 观察一周：PR 数量、PR 质量、有没有误报。

### 第 3 步（1 天）：验证 docker ecosystem 对你们 dex 的效果

**重点验证 `ARG BASE_IMAGE=alpine` 这种写法 Dependabot 能不能抓到**（我判断大概率抓不到 —— 这决定了你们要不要用 Renovate）。

### 第 4 步（半天）：接上镜像级验证

给 Dependabot PR 的 CI 加上 §6.3 的扫描 + 差分门禁（同时按 §5.2 方案 C 让 Dependabot PR 不推 release 镜像）。

### 第 5 步（可选）：试 AI agent 自动修复

在 1 个仓库里，把 2–3 条 Dependabot alert 分配给 Codex / Claude，人工评估 draft PR 的可用率。

### 第 6 步（如果上面几步都跑通）：上 self-hosted runner 或评估 Renovate

处理内网 registry / Go private registry 的缺口。
