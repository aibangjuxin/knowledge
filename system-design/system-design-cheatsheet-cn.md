## 1. 基础概念

| # | 支柱 | 定义 |
|---|---|---|
| 1.1 | **可扩展性（Scalability）** | 系统通过增加资源来应对增长的能力。 |
| 1.2 | **可靠性（Reliability）** | 即使发生故障，系统仍能正确工作。 |
| 1.3 | **可用性（Availability）** | 需要的时候系统处于运行状态。 |
| 1.4 | **可维护性（Maintainability）** | 便于更新、修复和演进系统。 |
| 1.5 | **性能（Performance）** | 系统响应快，能高效处理负载。 |

**扩展三定律（Scaling Law of 3）**（经验性启发，不是定理）：

> 流量每增长 3 倍，大约需要增加 2 倍的资源，
> 因为总有一部分流量属于"长尾"，它并不随头部流量线性增长。

## 2. CAP 定理

三个圆的韦恩图：

- **一致性（Consistency）** — 所有节点在同一时刻看到相同的数据。
- **可用性（Availability）** — 系统始终保持可用。
- **分区容错性（Partition Tolerance）** — 即使发生网络分区，系统依然能工作。

> **三者只能同时保证两个。**

**工程实践中的正确理解（能过设计评审的那种）：**

| 场景 | 你得到 | 你牺牲 | 典型选择 |
|---|---|---|---|
| 发生分区 | **CP** 或 **AP** —— 必须放弃一个 | 另一个 | 按操作区分：读可以 AP，写通常 CP |
| 没有分区 | **CA** 完全可行 | 无 | 一致性此时是"免费"的（直到分区出现） |

多数生产系统是**写路径 CP、读路径 AP**：写需要线性一致性，
读可以返回略微陈旧的副本，以换取更快、更高的可用性。

## 3. PACELC

- 如果发生 **P**artition（分区，P），选择 **A**vailability（可用性，A）而不是 **C**onsistency（一致性，C）。
- 否则（Else，E），选择 **L**atency（延迟，L）而不是 **C**onsistency（一致性，C）。

PACELC = CAP + "没有分区时，仍然用一致性换延迟"。
这正是只读副本和 CDN 存在的理由：它们降低延迟（和成本），代价是可能读到旧数据。

## 4. 负载均衡

- 把进入的流量分发到多台服务器。
- **类型：**轮询（Round Robin）、最少连接（Least Connections）、IP 哈希（IP Hash）、最短响应时间（Least Response Time）。
- 提升可靠性与可扩展性。

### 算法速查

| 算法 | 选取方式 | 适合场景 | 注意 |
|---|---|---|---|
| **轮询** | 按顺序轮流 | 机器同构、负载均匀 | 慢节点上会形成热点 |
| **加权轮询** | 按权重轮流 | 混合机型 | 需要人工调参 |
| **最少连接** | 选活动连接数最少的 | 长连接 / 单请求成本差异大 | 忽略单机 CPU 占用 |
| **IP 哈希** | 客户端 IP 哈希 | 会话保持 | 客户端少时不均衡 |
| **最短响应时间** | 选延迟最低的 | 异构 / 多地域 | 依赖准确的指标数据 |
| **一致性哈希** | 哈希环 + 虚拟节点 | 缓存集群、有状态分片 | 节点变更时需要再平衡 |
| **二选一（Power of Two Choices）** | 随机挑 2 个，取较优者 | 通用场景，均衡性极好 | 需要每节点统计信息 |

### L4 与 L7

| | **L4（传输层）** | **L7（应用层）** |
|---|---|---|
| 能看到 | TCP/UDP 连接 | HTTP 头部、路径、请求体 |
| 路由依据 | 只有 IP + 端口 | Host、路径、Cookie、Header |
| 能否卸载 TLS | 不能（只能透传） | 可以 |
| 开销 | 极小 | 较高（需要解析、缓冲） |
| 使用场景 | TCP/UDP、gRPC 透传、QUIC | HTTP API、缓存、限流 |

### 健康检查

- **存活探针（Liveness）** —— 进程还活着吗？失败意味着**重启** Pod。
  这里绝不要依赖下游服务，否则一次依赖故障会把整个集群重启一遍。
- **就绪探针（Readiness）** —— 现在能对外服务吗？失败意味着**从负载均衡摘除**，而不是重启。
- **启动探针（Startup）** —— 用于启动较慢的应用，在预热完成前不让负载均衡把流量打进来。

## 5. 扩缩容策略

| 策略 | 定义 |
|---|---|
| **垂直扩容（Scale Up）** | 给单台服务器加配置。 |
| **水平扩容（Scale Out）** | 在负载均衡后面加更多服务器。 |
| **自动扩缩容（Auto Scaling）** | 根据流量自动增删服务器。 |

**垂直扩容 vs 水平扩容**

| | 垂直扩容 | 水平扩容 |
|---|---|---|
| 上限 | 单机的物理上限 | 取决于软件设计 |
| 成本曲线 | 指数型（性能翻倍，价格远不止翻倍） | 接近线性，用多少付多少 |
| 故障影响 | 整机挂掉 | 众多节点中的一个挂掉 |
| 复杂度 | 简单 | 需要负载均衡、状态管理、节点协调 |
| 适合 | 数据库、有状态的老系统 | 无状态服务、读多写少的负载 |

**前提是无状态。** 把会话/状态挪到 Redis、数据库或对象存储，
这样任意 Pod 都能服务任意请求，水平扩容就变得非常简单。

## 6. 缓存

- 通过保存高频使用的数据来降低负载、提升响应速度。
- **类型：**浏览器缓存、CDN 缓存、应用缓存、数据库缓存。
- **工具：**Redis、Memcached。

### 缓存分层

| 层次 | 位置 | 典型 TTL | 失效方式 |
|---|---|---|---|
| 浏览器 / 本地 | 用户设备 | 分钟～天 | 用户清理、CDN 响应头 |
| CDN / 边缘 | 边缘节点 | 小时～天 | 刷新 API、源站版本号 |
| 应用内缓存（进程内） | 应用堆内存 | 秒～分钟 | 代码发布、TTL |
| 分布式缓存（Redis） | 集群 | 秒～小时 | TTL、显式删除 |
| 查询 / 行缓存 | 数据库引擎内 | 秒 | 写入 |

### 缓存策略（读路径）

| 策略 | 工作方式 | 未命中代价 | 说明 |
|---|---|---|---|
| **Cache-Aside（旁路缓存）** | 读缓存 -> 未命中 -> 读 DB -> 回填缓存 | +1 次 DB 读 | 最常用；必须配 TTL |
| **Read-Through（穿透读）** | 未命中时由缓存自己回源 | +1 次 DB 读 | 由客户端库封装 |
| **Write-Through（直写）** | 同时写 DB 和缓存 | 写变慢 | 缓存不会陈旧 |
| **Write-Around（绕写）** | 只写 DB，下次读时再填缓存 | +1 次 DB 读 | 适合很少被读的数据 |
| **Write-Behind / Write-Back（回写）** | 先写缓存，稍后异步刷到 DB | 有丢数据风险 | 需要持久化日志 |

### 淘汰策略与容量

- **LRU** —— 淘汰最近最少使用的。默认首选。
- **LFU** —— 淘汰使用频率最低的。适合访问热度倾斜的数据。
- **TTL** —— 按时间过期。唯一能真正防止脏读的手段。
- **Random / ARC / 2Q** —— 访问模式特殊时的替代方案。

> 经验法则：让缓存的工作集保持在缓存总大小的 70～80%，
> 这样被淘汰的是冷数据，而不是热数据。

### 缓存的四个经典难题

1. **缓存击穿（stampede / 惊群）** —— 热点 key 过期瞬间，上万请求同时打到 DB。
   对策：single-flight / 请求合并、TTL 加抖动、stale-while-revalidate、提前预热。
2. **缓存穿透（penetration）** —— 请求根本不存在的 key。
   对策：缓存空值（负缓存）、布隆过滤器、入参校验。
3. **缓存雪崩（avalanche）** —— 大量 key 同时过期。
   对策：TTL 抖动（±10～20%）、发布时预热、后台定时刷新。
4. **缓存失效（invalidation）** —— "计算机科学两大难题之一"。
   对策：版本号 key、事件驱动失效（CDC）、短 TTL 作为兜底。

## 7. 数据库

### 关系型数据库（SQL）
- 结构化数据，满足 ACID。
- **示例：**MySQL、PostgreSQL。

### 非关系型数据库（NoSQL）
- Schema 灵活，可扩展性高。
- **类型：**
  - **键值：**Redis、DynamoDB
  - **文档：**MongoDB
  - **列族：**Cassandra、HBase
  - **图：**Neo4j

### 分片（Sharding）
- 把数据拆到多个数据库实例上。
- 提升写入 / 读取的可扩展性。

**分片键策略**

| 策略 | 分配方式 | 优点 | 缺点 |
|---|---|---|---|
| **哈希分片** | hash(key) % N | 分布均匀 | 无法范围扫描；扩容迁移困难 |
| **范围分片** | 按 key 区间 | 天然支持范围查询 | 最新区间形成写热点 |
| **目录分片** | 查一张映射表 | 灵活，可按 key 精细控制 | 多一次查询；目录本身有单点风险 |
| **时间分片** | 按时间桶 | 过期与滚动归档简单 | 写入集中在最新桶 |

**分片的坑：**分片大小不均、跨分片 join、scatter-gather 扇出、
在线数据重新分片、每个分片一套连接池。

### 复制（Replication）
- 主从（Master-Slave）或 Leader-Follower 模型。
- 提升读可用性与容错能力。

| 诉求 | 方案 |
|---|---|
| 读扩展 | 只读副本（异步 = 可能读到旧数据；同步 = 增加写延迟） |
| 高可用切换 | 基于选主（etcd / Raft）的自动故障转移 |
| 写扩展 | Leader 写入是瓶颈 → 只能继续分片 |

### 存储引擎

| | **B-Tree**（MySQL InnoDB、PostgreSQL） | **LSM-Tree**（RocksDB、Cassandra、LevelDB） |
|---|---|---|
| 写入 | 原地更新数据页，随机 IO | 追加写 memtable + WAL，之后 compaction |
| 读取 | 点查/范围查都快 | 命中 memtable 很快，compaction 后变慢 |
| 写放大 | 低 | 高（compaction） |
| 读放大 | 低 | 中 |
| 适合 | 读多为主的通用 OLTP | 写多、写入吞吐高的场景 |

### 其他扩展手段

- **读写分离** —— 读走副本，写走主库。
- **反范式化** —— 用写入成本换读取速度。
- **CQRS** —— 读模型与写模型分离（读模型常放在搜索引擎里）。
- **归档 / 分层存储** —— 冷数据下沉到廉价存储（S3 + Athena）。

## 8. 系统架构模式

| 模式 | 说明 |
|---|---|
| **单体（Monolithic）** | 单一代码库、单一部署。简单，但难扩展。 |
| **微服务（Microservices）** | 小而独立的多个服务。可扩展、易维护。 |
| **SOA（面向服务架构）** | 服务之间通过企业服务总线通信。 |
| **事件驱动架构（EDA）** | 组件之间通过事件（异步）通信。 |

**同步调用 vs 异步调用**

| | 同步（REST / gRPC） | 异步（队列 / 事件） |
|---|---|---|
| 耦合 | 调用方阻塞，依赖被调方 | 松耦合，调用方不知道谁在消费 |
| 故障模式 | 调用方阻塞 / 超时 | 消息被缓冲、重试 |
| 延迟 | 计入用户请求链路 | 从请求链路中移除 |
| 一致性 | 更容易推理 | 最终一致，需要幂等 |
| 适合 | 需要立刻给答案的读操作 | 写操作、突发流量、扇出、慢任务 |

**服务边界：**按**业务能力**（限界上下文）拆分，而不是按技术分层
（"所有 Controller 放一个服务"）。团队归属对应服务；
两个团队抢同一个服务，说明拆错了。

## 10. 设计流程

六步走：

1. **理解需求** —— 厘清功能需求与非功能需求。
2. **确定目标与约束** —— 明确规模、延迟、可用性、一致性、预算。
3. **高层设计** —— 设计主要组件及其交互。
4. **详细设计** —— 设计每个组件与数据模型。
5. **容量估算** —— 估算存储、带宽、QPS 与资源需求。
6. **权衡与备选方案** —— 评估并记录权衡取舍。

### 真正决定设计的问题

| 问题 | 没人回答时的默认假设 |
|---|---|
| 读多还是写多？ | 假设读多（10:1） |
| 峰值 / 平均流量比？ | 假设 3～10 倍 |
| 是否多租户？ | 单租户，之后再加 tenant_id 列 |
| 是否需要强一致？ | 最终一致，会话内保证 read-your-writes |
| 是否全球部署？ | 单地域 + CDN，除非业务另有要求 |
| 预算 / 成本上限？ | 先保延迟，再用缓存与自动扩缩容降本 |
| 合规要求（PII、审计）？ | 静态与传输加密、审计日志、数据留存策略 |

### 高层设计草图

```text
Client
  |
  v
CDN ---> 静态资源
  |
  v
API Gateway  (TLS、认证、限流、路由)
  |
  +---> Service A  ---> Redis（缓存）
  |        |
  |        +---> Message Queue ---> Worker ---> DB / 对象存储
  |
  +---> Service B  ---> SQL 主库 ---> 只读副本
```

## 11. 容量估算速查

### 10 的幂（数据大小）

| 单位 | 字节（约数） | 字节（二进制，精确） |
|---|---|---|
| 1 KB | 10^3 = 1 000 | 2^10 = 1 024 |
| 1 MB | 10^6 = 1 000 000 | 2^20 = 1 048 576 |
| 1 GB | 10^9 = 1 000 000 000 | 2^30 = 1 073 741 824 |
| 1 TB | 10^12 = 1 000 000 000 000 | 2^40 = 1 099 511 627 776 |

> 面试约定：快速估算用 10^n；当问题落在实际存储上时用 2^n
> （磁盘上一个"1 MB 的文件"通常是 1 048 576 字节）。

### 10 的幂（用户规模）

| 用户数 | 约等于 |
|---|---|
| 1 000 | 10^3 |
| 100 万 | 10^6 |
| 10 亿 | 10^9 |

### 延迟数量级（取整数值，与"每个程序员都该知道的延迟数字"同一量级）

| 操作 | 耗时 |
|---|---|
| L1 缓存读 | ~0.5 ns |
| L2 缓存读 | ~3 ns |
| 内存读 | ~100 ns |
| SSD 随机读 | ~50～100 µs |
| 磁盘随机读（SSD） | ~150 µs |
| 同机房 TCP 往返 | ~0.5 ms |
| 同大洲跨地域往返 | ~30～50 ms |
| 跨大洲往返 | ~150～200 ms |

> 内存速度与网络速度之间的差距，是系统设计里最重要的一个数字：
> 通过网络搬运一个字节，代价约等于一次内存访问的 10^6 倍。

### 核心公式

- **带宽** = 数据传输量 / 时间
- **存储** = 数据量 × 副本因子
- **QPS** = 每秒请求数

### 一个完整估算示例

> *设计一个短链服务：每月新增 1 亿条短链，每天 1 亿次读取。*

1. **写 QPS** = 1 亿 / 30 天 / 86 400 秒 ≈ **40 次写/秒** —— 非常小。
   单台现代 Postgres 就足以承担写入。
2. **读 QPS** = 1 亿 / 86 400 秒 ≈ **1 150 次读/秒**（约 1.2k）。
   再按 10 倍峰值算 ≈ 12k 读/秒。
3. **存储** = 1 亿条 × 约 500 B（含元数据）≈ **50 GB/年**。
   3 副本 ≈ 150 GB，几年内一个卷都装得下。
4. **键值查询** —— 读路径就是按 key 做一次 GET，用 KV 存储
   或主库上的索引即可，不需要分片。
5. **缓存** —— 大概率 20% 的短链承载了大部分流量，
   用 Redis 或进程内 LRU 把读压力从 DB 上卸下来。
6. **跳转延迟目标** = 1 次 DNS + 1 次 TCP/TLS + 1 次查询 ≈ **< 100 ms**；
   热路径放在内存里，短码预先生成。

## 12. 一致性模型

| 模型 | 行为 |
|---|---|
| **强一致（Strong Consistency）** | 所有读都返回最新写入的值。可用性可能受影响。 |
| **最终一致（Eventual Consistency）** | 数据最终会收敛一致。可用性高，容忍分区。 |
| **弱一致（Weak Consistency）** | 某些读可能返回陈旧数据。可用性高。 |

### 更细的划分（面试常用词汇）

| 模型 | 保证 |
|---|---|
| **线性一致（Linearizable）** | 读写表现得像在同一份副本上，按真实时间顺序生效 |
| **顺序一致（Sequential）** | 所有节点看到相同的操作顺序（但可能读到旧值） |
| **因果一致（Causal）** | 有因果关系的操作按顺序可见 |
| **读己之写（Read-your-writes）** | 你一定能读到自己的写入（会话粘滞 / 版本号 token） |
| **单调读（Monotonic reads）** | 连续读取时不会"时间倒退" |

## 13. 故障处理

| 模式 | 说明 |
|---|---|
| **重试（Retry）** | 失败请求按退避策略重试。 |
| **超时（Timeout）** | 服务太慢就快速失败。 |
| **熔断（Circuit Breaker）** | 临时停止调用故障服务。 |
| **降级（Fallback）** | 主路径失败时返回备用结果。 |

### 重试的细节

- **指数退避** —— 延迟 = base × 2^尝试次数。
- **抖动（Jitter）** —— 加随机性，否则所有客户端会整齐划一地重试
  （恢复时形成惊群）。Full Jitter 是最简单也最有效的变体。
- **重试预算** —— 把重试量限制在总请求的某个比例（如 10%），
  避免重试风暴拖垮整个系统。
- **只重试幂等操作** —— 或者把操作改成幂等的（见下）。
- **重试放大** —— 3 层调用各重试 3 次 = 27 倍负载。
  要有全局策略，并把 deadline 往下游传递。

### 幂等性

| 手段 | 做法 |
|---|---|
| **幂等键（Idempotency key）** | 客户端带唯一 key，服务端把结果存一个 TTL，重放时直接返回 |
| **条件写** | `INSERT ... ON CONFLICT`、`UPDATE ... WHERE version = n` |
| **去重键** | 在业务键上建唯一索引，重复的直接拒绝 |
| **天然幂等** | 用 `SET key = value` 代替 `key = key + 1` |

### 降级阶梯（出问题时按顺序尝试）

1. **命中缓存** —— 返回旧数据（stale-while-revalidate）。
2. **兜底 / 默认响应** —— 返回一个降级但仍然有效的答案。
3. **负载丢弃（Load shedding）** —— 主动拒绝一部分流量以保护核心链路。
4. **熔断打开** —— 彻底不再调用已经故障的依赖。
5. **快速失败** —— 直接返回错误，绝不挂住。

> 可用性是一份预算：你调用的每个依赖都可能挂。
> 优先选择更少、更快、更可靠的依赖。

## 14. 监控与可观测性

| 支柱 | 用途 |
|---|---|
| **日志（Logging）** | 收集日志用于排查问题。 |
| **指标（Metrics）** | 收集指标（CPU、内存、QPS）。 |
| **链路追踪（Tracing）** | 跨服务追踪一次请求。 |
| **告警（Alerts）** | 对错误率、延迟等触发告警。 |

### 指标框架

| 框架 | 指标 | 适用对象 |
|---|---|---|
| **RED** | Rate、Errors、Duration | 所有对外提供请求的服务 |
| **USE** | Utilisation、Saturation、Errors | 所有资源（CPU、磁盘、网络） |
| **四大黄金信号** | 延迟、流量、错误、饱和度 | 服务级看板 |

### SLI / SLO / SLA / 错误预算

| 术语 | 含义 |
|---|---|
| **SLI** | 被测量的那个数字（如"99.9% 的请求 < 200 ms"） |
| **SLO** | 针对该 SLI 的目标值 |
| **SLA** | 对客户的合同承诺（通常比 SLO 更宽松） |
| **错误预算** | 1 − SLO，即允许消耗的"不可靠额度" |

> 错误预算用光了就冻结新功能，把时间花在可靠性上。
> 这是你写过最便宜的一条运维策略。

### 日志与追踪实践

- **结构化日志**（JSON），每行都带 `request_id` / `trace_id`。
- **三大支柱**：日志（细节）、指标（趋势）、追踪（位置）。
- **采样**：错误 100% 保留，正常流量采样 1%～10%。
- **基数（Cardinality）**：指标标签只用有界维度 —— 无界标签
  （如 user_id）会打爆指标后端。
- **对症状告警，而不是对原因告警**：页面告警用"错误率 > 2%"，
  而不是"CPU > 80%"。

## 16. 限流与背压

### 限流算法

| 算法 | 行为 | 是否允许突发 | 适用场景 |
|---|---|---|---|
| **固定窗口** | 每 N 秒重置计数器 | 窗口边界处会突发 | 简单，但边界会漏 |
| **滑动窗口日志** | 记录每个请求的时间戳 | 精确 | 低流量、要求精确 |
| **滑动窗口计数器** | 上一个窗口与当前窗口加权 | 平滑 | 通用场景 |
| **令牌桶** | 令牌按速率补充，每个请求消耗令牌 | 可以，最多到桶容量 | API、允许突发 |
| **漏桶** | 请求以固定速率流出 | 不允许 | 平滑流量，比如打到 DB |
| **并发数限制** | 限制在途请求数 | 不允许 | 保护稀缺资源 |

### 在哪里限流

- **边缘 / CDN** —— 保护整个源站不被洪峰打垮。
- **API 网关** —— 按用户、按 key、按路由维度。
- **服务自身** —— 防止被行为异常的内部调用方拖垮。
- **下游依赖** —— 保证你的 QPS 不超过 DB 能承受的上限。

### 背压（Backpressure）

背压 = 消费方跟不上时，系统主动让生产方放慢速度。常见机制：

| 机制 | 做法 |
|---|---|
| **有界队列** | 满了就拒绝（或阻塞）—— 最简单的背压 |
| **负载丢弃** | 按优先级只服务前 X% 流量，其余丢弃 |
| **自适应并发** | 动态限制在途请求数，把延迟维持在目标值 |
| **信用 / 配额制** | 消费方发放额度，生产方消耗额度 |
| **异步缓冲** | 先进 Kafka / Pub-Sub，让消费方慢慢追 |

> 无界队列不是背压，它只是一个多了几步的内存泄漏。
> 队列必须有界，并且明确"满了会怎样"。

## 17. 部署与发布策略

| 策略 | 做法 | 回滚 | 适用场景 |
|---|---|---|---|
| **滚动更新（Rolling update）** | 逐个替换实例 | 快（前滚或回退） | 无状态服务 |
| **蓝绿发布（Blue-Green）** | 准备两套相同环境，切换流量 | 瞬时（切回去） | 大版本发布；涉及 DB 变更需谨慎 |
| **金丝雀（Canary）** | 少量流量 -> 新版本 | 瞬时（停掉金丝雀） | 高流量服务 |
| **重建（Recreate）** | 全部停掉再启动新版本 | 会有中断 | 开发环境 / 批处理任务 |
| **Feature Flag** | 代码已部署但开关关闭 | 翻开关 | 把部署和发布解耦 |

### 数据库零停机变更

| 变更 | 安全做法 |
|---|---|
| 加字段 | 扩展：加可空字段 -> 回填 -> 双写 -> 切读 |
| 改字段名 | 加新字段，双写，迁移读端，之后再删旧字段 |
| 删字段 | 先停止使用 -> 等一个发布周期 -> 再删除 |
| 加索引 | 用在线 / 并发建索引，而不是阻塞式的 CREATE INDEX |
| 改类型 | 新字段 + 回填 + 切换（不要原地改类型） |

> **扩展 / 迁移 / 收缩（Expand / Migrate / Contract）** 是通用的三阶段模式。
> 永远不要在同一次发布里同时改表结构和改代码。

## 18. 高可用与灾难恢复

| 术语 | 含义 |
|---|---|
| **SLO** | 可用性目标，如 99.9%（"三个九"） |
| **可用时间预算** | 每个周期内允许的停机时间 |
| **RTO** | 恢复时间目标 —— 恢复服务需要多久 |
| **RPO** | 恢复点目标 —— 可以接受丢失多少数据 |
| **故障切换（Failover）** | 把流量切到另一个地域 / 集群 |
| **多可用区（Multi-AZ）** | 同地域不同可用区 —— 便宜，默认选项 |
| **多地域（Multi-region）** | 不同地域 —— 能扛住整个地域级故障 |

| 可用性 | 每年停机 | 每天停机 |
|---|---|---|
| 99% | 3.65 天 | 14.4 分钟 |
| 99.9% | 8.77 小时 | 86.4 秒 |
| 99.95% | 4.38 小时 | 43.2 秒 |
| 99.99% | 52.6 分钟 | 8.64 秒 |
| 99.999% | 5.26 分钟 | 0.86 秒 |

**设计手段**

- **主备（Active-Passive）** —— 备机待命；切换慢，成本低。
- **双活（Active-Active）** —— 两边都服务；切换快，但冲突解决很麻烦。
- **多地域读** —— 本地读，写复制回"主地域"。
- **备份 ≠ 复制** —— 复制出去的错误也会被复制。
  要演练恢复，并保留一份不可变 / 离线备份。
- **故障演练（Game day）** —— 平时要演练切换；没演练过的容灾方案只是传说。

## 19. 安全与 API 基础

| 领域 | 基线要求 |
|---|---|
| **传输** | 全链路 TLS；TLS 1.2+（优先 1.3）；HSTS |
| **认证（AuthN）** | 用户侧 OAuth2 / OIDC，短时效 JWT 或会话 Cookie |
| **授权（AuthZ）** | 每个请求都校验权限；默认拒绝；RBAC / ABAC |
| **密钥** | 绝不放进代码或镜像；用密钥管理服务并定期轮换 |
| **加密** | 静态加密（KMS 托管密钥）+ 传输加密 |
| **输入校验** | 白名单、参数化查询、大小限制 |
| **限流 / WAF** | 按身份限流，而不只是按 IP |
| **审计** | 记录谁在何时从何处做了什么（写入不可变存储） |
| **PII** | 最小化收集、加密、明确留存与删除策略 |

### API 版本与兼容性

| 变更 | 是否兼容 |
|---|---|
| 增加可选字段 | 是 |
| 新增接口 | 是 |
| 放宽类型（int -> string 这种则**不是**） | 视情况 |
| 删除 / 重命名字段 | 否 —— 需要升版本或先废弃 |
| 修改默认行为 | 否 |
| 修改错误码 / 状态码 | 否（客户端依赖它们） |

版本化方式：URL 路径（`/v1/...`）、请求头，或"扩展 / 收缩"式并行多版本共存。
要提前公布废弃时间，并通过埋点数据驱动旧版本下线。

## 20. 面试检查清单

开始画框之前，先准备好回答：

- [ ] 功能需求是什么？哪些明确不在范围内？
- [ ] 用户规模多大？人均每天请求多少次？
- [ ] 读写比例是多少？峰值与平均的比值是多少？
- [ ] 延迟目标（p50 / p99）和可用性目标分别是多少？
- [ ] 是否必须强一致，还是最终一致也可以？
- [ ] 全球部署还是单地域？是否多租户？
- [ ] 未来 12 个月的增长预期？
- [ ] 预算是多少？成本主要花在哪？
- [ ] 有哪些合规 / 数据驻留约束？
- [ ] 你最担心的故障域是哪个？

设计过程中：

- [ ] 画出高层架构图，并完整讲一遍一个请求的端到端流程。
- [ ] 把写路径和读路径分开讲。
- [ ] 指出瓶颈与扩展上限（"这个设计在 5 万 QPS 会挂，因为 ..."）。
- [ ] 给出数据模型（实体、键、基数）。
- [ ] 说明故障模式：某个依赖挂掉时会发生什么？
- [ ] 讲清楚你做了哪些权衡，以及预算更多时会怎么改。

| **幂等键** | 客户端生成的、让重试变得安全的唯一 token |

| **OpenTelemetry** | 与厂商无关的链路追踪与指标标准 |

| **读己之写** | 用户写入后立刻能读到自己的写入 |
| **RPO / RTO** | 恢复点目标 / 恢复时间目标 |
| **分片（Sharding）** | 把数据拆到多个数据库实例上 |
| **SLO / SLI** | 服务等级目标 / 服务等级指标 |
| **会话粘滞（Sticky session）** | 强制某个用户的请求始终落到同一个实例 |
| **吞吐（Throughput）** | 单位时间内完成的操作数 |
| **令牌桶** | 允许一定突发流量的限流算法 |
| **零停机发布** | 发布新版本时不断服务 |
